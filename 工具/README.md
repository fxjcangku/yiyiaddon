# 公开展示与双平台下载维护

平台展示名为 **Windows x64** 与 **Mac x64**，下载按钮分别写「下载 Windows x64」「下载 Mac x64」。Mac x64 只是展示名；实际架构、原生依赖和 Java 仍为 ARM64，Intel Mac 不在支持范围。文件后缀继续为 `win64`／`mac64`，不改真实附件名或历史发行事实。

## 真实附件与首页

`发行附件.mjs` 统一识别同一已公开 Release 的游戏版本与平台。只接受 `uploaded`、正大小且 URL 与固定仓库、tag、文件名一致的真实附件。每游戏的两个入口必须属于同一 Release；新版本缺 Mac 时不得借用 Windows URL 或旧版 Mac 伪装一对。历史无后缀包仅用于 Windows；真实 `desktop` JAR 保留原共享兼容性，不能当作两份新构建。

`更新公开首页.mjs` 依据真实公开目录刷新 README、品牌图、下载图和历史归档。每个游戏版本保留 Windows 卡片入口，并在同一单元内显示独立的 Mac 按钮；没有 Mac 包时显示无链接的待发布状态。两按钮使用同尺寸和字号，原生链接在 Markdown 中独立存在，不依赖 SVG 图片内部点击区域。旧版附件按所属 Release 保留，原有动态封面继续复用。

当 latest 为 1.3 起的分包系列（含 1.3.1）时，首页入口先执行四版本八专用包门槛，再生成任何文件；缺任意 Windows 或 Mac 包都会停止并保留现有首页，不能拿旧版本补齐后宣称本版已完整发布。1.2 及更早历史系列仍保留按游戏版本回退到实际 Windows 安装包的兼容行为。

```sh
node 工具/更新公开首页.mjs --latest /path/to/latest.json --catalog /path/to/catalog.json
node --test 工具/分平台下载.test.mjs
```

首页下载图片使用 `download-<模组版本>-<游戏版本>-<windows|mac>-<主题>.svg`，把实际版本与平台放进路径，避免 GitHub raw 分支路径缓存沿用旧按钮。原有固定路径图片继续保留，作为配色模板及历史兼容资源，不删旧图。

`.github/workflows/homepage-release.yml` 在刷新前运行上述回归测试，暂存白名单包含这些分版本、分平台资源。以后变更生成文件名时同步白名单，避免只有 README 更新而按钮资源遗漏。历史归档由 `生成历史版本.mjs` 识别实际新后缀；旧已发布说明、日期、附件和无后缀 Windows 记录不因模板更新改写。

## 1.3 准备与正式 Release

`生成1.3准备按钮.mjs` 和 `1.3准备页布局.mjs` 只用于准备状态：保留 18 组 146 条说明，卡片仅打开真实准备说明。出现正式 `发布说明/1.3.md` 后，准备生成器停止覆盖，避免恢复过时状态。

`整理发布页面.mjs` 的正式模板支持同一游戏版本的两平台按钮、包含平台的 SVG 文件名和去重的游戏版本列表。它只生成本地正文与资源，不修改 GitHub Release。1.3 正式模式必须核实四个游戏版本各有真实 `win64` 与 `mac64` JAR，共八个独立包；草稿、缺包和历史 desktop 都不能满足这一步。`--latest` 可传入 GitHub latest 的实际快照，明确当前正式版。

正式发包时，先完成独立构建及逐包校验，上传真实附件并公开后，再用同一份实际目录生成首页、历史归档和 Release 双按钮正文。提交生成资源后将 Release 图片固定到该资源提交，并回读四版本共八个按钮的实际链接。保留完整原始更新记录、封面与安装要求；独立检查官网、仓库首页、Release 三处的一致性。模板可运行不代表八包已经构建、上传或发布。

`生成1.3正式页面.mjs` 从现有完整 1.3 正文提取 18 组 146 条记录，复用 `composeRelease` 生成布局。它读取本次实际八包快照，核对准确附件清单和 SHA-256，在公开工作树之外暂存正文、资源、安装指南、功能指南与版本说明。正常模式只接受真实已公开 v1.3，完成后以 `发布说明/1.3.md` 为后续生成源，原准备地址变为正式记录指引。真实发布时间按北京时间显示，图内按钮与摘要来自当前附件。

```sh
node 工具/生成1.3正式页面.mjs --release /private/v1.3-published.json \
  --output-dir /private/v1.3-pages --asset-ref <资源提交的40位SHA>
```

上传后的草稿尚未公开时可加 `--draft-preview`。该模式只接受标签为 v1.3、八包均 uploaded 且带真实摘要的原始草稿快照，保留 `draft=true` 与空发布时间，标题明确标为草稿，只输出本地正文和资源。它不生成公开指南、不写 README，也不能绕过首页的真实正式版门槛。`PUBLIC_ASSET_REF` 仅供提交前本地排版预览，发送实际正文前须替换为已上传资源的确切提交 SHA。GitHub 草稿可能在 `html_url` 与附件 URL 中保留同一个 `untagged-...` 标识。只有显式 1.3 草稿预览接受与实际页面完全相同的本仓库标识，保留原 API URL；正式发布请求正文可为这些已经上传的准确文件使用目标 `v1.3` 地址。已公开记录继续严格按实际标签核对。工具不调用 GitHub 发布接口。

发布前资源与正文按同一份真实草稿快照处理。

1. 八包上传后，先使用 `--draft-preview --asset-ref PUBLIC_ASSET_REF` 输出私有预览。只把输出内的 `展示资源/theme/release-1.3-<MC>-{windows,mac}-{light,dark}.svg` 共 16 个图片文件复制到公开仓库并提交。此时 README 和当前指南保持真实公开状态。
2. 推送并回读这个资源提交，使用其确切 SHA 再运行草稿预览，并加 `--publication-body`。工具逐一读取该 Git 提交中的 16 个 SVG，与真实附件生成结果比较，任何错图或缺图均停止。正文资源引用使用该 SHA，不能继续保留占位符。
3. `release-body.md` 继续显示草稿身份，额外的 `release-publication-body.md` 是供正式发布请求使用的本地预备正文。该文件使用正式标题，不猜测发布时间，不改动输入中的草稿状态和空发布时间，也不生成公开指南。八包与发布验证决策由发布执行者另行完成，再将此正文用于实际正式发布请求。
4. 发布后回读真实公开快照，使用普通模式生成带真实日期的正式页和指南，再刷新首页与历史索引。既有功能回归记录与本次最终安装包验证分开填写，不能把旧记录当作当前包或双系统实机通过。

```sh
node 工具/生成1.3正式页面.mjs --release /private/v1.3-draft-uploaded.json \
  --draft-preview --publication-body --asset-ref <已推送资源提交的40位SHA> \
  --output-dir /private/v1.3-publication
```

合成八包回归只在内存和隔离临时目录进行，不访问网络，也不写入仓库 README 或实际 Release。真实 1.2 最小快照位于 `测试数据/1.2公开附件.json`。

## 后续分包版本

上述正式页入口保留旧名称并支持 1.3.1 等后续正式系列。新版本必须提供属于本版的 `--source` 正文，或已存在的 `发布说明/<版本>.md`／`发布准备/<版本>.md`；不自动借用 1.3 的18组146条及实测结论。正文须保留既定地图画封面、notes/install/compatibility/feedback 边界、四版依赖表与本版 `yiyiaddon:update-summary`。1.3 的原严格条目门槛保持，后续版本使用自身非空分组和条目。

```sh
node 工具/生成1.3正式页面.mjs --release /private/v1.3.1-draft-uploaded.json \
  --source /private/1.3.1.md --draft-preview --asset-ref PUBLIC_ASSET_REF \
  --output-dir /private/v1.3.1-preview
```

资源提交回读后可追加 `--publication-body` 并传确切资源 SHA；真实公开后去掉草稿参数重新生成当前指南与 `发布说明/1.3.1.md`。输出仅在指定仓外目录，旧 `发布说明/1.3.md` 与1.3附件保持。公开标题沿用本版真实 name，不自动添加“修复版”。未公开快照不能更新 README 或当前安装指南。
