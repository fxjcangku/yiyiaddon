# 04-埋点修复

> 这是「用户报的 bug 用常规手段修不好」时才启用的**运行时埋点修复**专用目录。
> 规则正本在 `开发习惯.md` 第三十三章（第 218~224 条），本文件只讲目录约定与工具用法。

---

## 一、什么时候才允许用它

同时满足这三条才启用（缺一条都不许开）：

1. **是用户报的 bug**（不是自己顺手做的「优化」）；
2. 已经按 `开发习惯.md` 第二十八章走过常规流程（复现 → 取样 → 静态分析 → 排除法），**仍然定性不出来**；
3. 已向用户说明「要用埋点修复方案 + 为什么必须用它」，**用户同意**（第 165 条）。

反面用法（禁止）：
- 拿它当常规调试手段（能靠日志/崩溃报告定性的，一律走第二十八章）；
- 拿它当「多打几行日志再看看」的借口——**每个探针都必须对应第 3 节里的一条判据**。

## 二、目录约定

```
04-埋点修复/
├── README.md                    本文件（总纲）
├── 案例模板.md                   新开一案时复制成 进行中/<案名>/README.md
├── 工具/
│   ├── 公共.js                  两个工具共用的函数（参数解析、表格排版、ndjson 读取）
│   ├── 采集服务.js               接收埋点事件、落盘 ndjson、提供查询接口
│   └── 分析.js                  读 ndjson 出结论（总览 / 时间线 / 分组 / 空档 / 会话对比）
├── 进行中/
│   └── <YYYY-MM-DD-一句话现象>/   一案一个文件夹：README.md（案例档）+ 日志-<会话名>.ndjson
└── 已修复/
    └── <YYYY-MM-DD-一句话现象>/   结案后整体移到这里
```

- **一案一个文件夹**，文件夹名 `YYYY-MM-DD-一句话现象`（同日多案加 `-2`、`-3`）。
- 案例档（`README.md`）照 `案例模板.md` 填；**假设必须先写，数据后采**，禁止事后编故事。
- 日志文件按会话名分开：`日志-修复前.ndjson`、`日志-修复后.ndjson`，
  《分析.js》的「会话对比」就是拿这几个会话横向比。
- `01-开发参考库` 那类只读资料不要往这里放；这里只有「案例 + 日志 + 工具」。

## 三、一分钟上手

```powershell
# ① 建案（自动复制模板，并起采集服务；Ctrl+C 停服）
node 04-埋点修复/工具/采集服务.js --案例 2026-09-17-某个现象

# ② 按案例档的埋点清单在 Java 侧插桩（骨架见 开发习惯.md 第三十三章），
#    然后另开一个窗口跑开发客户端复现：
.\gradlew runClient --console=plain

# ③ 看结论（默认挑最新日志；--列表 先看有哪些会话）
node 04-埋点修复/工具/分析.js --列表
node 04-埋点修复/工具/分析.js --案例 2026-09-17-某个现象 --会话 修复前
node 04-埋点修复/工具/分析.js --事件 begin --时间线
node 04-埋点修复/工具/分析.js --分组 data.pos --前N 10
node 04-埋点修复/工具/分析.js --空档 ts --最小间隔 500

# ④ 修完再采一遍「修复后」，对比会话
node 04-埋点修复/工具/分析.js --案例 2026-09-17-某个现象 --会话 修复后
```

采集期间也可以直接问服务：

```powershell
# 存活与计数
Invoke-RestMethod http://127.0.0.1:7777/health

# 查事件：返回值本身就是一个数组，直接 .Count / 下标即可
$事件 = Invoke-RestMethod "http://127.0.0.1:7777/logs?run=修复前&tail=30"
$事件.Count
$事件[-1].msg

# 打一个时间标记（分界点，分析时会单独列出）
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:7777/mark" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes('{"run":"修复前","label":"复现开始"}')) `
  -ContentType 'application/json; charset=utf-8'
```

> PowerShell 5.1 的坑：**不要写 `@(Invoke-RestMethod …)` 取条数** —— 它会把整个数组当成一个对象，
> `.Count` 恒为 1（本次实测踩过）。要么直接用返回值（`$x.Count`），要么 `| ForEach-Object { $_ }` 展开。
> 中文请求体一律用 `UTF8.GetBytes(...)` 传字节，否则会话名会变乱码。

## 四、工具参数

### 采集服务.js

| 参数 | 说明 |
| --- | --- |
| `--案例 <文件夹名>` | 在 `进行中/` 或 `已修复/` 下找同名案例；找不到会按「进行中」新建并复制模板 |
| `--目录 <路径>` | 直接指定案例目录（优先于 `--案例`） |
| `--端口 <数字>` | 默认 `7777`（与埋点契约一致，Java 骨架里写死了这个端口） |
| `--详细` | 心跳事件也逐条打印（默认每 100 条汇总一行） |
| `--安静` | 不打事件行，只看启动 / 关闭摘要 |

路由：`POST /event`、`POST /events`、`POST /mark`、`POST /clear?run=`、
`GET /logs?run=&tag=&location=&msg=&since=&limit=&tail=&raw=1`、`GET /runs`、`GET /export?run=`、`GET /health`。
事件契约（Java 侧照此发包）：`{"run","tag","location","msg","data"}`，服务端补 `ts` 与 `seq`。

### 分析.js

| 参数 | 说明 |
| --- | --- |
| `--列表` | 列出该案例的全部日志文件（会话名 / 条数 / 起止时间） |
| `--案例 <名>` `--目录 <路径>` `--文件 <路径>` `--会话 <名>` | 选日志（默认：全库最新的一份） |
| `--探针 A,B` `--位置 <子串>` `--事件 <名>` `--从 22:40` `--到 23:00` | 筛选 |
| `--时间线` | 逐条打印（`--完整` 不截断 data） |
| `--分组 data.pos` `--前N 10` | 按字段分组计数（裸 `--分组` = 按位置） |
| `--空档 ts --最小间隔 500` | 找相邻事件间隔过大的「空档」= 停摆 / 卡顿窗口 |
| `--JSON` | 以 JSON 输出结论 |

默认（不带模式）= **总览**：条数 / 时长 / 速率 / 标记 / 按探针 / 按位置 / 按事件 /
心跳节奏（含「可疑停摆」自动点名）/ 同案例会话对比。

## 五、结案（三件事，缺一不许归档）

1. **删插桩**：全部 `#region debug-point` 段落与埋点辅助类一起删；用 Grep 校验 0 命中；
   重新 `.\gradlew build --console=plain -q` 确认 EXIT=0，再重启客户端。
2. **停采集服务**：Ctrl+C；顺手确认端口不再监听。
3. **归档**：把案例文件夹从 `进行中/` 移到 `已修复/`，并在
   `02-开发报告/项目开发报告/` 写一份复盘（编号接续），案例档里注明报告编号。

> 埋点代码**永远不许留在发布产物里**（jar / 混淆版 / 公开仓库，见第 204 条）。
