# 77 - 复盘：「挖不动面前的方块」自愈误触发，掀翻秒破与连锁

- 日期：2026-09-17
- 触发：用户「⚠ 挖不动面前的方块 ▸ 重置采掘目标脱困 我怀疑是这个弄的 老是失效 秒破跟连锁」
- 涉及文件：`feature/mining/fsm/MiningStateMachine.java`
- 验证：`./gradlew build --console=plain` → **BUILD SUCCESSFUL（EXIT=0）**；**实机待确认**

---

## 1. 用户怀疑成立，chatlog 钉死时间线

```
21:22:12  [自动挖矿]已开启 / ✓ 前往野外
21:22:15  [自动挖矿]✓ 开始挖矿 ▸ 时运 · 青金石
21:22:18  [自动挖矿]Baritone 已启动挖掘：青金石矿石 等 2 种变体
21:22:38  [自动挖矿]⚠ 挖不动面前的方块 ▸ 重置采掘目标脱困     ← 20 秒
21:22:38  [自动挖矿]Baritone 已启动挖掘：青金石矿石 等 2 种变体
21:22:48  [自动挖矿]连锁挖矿 ▸ 识别到 2 块可挖矿脉，已接管挖掘  ← 10 秒后就出矿，说明那片区域正常
```

判据需要**连续 300 刻（15 秒）**成立，触发点距 mine 启动约 20 秒 —— 与「从进 `MINING` 起一直没进展」完全吻合。

## 2. 根因：计时器把「mine 初始化期」当成了「卡死」

原判据（1015-1018，改动前）：

```java
boolean mineNoProgress = !uiOpen
    && module.getBaritone().isPathing()
    && currentSpeed < MIN_SPEED_THRESHOLD     // 0.05
    && !MiningFastBreakController.instance().isActive();
```

落地后 Baritone 要**扫矿 → 算路径 → 等区块加载**，头 15~20 秒秒破**必然不 active**、玩家站着不动、
而 `isPathing()` 为真（它正在为这次 mine 寻路）——三条全部成立，于是**每次 RTP 落地后必然误触发一次**。

触发动作的破坏力正在于此：

```java
module.getBaritone().stop();                                   // ← 停掉 Baritone
...
module.getBaritone().startMining(module.getMiningTargets());    // ← 重新下发 mine
```

连锁接管时它把 Baritone 停在自己手里（`baritoneSuspended = true`），这个自愈却反手把 Baritone 重新拉起来
→ 两边同时认为自己控制着导航与挖掘 → 连锁的队列与秒破的目标状态被打乱，用户感知就是**「秒破跟连锁失效」**。

## 3. 修复：加两道「正常静止」的排除条件

```java
int sinceLastBreak = mc.player.tickCount - MiningFastBreakController.instance().lastBrokenTick();
boolean mineNoProgress = !uiOpen
    && mc.player.tickCount - mineStartTick > MINE_START_GRACE_TICKS   // ① mine 启动后 30 秒宽限
    && sinceLastBreak > MINE_PROGRESS_GRACE_TICKS                     // ② 最近 5 秒破坏过方块就不算无进展
    && module.getBaritone().isPathing()
    && currentSpeed < MIN_SPEED_THRESHOLD
    && !MiningFastBreakController.instance().isActive();
```

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `MINE_START_GRACE_TICKS` | 600（30 秒） | 覆盖「扫矿 + 算路径 + 等区块」的初始化期 |
| `MINE_PROGRESS_GRACE_TICKS` | 100（5 秒） | 块与块之间的间隙（含寻路到下一块）不该计成卡死 |

`mineStartTick` 在**三处**刷新，保证宽限总是从「一次新的 mine 启动」起算：
1. `onStateEnter(MINING)`（基准兜底，避免初值 0 让宽限直接失效）；
2. 主启动分支（`mineStartIssued = true` 之后，真正下发 mine 的那一刻）；
3. 自愈重下发处 —— 否则重下发后的「扫矿 + 算路径」空窗会立刻把第二次判定顶到，直接跳过第二级跳进「换区」。

取「最近破坏过方块」这个证据复用了秒破已有的 `lastBrokenTick()`（`MiningFastBreakController:494`），
不需要新增接口；秒破覆盖了绝大多数挖掘，块与块之间也会持续刷新它。

## 4. 保留了原有的兜底能力

真的挖不动（例如目标被保护方块封死、刷怪笼够不到）时，判据依然会成立 —— 只是从「落地 15 秒」变成
「mine 启动 30 秒后、且最近 5 秒确实没破坏任何方块、仍原地不动 15 秒」。两级阶梯不变：
第一次重下发 mine（先甩掉刷怪笼），第二次才 `GO_WILD` 换区。

## 5. 待实机验证项

1. RTP 落地后**不再**出现「⚠ 挖不动面前的方块」；挖矿在扫矿 + 寻路完成后正常起步。
2. 挖矿过程中不再被该自愈打断，秒破与连锁的「失效」现象消失。
3. 真的卡死（例如把目标封在保护方块里）时仍能自愈：先重下发、再换区，播报与原来一致。
4. 21:22 那种「落地 20 秒」的固定节拍不再复现。
