## 一、本阶段目标

把第六阶段建立的模块运行时与指令系统拉到实机验证，并补上资源链路最后一段缺失的实现，使「资源包识别」从「有框架无实现」变为「可真实解析、可缓存、可由玩家触发」的闭环。

本阶段交付的能力：

1. 客户端指令系统的实机验证（前缀 `.`、中文提示、错误提示、Tab 补全）
2. 模块快捷键的实机验证（开关、保存、重启恢复、与界面快捷键分家）
3. 资源内容探针 `ResourceContentProbe` 的默认实现（资源枚举、命名空间分类、内容指纹、分类计数）
4. 资源结果模型 `ResourceAnalysisResult`（来源、指纹、数量、分类、未知资源、解析状态）
5. 分析结果缓存（指纹一致读缓存、内容变化重新分析、不只看文件名）
6. 资源指令 `.resource`（检测 / 解析 / 状态 / 缓存）

本阶段不迁移任何业务模块，不做界面视觉改造，不改第五、第六阶段已定型代码的对外契约。

## 六、资源识别闭环设计

### 6.1 闭环链路

```
玩家输入 .resource check
        ↓
ResourceExtractionService.requestExtract()        （生命周期状态机，唯一入口）
        ↓
ResourceIndexProbe（已由 AddonModules 注册）
        ↓
ResourceEnumerator.list()                         （唯一接触 ResourceManager 的地方）
        ↓
ResourceClassifier                                 （挑出服务器自定义命名空间）
        ↓
ResourceFingerprint.compute()                      （按内容算指纹）
        ↓
ResourceAnalysisCache.load()                       （指纹一致 → 直接复用分类结果）
        ↓
ResourceAnalysisResult                             （来源 / 指纹 / 数量 / 分类 / 未知 / 状态）
        ↓
ResourceScanResult（精简）→ 生命周期服务就绪判断
ResourceAnalysisResult（完整）→ .resource 指令与后续业务模块
```

分层约束：`service` 只做判定与编排、`platform` 只做 Minecraft 适配、`repository` 只做持久化、`model` 只做数据。探针不自己读文件、不自己拼 JSON。

### 6.2 资源内容探针

`analyzeDetailed()` 五步，任一步失败都返回带原因的 `FAILED`，不伪装成「无资源」：

| 步骤 | 失败处理 |
| --- | --- |
| 枚举资源 | 资源管理器不可用或枚举抛错 → `FAILED`，原因入结果 |
| 过滤命名空间 | 不失败；目标为空即无目标命名空间 |
| 矛盾检测 | 命名空间列表里有目标命名空间、却一条资源都枚举不到 → `FAILED`（这属于接口失效，不是「服务器没有资源」） |
| 算指纹 | 单文件 / 总量超限只记 `skippedFiles`，由 `contentFull` 如实反映，不静默 |
| 查缓存 / 分类 | 命中则复用分类计数并标记 `fromCache`；未命中才逐条分类并写回缓存 |

另有 1 秒短时缓存服务 `loadedContentIds()`：生命周期服务在等待阶段逐刻调用它，没有缓存会导致每刻全量枚举资源树。且该缓存与指纹来自**同一次枚举**，避免「指纹描述新资源、内容 id 还是旧资源」的错配。

### 6.3 资源结果模型

`ResourceAnalysisResult` 为 record，覆盖阶段要求的六项，并额外承载三项必要信息：

| 字段 | 对应阶段要求 |
| --- | --- |
| `source` | 资源来源 |
| `fingerprint` | 资源指纹 |
| `total` | 资源数量 |
| `counts` | 资源分类 |
| `unknownCount` | 未知资源 |
| `state` | 解析状态 |
| `contentFull` | 追加：指纹是否覆盖全部定义类资源，区分「确实无内容」与「读取被跳过」 |
| `targetNamespaces` / `ignoredNamespaces` | 追加：命名空间归属，使误判可审计 |
| `fromCache` / `parsedAtMillis` | 追加：本次是否命中缓存与产生时间 |

与 `ResourceScanResult` 的分工：后者是给生命周期服务的精简输入（只有计数与 id），本记录是给指令、界面与后续业务模块读取的完整结果，并提供 `toScanResult()` 单向转换。

### 6.4 命名空间分类

客户端资源管理器里同时躺着原版资源、所有已加载模组自带的资源、服务器资源包与本地资源包的资源。只有第三类才是目标。

判定口径：内置基线（`minecraft`、`realms`、`fabric`、`yiyiaddon`、`baritone`）+ 全部已加载模组 id（含连字符替换下划线形式）。被排除的命名空间会随结果一并输出，误判可直接看出来，不需要猜。

实测输出（单人世界）：

```
目标命名空间：无
忽略命名空间：fabric、fabric-api-base、…、fabricloader、minecraft、realms、yiyiaddon
```

即分类器正确排除了原版与全部模组命名空间。

### 6.5 内容指纹

要求是「不能只看文件名」。实现口径：

- 全部资源 id 进哈希（这样新增 / 删除文件一定改变指纹）；
- `.json` 文件内容进哈希（方块状态、模型、语言文件的内容变化一定改变指纹）；
- 二进制文件（贴图等）只计路径，不读字节：逐字节读取几十兆贴图会把主线程拖死，收益却接近零；
- 单文件上限 512 KB、单次总上限 16 MB，超限跳过并计入 `skippedFiles`，不静默截断。

输出取 SHA-256 前 6 字节，共 12 位十六进制。

### 6.6 分析缓存

- 目录：`<游戏目录>/yiyiaddon_resourcepacks/.analysis/`，文件名即指纹 `<指纹>.json`。
- 选此位置的原因：`ResourcePackCache` 扫描缓存目录时只接受 `isFile() && length() > 0` 且只认 `.zip` 后缀，子目录不会干扰 ZIP 扫描。
- 读：按指纹查文件，命中即复用分类计数与未知数，并标记 `fromCache`；指纹不一致视为未命中，且**不删除**原文件。
- 写：仅在「完整分析成功且有目标内容」时写入；写入走 `JsonFileStore.writeAtomic`。
- 淘汰：上限 64 条，超出按最后修改时间删最旧。

之所以「无目标资源」不写缓存：此状态下指纹是空输入的哈希（常量），无法区分「确实没有目标资源」与「资源尚未加载完成」。若缓存它，一旦后续资源就绪就会错误命中，宁可重算也不写错。

### 6.7 资源指令

| 子命令 | 别名 | 行为 |
| --- | --- | --- |
| `check` | `检测` | 走完整生命周期（检查缓存 / 下载 / 等待生效 / 解析）；仅多人服务器可用，单人世界直接中文拦截 |
| `analyze` | `analyse`、`解析`、`分析` | 直接对当前已加载资源跑一次完整分析，不依赖服务器资源包，单人世界可用 |
| `status` | `状态` | 只读展示生命周期、来源、缓存文件、服务器键、指纹、失败原因与最近一次分析 |
| `cache` | `缓存` | 展示分析缓存条数与上限 |

全部中文，且不输出资源包下载地址等敏感信息。

## 八、问题记录

### 8.1 本阶段发现并已修复

1. **分类计数的展示顺序会抖动**（实机日志发现）。日志实际输出为「其它 0 / 语言 0 / 方块状态 0 / 模型 0 / 贴图 0 / 字体 0」，与 `ResourceCategory` 的声明顺序（方块状态 → 模型 → 贴图 → 语言 → 字体 → 其它）不符，且每次启动顺序可能不同。

   - 根因：`ResourceAnalysisResult` 紧凑构造器用 `Map.copyOf(counts)` 做防御性拷贝。`Map.copyOf` 返回的不可变 Map 迭代顺序由哈希盐决定，与插入顺序无关，因此探针里 `orderCounts()` 排好的顺序在这一步被丢弃。
   - 影响：纯展示问题。分类计数与 `.resource analyze` 的分类行顺序不可预测，同一份数据两次启动可能显示不同顺序；不影响计数正确性与指纹。
   - 修复：把顺序保证收到模型这一层——`ResourceAnalysisResult` 紧凑构造器改为按 `ResourceCategory` 声明顺序重建 `LinkedHashMap` 并用 `Collections.unmodifiableMap` 包装，未声明的分类按原顺序追加。同时删除探针中重复的 `orderCounts()`，避免两处各排一次。
   - 状态：已修复，编译通过；尚未重启客户端复测显示效果。

2. **`analyze()` 与指令需要的返回类型不一致**（编译期发现）。`ResourceContentProbe.analyze()` 的契约是返回精简的 `ResourceScanResult`，而 `.resource analyze` 需要完整结果。

   - 修复：拆出 `analyzeDetailed()` 返回 `ResourceAnalysisResult`，`analyze()` 改为 `analyzeDetailed().toScanResult()`，接口契约不变。

3. **首次枚举与内容 id 缓存可能错配**。`loadedContentIds()` 有 1 秒短时缓存，若 `analyzeDetailed()` 另行枚举，会出现「指纹描述新资源、内容 id 还是旧资源」。

   - 修复：`analyzeDetailed()` 用同一次枚举顺带刷新 `idsCache`，两者强制同源。

4. **解析失败与「无内容」混淆风险**。三条失败路径（资源管理器不可用、枚举抛错、命名空间有目标但枚举为空）原先都会退化成「无资源」。

   - 修复：三条路径统一返回 `FAILED` 并带中文原因，只有确实没有目标资源才是 `EMPTY`。

### 8.2 本阶段发现、未修复

1. **单人世界无法验证「指纹一致读缓存」路径**。单人世界的目标命名空间为空，无目标内容即不写缓存，第二次 `.resource analyze` 仍显示「完整分析」（日志已印证）。这是刻意的写缓存条件（见 6.6），不是缺陷；但意味着缓存机制的命中路径必须放到多人服务器或加载了自定义命名空间本地资源包的环境验证。
2. **指纹对二进制内容不敏感**。贴图逐字节不进哈希，因此「只改贴图内容、不改文件名与路径」的变化不会被指纹识别。这是为控制主线程开销做的取舍，已由 `contentFull` 之外无任何标记提示用户。若后续星露谷资源依赖贴图区分作物，需要重新评估是否对贴图做采样哈希（例如按固定步长抽样若干字节）。
3. **资源枚举与指纹在主线程执行**。虽有 1 秒短时缓存与文件上限，但大型整合包首次 `.resource analyze` 仍会有一次可感知的停顿，未做大资源包实测。
4. **`ResourceClassifier` 排除表依赖模组 id**。模组若使用与自身 id 完全无关的命名空间（既不在内置基线里，也不等于任何模组 id），会被误判为目标内容。当前实现会把该命名空间如实输出，属于可审计而非静默误判，但根因未解决。

### 8.3 观察到的环境问题

1. 并行编辑仍在继续（本次验证期间 `CardPage.java` 一度编译失败，`AddonModules` 分类图标被改）。重要阶段验证期间建议冻结编辑，否则编译失败与运行差异的责任归属只能靠分析错误位置判断。
2. 第四至第七阶段成果仍未提交 Git。第七阶段报告定稿时工作区依然只有未提交改动，一旦误操作不可回滚。
