## 一、对账方法（本轮确立）

任何「与旧项目不一致」的结论，动手前必须先取证，取证来源限定为四类：

| 证据类型 | 本轮用法 | 解决了什么争议 |
| --- | --- | --- |
| 旧项目源码 `文件:行号` ＋ 原文摘录 | 逐方法读两边的 `IdIdentifyModule` / `IdConfigModule` / `IdCommand` / `ItemIdentity` / `ItemIdentifier` / `BlockIdentifier` | 判定「判据是否同源」 |

## 二、逐条核对结论

### 2.1 `.id 方块` 在「聊天复制/显示」下静默：既不保存也不弹窗 —— **真移植偏差**

| | 旧项目 | 新项目（修复前） |
| --- | --- | --- |
| 判据 | `mode == AUTO_SAVE` 才保存，**其余模式一律弹结果窗** | `mode == CROSSHAIR_BLOCK` 才弹窗，其余走 `savesToLibrary()` |
| 聊天复制/显示 | 弹 `BlockResultScreen`，不写盘 | 不弹窗、不写盘，只剩一条聊天回执 |
| 准星方块识别 · `.id 物品` | 弹 `IdResultScreen`，不写盘 | **会落盘**（`savesToLibrary()` 为真） |

证据：旧项目 `itemid/IdCommand.java` 的物品 / 实体 / 方块三条路径均为 `if (mode == AUTO_SAVE) { …落盘… } else { mc.execute(() -> mc.setScreen(new XxxResultScreen(...))); }`；新项目 `feature/identity/IdIdentifyModule.java` 两个方法把判据写成了另一个枚举值。

**根因**：新项目在识别模式之外又自造了第二份判据 `IdentityModuleConfig#savesToLibrary()`（仅「聊天复制/显示」为假），与旧项目的单一判据方向相反，两个入口各判一次、互相矛盾。

### 2.2 准星朝天也能保存方块（写出空气） —— **两边本来就一样**

`BlockIdentifier.identify()` 在两边**逐字相同**，都只判 `hit instanceof BlockHitResult`。准星朝天空 / 朝空气时 `mc.hitResult` 同样是 `BlockHitResult`，只是类型为 `Type.MISS`，其坐标是射线端点附近的空气方块，因此会被当成命中方块写出 `minecraft:air`。

经用户确认：**两个项目一起加拦截**。

### 2.3 「ID配置管理 → 识别准星方块」无条件保存、不跟随识别模式 —— **两边本来就一样**

旧项目该方法注释原文即「与「识别物品」对称，**不再弹复制框**」，直接落盘 + 播报，且全类不引用识别模式；新项目实现逐字对应。

经用户确认：**两边一起改成跟随「ID识别」的模式**（属于对旧项目行为的追加修改，不是回退）。

### 2.4 沙子被判为「自定义物品」 —— **两边判据逐字相同**

真实存档证据 `d:\mcaddon\yiyiaddon\run\AutoChest\items\沙子.json`：

```json
{
  "物品ID": "minecraft:sand",
  "显示名称": "沙子",
  "原始名称": "沙子",
  "物品类型": "自定义",
  "自定义物品": true,
  "物品名称": "沙子",
  "物品模型": "minecraft:sand",
  "数量": 20,
  "数据版本": 4790
}
```

服务器给了 `minecraft:item_name = 沙子` 组件，`ItemIdentity#isCustom()` 命中 `itemName 非空` 这一条。该判据与 `ItemIdentifier` 的提取逻辑在两边**逐字相同**（旧 `itemid/ItemIdentity.java` 与新 `model/identity/ItemIdentity.java` 的 `isCustom()` 完全一致），**不是移植偏差，旧项目同样会把沙子判为自定义**。

经用户确认：**两边一起收紧**（`itemName` 与注册表默认名相同时不构成自定义证据）。该判据不参与身份键构造，只影响分组与类型名。

### 2.5 目标物品列表里自定义条目没有图标 —— **新项目自造增强的副作用**

旧项目 `ItemTargetSelectScreen` 的列表**本来就只有文字**，没有图标；图标是新项目自建的展示增强。新项目 `AutoChestPage.ItemEntry#drawIcon` 第一行 `if (!vanilla) return false;`，导致非原版条目一律不画。

经用户确认：**两边一起改**（不再按原版/自定义一刀切，按真实载体物品取贴图，取不到才回退纯文字）。旧项目侧无此列表图标逻辑，本条实际只落在新项目。

### 2.6 目标物品列表的空分组连标题一起消失 —— **真移植偏差**

| | 旧项目 | 新项目（修复前） |
| --- | --- | --- |
| 分组标题 | 无条件先画 `§a§l▌ 原版物品`、再画 `§d§l▌ 自定义物品`，空分组补一行 `§8无` | 按组收集，**组内为空整组不渲染**（标题一起消失） |

证据：旧项目 `itemid/ItemTargetSelectScreen#rebuild()` 逐个分组调用 `addAvailableByType(...)`，返回 `false` 时补 `theme.label("  §8无")`；新项目 `ui/screen/SelectorScreen#buildAvailable` 用 `LinkedHashMap` 先看有没有内容再决定要不要建组。

### 2.7 两个「清除…处理记录」按钮的显示条件 —— **两边本来就一样，且旧项目从未有过「只在标点模式」的版本**

**git 取证（旧项目）**：

```
8f2331a9  首次引入这两个按钮时即无条件添加，与「设置箱子点位 / 删除箱子点位 / 查看当前设置箱子信息 / 清空全部点位」并列
3ab2435f  只把点位类按钮收进 if (markerMode)，两个清除按钮留在外面，
          并显式加注释「处理记录清除（三模式通用：ESP 显示处理状态，与运行模式无关）」
```

即 git 历史里**不存在**「清除记录按钮只在标点模式出现」的版本。新项目 `AutoChestPage#buildMarkerActions` 与旧项目当前源码同构。

经用户确认：**两边一起改成只在标点模式显示**（属于对旧项目行为的追加修改）。

### 2.8 「ID识别」模块点击开启即识别丢失 —— **真移植偏差**

| | 旧项目 | 新项目（修复前） |
| --- | --- | --- |
| 开启行为 | `onActivate()` 完整执行一次识别（准星方块识别模式下识别方块，否则识别主手 → 副手），随后 `closeQuietly()` 静默自关 | `onEnable()` 只做 `load()` ＋ 清理失效目标，不识别 |
| 残留 | — | `identifyByMode()` 存在但**全项目无调用点**（死代码），模块 description 仍写着「点击开启即识别」 |

### 2.9 三件套整体对齐体检（用户要求「看看是不是对齐了」）

| 检查项 | 结论 |
| --- | --- |
| `.id` 命令树 | 对齐：旧项目无参数 + 3 个字面量叶子（物品 / 实体 / 方块）；新项目 `IdentityCommand` 同构 |
| `IdentifyMode` 枚举 | 对齐：三个取值同名、同显示名、同默认值 `AUTO_SAVE` |
| 结果窗口 | 数量对齐（物品 / 方块 / 实体三个），但打开条件见 2.1（真偏差） |
| `ItemIdentity` / `ItemIdentifier` | 逐字一致（除包名与新项目的 `platform` 分层） |
| `IdConfigModule` 设置项 | 对齐：旧项目该模块不注册任何设置项，新项目同样不定义设置 |
| `IdIdentifyModule` 设置项 | 对齐：`识别模式` + `方块语义调试` 两项 |
| `IdConfigModule` 面板按钮 | 对齐：5 个按钮文案逐字 |
| 行为偏差 | 仅 2 处：模式分支判据（2.1）与「点击开启即识别」丢失（2.8） |

结论：**不是「上一个实现整体搬错」，三件套骨架与数据模型是对齐的；偏差集中在两处行为分支与一处新项目自造的展示层。**

### 3.2 实机验收反馈的三条修复（2026-09-15，用户拍板后追加）

**背景证据（先取证后动手）**：Meteor 本体 `Module.toggle()`（`meteor-client-26.1.2-SNAPSHOT-sources.jar`）里 `toggle()` 是**唯一**开关入口，GUI 开关与快捷键都走它，激活时调 `onActivate()`；`Modules.onAction` 快捷键回调也只调 `module.toggle()`。因此旧项目 `IdIdentifyModule` 的 `onActivate()`（识别一次 ＋ `closeQuietly()`）**在 GUI 点开关时同样会触发**，「开一下立刻关」是旧项目真实行为，不是移植错误。

| 现象 | 判定 | 改动 |
| --- | --- | --- |
| `.id 方块` 提示「模块未启用」不给保存 | **真偏差**（旧 `IdCommand` 中 `isEnabled`/`enabled`/`requireEnabled`/`模块未启用` **0 命中**，`.id` 指令从不看模块开关） | `IdIdentifyModule` 删除 `requireEnabled()` 及其在三处识别入口的调用；连带删掉用不到的 `CommandManager` import。自造文案「`.module on id_identify 可开启`」随之消失 |
| `.module 开 ID识别` 后「已开启」与「模块未启用」自相矛盾 | **真 bug**（`onEnable` 内 `closeQuietly()` 自关后，`tryEnable` 仍执行 `persistEnabled(true)` 并播报「已开启」→ 内存 false / 配置 true） | `ModuleManager.tryEnable` 在 `onEnable` 返回后复查 `module.isEnabled()`：已自关则写回 `false` 并跳过「已开启」播报。该修复对全部「自关型」模块生效 |
| 开关点一下没有动画 | 旧口径下的**观感**问题（同一帧内开→关，弹簧两次目标相互抵消），且该步延后不影响任何行为 | `IdIdentifyModule` 自关改为**延迟 8 刻（约 0.4 秒）**执行（`pendingSelfCloseTicks` ＋ `onTick` 倒计时，`onDisable` 里撤销），让滑块先滑到位再回弹；行为仍是「识别一次后必定自关」，不额外播报任何东西 |
