## 一、本次迁移目标

把旧项目 `D:/mcaddon/26.1.2` 中三组与框架无关的基础能力，按 yiyiaddon 自研架构重新组织后迁入
`D:/mcaddon/yiyiaddon`，并在迁移过程中彻底切断旧框架依赖。

三组目标：

| 组 | 旧实现 | 目标产物 |
| --- | --- | --- |
| 第一部分 | `farm/ContainerBroker`、`farm/FarmPacketOps` | 容器交互服务、发包服务、预测同步基础 |
| 第二部分 | `resourcepack/ResourcePackDownloader`、`resourcepack/BlockStateModelResolver`、`resourcepack/ServerResourceService` | 资源包检测、下载缓存、SHA 校验、资源生命周期、方块状态语义识别 |
| 第三部分 | `itemid/*`、`worldblock/*` | 物品 / 实体 / 方块身份识别、JSON 持久化、快照系统、中文数据结构 |

边界说明（本批不做）：

- 星露谷、自动农场、自动挖矿、自动箱子、村民交易、图书管理员、附魔、传送、自动登入、绕过与战术系统一律未迁移。
- 旧项目的旧框架 `Setting` / `Command` / `Screen` 需要 yiyiaddon 的模块系统、指令系统与界面框架支撑，而该框架目前尚不存在，因此本批只迁移其数据部分，界面与指令部分未实现（见第九节）。
- 未修改旧项目任何文件。

## 四、分类调整说明

### 4.1 分类依据

按项目规范第十章七类目录划分：`model`（数据模型）、`service`（业务服务）、`repository`（数据存储）、`platform`（Fabric / Minecraft 适配）、`integration`（第三方兼容）、`config`（配置管理）、`utils`（通用工具）。原则：

- 数据与行为分离：模型只放 record / 值对象 / 枚举，不含任何 Minecraft 调用；
- 数据与存储分离：仓储只做文件读写，不持有监听器、不做业务判断；
- 存储与适配分离：路径解析、注册表访问、包构造一律放 `platform`；
- 对外只暴露服务：业务模块只调 `service`，不直接接触 `platform` 与 `repository`。

### 4.2 关键拆分

**`ContainerBroker`（旧 1 个类）→ 3 个类**

| 拆分结果 | 归属理由 |
| --- | --- |
| `ContainerTransferResult` | 纯枚举，属于数据模型 |
| `ContainerAccess` | 全是 `AbstractContainerMenu` / `Slot` / `ContainerInput` 读写，属 Minecraft 适配 |
| `ContainerService` | 承载 `stateId` 稳定性观测与「先判断再搬运」的业务动作，属服务 |

旧实现把三者塞在一个类里，且枚举嵌套在类中，导致仓储 / 服务 / 适配三层混在一起。

**`FarmPacketOps`（旧 1 个类）→ 2 个类**

| 拆分结果 | 归属理由 |
| --- | --- |
| `BlockPacketSender` | 预测窗口、`sequence` 取号、包体构造，全是协议与 Minecraft 适配 |
| `PacketService` | 对外 API 与耐久工具，供业务模块调用 |

**`ServerResourceService`（旧 1 个类，1042 行）→ 5 个类 + 1 个接口**

| 拆分结果 | 归属理由 |
| --- | --- |
| `ResourcePhase` / `ResourceSource` / `ResourceScanResult` | 枚举与记录，属数据模型 |
| `ResourcePackCache` | 下载、缓存命名、SHA 校验、指纹，属服务（文件与网络，不碰游戏状态） |
| `ResourceExtractionService` | 生命周期状态机，属服务 |
| `ResourceContentProbe` | 识别内容由业务层注入的解耦接口，属服务契约 |

旧实现把「下载器」与「生命周期」放在两个文件，但生命周期里直接 `import` 星露谷扫描器与选择器分类，
导致资源链路无法脱离星露谷使用。新实现通过 `ResourceContentProbe` 反向注入，生命周期不认识任何具体资源结构。

**`BlockStateModelResolver`（旧 1 个类）→ 2 个类**

| 拆分结果 | 归属理由 |
| --- | --- |
| `ResourcePackAccess` | 「按资源包优先级读 JSON」是通用能力，独立后可被其它解析器复用 |
| `BlockStateModelResolver` | 只负责「方块状态 → 变体匹配 → 语义身份派生」 |

**身份体系（旧 24 个类）→ 按层重组**

| 旧位置 | 新位置 | 依据 |
| --- | --- | --- |
| `ItemIdentity` / `EntityIdentity` / `BlockIdentity` / `IdentifyMode` | `model/identity` | 纯数据 |
| `ItemIdentifier` / `EntityIdentifier` / `BlockIdentifier` | `platform/identity` | 全部依赖注册表与游戏对象读取 |
| `ItemIdentityMatcher` | `platform/identity` | 需要 `ItemStack` 才能匹配 |
| `ItemIdManager` / `EntityIdManager` / `BlockIdManager` | `repository/identity` | 只做文件读写与去重 |
| `ItemSnapshotManager` / `BlockSnapshotManager` | `repository/identity` | 同上 |
| `ItemTargetSetting` 的数据部分 | `config/identity` | 属配置持久化 |
| 三处重复的文件事务逻辑 | `repository/JsonFileStore` | 收敛为唯一实现 |
| 三处重复的文件名清洗 | `utils/FileNames` | 收敛为唯一实现 |
| 无对应物 | `service/identity/IdentityService` | 统一门面，避免业务模块直接持有 5 个仓储 |

### 4.3 为满足「model 不访问 Minecraft」所做的改动

旧实现中三个身份类都直接调用注册表，已全部上移到 `platform`：

| 旧实现位置 | 新实现位置 |
| --- | --- |
| `ItemIdentity#resolveItem` / `#matches` | `ItemIdentityMatcher`（platform） |
| `ItemIdentity.fromItemId` / `fromItemAndCustomName` / `fromCustomSpec` | `ItemIdentifier`（platform） |
| `ItemIdentity.fromJsonObject` 内的注册表校验 | `ItemIdentifier.exists`（platform，由 `IdentityService.load()` 调用） |
| `EntityIdentity.fromJsonObject` 内的注册表校验 | `EntityIdentifier.exists`（platform，由 `EntityIdentifierRepository.pruneMissing` 调用） |
| `BlockIdentity.fromJsonObject` 内的注册表校验 | `BlockIdentifier.exists`（platform） |
| `BlockIdentity#resolveBlockName` | `BlockIdentifier.localizedBlockName`（platform），结果作为 `blockName` 字段传入模型 |
| `BlockIdentity#dimensionDisplay` | `WorldIdentity.dimensionDisplayName`（platform） |

副作用：`BlockIdentity` 相比旧版新增 `blockName` 字段，用于保留 JSON 中的「方块名称」。

### 4.4 数据路径与兼容决定

- 身份数据根目录沿用 `<游戏目录>/AutoChest`（含 `items` / `entities` / `blocks` / `snapshots` / `block-snapshots`）。
  **原因**：既有玩家数据已落在该目录，改名会让历史数据全部失联。目录名保留历史来源痕迹，但字段结构与文件语义已按新架构重新定义。
- 资源包缓存目录沿用 `<游戏目录>/yiyiaddon_resourcepacks`，缓存命名规则沿用 `<host>_<port>.zip`，
  并保留对历史命名（`<host>_<中文名>.zip`、`<host>.<port>.zip`）的识别，旧缓存可直接复用。
- 新增的身份目标配置写到 `config/yiyiaddon-identity-targets.json`，与既有 `yiyiaddon.json` 分离，避免污染界面配置。
- JSON 字段名全部沿用旧版中文字段（如「物品ID」「方块状态」「状态指纹」），并保留英文字段读取兼容分支，旧档可直接读取。

## 六、修改内容

### 6.1 第一部分

1. **容器搬运结果枚举独立**：`DepositResult` 由 `ContainerBroker` 的内部枚举提升为 `model/container/ContainerTransferResult`，并新增中文文案与两个语义判定方法（`isWaiting` / `isEmptyResult`）。

4. **搬运逻辑不变**：`depositOne` 仍为「只处理背包侧槽位、放不下则跳过该槽位继续找、有匹配但都放不下返回箱子满」；`withdrawOne` 仍在背包无空位时不发包。

6. **耐久工具上移**：`getRemainingDurability` 从发包层移入 `PacketService`，语义不变（不可损坏物品返回 `Integer.MAX_VALUE`）。

### 6.2 第二部分

1. **生命周期去星露谷化**：`Phase` 枚举中的 `NOT_STARDEW` 改为 `NO_CONTENT`（未发现目标资源）；六类硬编码计数（作物 / 盆 / 肥料 / 药剂 / 水壶 / 洒水器）改为 `ResourceScanResult` 的分类计数表，分类名由探针定义。
2. **解析与通知解耦**：解析阶段由「调用星露谷扫描器并统计六类」改为「调用 `ResourceContentProbe.analyze()`」，未注册探针时空结果直接进入 `NO_CONTENT`。

### 6.3 第三部分

1. **模型去 Minecraft 依赖**：三个身份类不再调用注册表；`EntityIdentity` 去掉瞬态 `EntityType` 字段；`ItemIdentity` 去掉瞬态 `Item` 字段与 `matches` 方法；`BlockIdentity` 去掉维度展示方法与方块名解析方法并新增 `blockName` 字段。

7. **方块库迁移逻辑保留**：`BlockIdentityRepository` 完整保留旧版迁移流程——检测重复稳定键或文件名不符当前命名规则时，先整目录备份到 `blocks-backup-<时间戳>/`，备份不完整则放弃迁移，再按稳定键去重（保留时间最新）并用新命名重写。
8. **清单变化**：方块库、方块快照库、物品身份库、物品快照库、实体身份库的目录与文件名规则全部保持不变，旧数据可直接读取。
9. **单人存档标识**：`WorldIdentity.server()` 的单人分支由旧框架工具方法改为按 `level.dat` 父目录名取唯一标识；多人分支补齐端口、统一小写、IPv6 加方括号，并删除旧版「不补端口、不小写」的第二套实现（旧版 `WKCommand` 那套未迁移）。
10. **配置重写**：`IdentityTargetConfig` 只持久化身份键集合，提供 `selectedItems` / `pruneInvalid` / `countText` / `setItemSelected` / `reset`，对应旧 `ItemTargetSetting` 的数据部分（`pruneInvalid` / `selectedIdentities` / `countText` 三项语义一致）。
11. **入口接线**：`YiyiAddonClient` 新增三个调用——`IdentityTargetConfig.load()`、`IdentityService.shared().load()`、`ResourceExtractionService.init()`。

### 6.4 Mixin 注册

`yiyiaddon.mixins.json` 的 `client` 数组新增三项：`ClientLevelPredictionAccessor`、`ModelManagerReloadMixin`、`ResourcePackPushMixin`。该文件 `required` 为 true、注入器 `defaultRequire` 为 1，注入点签名不符会导致启动失败，因此本次改动风险集中在启动阶段，已通过启动验证（见第八节）。

## 九、遗留问题

### 9.1 本批未迁移、需后续补齐的内容

1. **旧框架 Setting / Command / Screen 未迁移**：旧 `ItemTargetSetting` 的界面控件、`IdCommand`、6 个 Screen

   （详见 9.5），缺的是模块运行时（生命周期 / 开关 / 持久化）与指令系统。
   已迁移的只有数据部分（`IdentityTargetConfig`）与识别部分（`ItemIdentifier` / `EntityIdentifier` / `BlockIdentifier`）。
2. **资源内容探针无实现**：`ResourceContentProbe` 只有接口，没有实现类。当前资源生命周期在解析阶段必然得到空结果并进入「未发现目标资源」。真正的解析实现（星露谷六类资源扫描）属后续批次。
3. **`ResourceExtractionService.requestExtract()` 无调用方**：当前没有任何界面或指令触发它，因此资源链路实际处于「只识别服务器、不动作」状态。这是本批的预期状态，但需注意：该服务在真机上目前不会产生任何可见效果。
4. **`IdentityMode` / `IdentifyMode` 无消费方**：识别模式枚举已迁移，但没有模块使用它。
5. **星露谷坐标 / 点位的 `WKCommand` 第二套服务器键实现未统一**：本批统一了 `WorldIdentity` 的口径，但挖矿点位、村民交易点位等模块尚未迁移，其历史文件格式（不补端口、不小写）在迁移时需要单独处理。

### 9.2 迁移过程中发现并已处理的问题

1. **旧 `ContainerBroker.hasChestSpace` 未判 `menu` 为空**：传入 null 会抛异常。新实现已加入空值防护。
2. **旧 `ItemIdentity.sanitizeFileName`、`BlockIdManager.sanitizeFileName`、`BlockSnapshotManager.sanitize` 三份实现**：正则与兜底值不完全一致（兜底分别为传参、`block`、`block`）。新实现统一到 `FileNames.sanitize`，调用方各自传入自己的兜底值，行为与原实现等价。
3. **旧三处文件事务代码存在细微差异**：`ItemIdManager` 与 `EntityIdManager` 在取消 `used.add` 的顺序上写法不同（`ItemIdManager` 先 add 再 remove 复用，`EntityIdManager` 直接判断）。新实现统一为 `JsonFileStore.plannedFileName` 的集合判断，结果一致但可读性提升。
4. **旧 `BlockSnapshotManager.clear()` 失败时会 `reload()` 重建索引**：新实现保留该行为（不谎报已清空）。
5. **旧 `ServerResourceService` 的 `Environment` 枚举转发自旧框架的世界上下文工具**：新实现改为直接调用 `GameProbe.inWorld()` 与 `GameProbe.isSingleplayer()`，删除了「枚举名转发」这层无意义转换。
6. **旧 `ResourcePackPushMixin` 同时承担观测与策略两件事**：策略部分依赖 `ServerDetector` 模块，本批删除策略部分，只保留观测；后续若需要资源包拦截策略，应在模块框架建立后由模块自行订阅。

### 9.3 尚未解决的问题（如实记录，未尝试修复）

1. **`ItemIdentity` 与 `BlockIdentity` 的 equals 语义不一致**：`ItemIdentity` 重写了 `equals` / `hashCode`（按身份判据），`BlockIdentity` 是 record（`equals` 比较全部字段，包括坐标与状态）。这是旧实现的原样保留，未做统一。影响：方块库去重依赖 `identityKey` 手工判重而非 `equals`，`BlockIdentityRepository.add` 中的 `existing.equals(identity)` 判断实际比较的是全字段，与「状态变化即更新」的注释语义一致但容易被误读。
2. **`IdentityService.load()` 清理失效条目的方式为逐个 `remove`，每次都会触发一次整目录重写**：条目较多时是 O(n) 次目录写。旧实现没有这段清理逻辑，属新增行为，尚未做性能验证。

4. **`ResourcePackAccess.verbose` 与 `BlockStateModelResolver.setVerbose` 为全局可变开关**：旧实现的 DEBUG 开关也是静态的，本批未改。
5. **`GameProbe.isSingleplayer()` 用 `hasSingleplayerServer()` 判定**：与旧实现 `mc.hasSingleplayerServer()` 一致，但该方法在单人世界创建早期或局域网主机场景下的取值时机未做验证。

### 四、任务拆分

**任务 1：模块运行时**

- 目标：提供可复用的模块壳，任何业务模块只实现一个基类即可被模块中心识别与开关。
- 涉及目录：`core/module/`（新增）。
- 影响范围：仅新增；`module/` 注册表结构不改。
- 预计修改内容：新增模块基类（模块 ID、中文名、分类 ID、启用状态、`onEnable` / `onDisable` / `onTick` 生命周期、自检接口）与模块管理器（注册、按 ID 查找、启用 / 禁用、批量保存与载入、异常隔离）。基类只做壳，业务逻辑不得内联。

**任务 2：模块启用状态持久化**

- 目标：模块开关重启后保留，且与模块卡片状态一致。
- 涉及目录：`config/`（新增模块状态配置文件）。
- 影响范围：`core/module/` 管理器、`module/ModuleEntry` 的状态来源接线。
- 预计修改内容：启用状态按模块 ID 写入独立配置文件；沿用 `repository/JsonFileStore` 的原子写与失败回滚；状态缺失按默认值回填；配置损坏时回退默认且不崩。禁用时调用 `onDisable` 清理运行态。

**任务 3：注册分类与模块中心内容**

- 目标：模块中心出现真实分类与模块卡片，不再是 0。
- 涉及目录：`core/module/`（注册调用点）、`feature/`（业务模块）。
- 影响范围：`CategoryRegistry` / `ModuleRegistry` 的注册调用；注册表实现不改。
- 预计修改内容：按旧项目分类口径注册分类（工具 / 自动化 / 辅助 / 绕过 / 星露谷），权重与图标统一；注册本阶段接入的模块条目；注册顺序固定在客户端初始化早期，早于界面首次创建。

**任务 4：统一客户端事件入口**

- 目标：模块通过订阅接收事件，不再各自注册 Fabric 事件，消除注册顺序不确定。
- 涉及目录：`core/event/`（新增）。
- 影响范围：`YiyiAddonClient`、第 05 阶段自行注册事件的 `ResourceExtractionService`。
- 预计修改内容：定义事件类型（每 tick、进服、断线、打开界面、收包、发包）与固定派发顺序；模块在启用时订阅、禁用时退订；把 `ResourceExtractionService` 的三处 Fabric 事件注册迁入该入口；禁止在事件回调里做重活。

**任务 5：指令系统**

- 目标：提供中文指令注册与统一回显，支撑模块开关与功能触发。
- 涉及目录：`command/`（新增）。
- 影响范围：客户端初始化入口；不侵入界面层。
- 预计修改内容：Brigadier 注册入口、中文字面量与别名、补全、统一中文回显（沿用既有排版口径）；提供通用的「模块 开 / 关 / 状态」指令实现，业务模块只注册自己的子命令。

**任务 6：第一个真实模块 —— 身份识别与配置管理**

- 目标：交付一个可实际使用的模块，同时验证第 05 阶段的身份识别、方块语义解析、持久化三组能力。
- 涉及目录：`feature/identity/`（新增，按七类分 `model` / `service` / `ui` / `config`）。
- 影响范围：新增；`service/identity`、`repository/identity`、`platform/identity` 只被调用，不改结构。
- 预计修改内容：识别物品 / 实体 / 准星方块并展示完整身份信息；身份库的增删查改与目录打开；目标选择与失效项清理；模块页实现 `ModulePage`，未接入页面的模块仍走 `ModuleDetailPage` 占位；识别模式枚举 `IdentifyMode` 接入。

**任务 7：资源服务入口**

- 目标：让资源链路第一次被真实触发，跑通状态机与缓存，为后续探针实现铺路。
- 涉及目录：`feature/identity/ui` 或 `command/`。
- 影响范围：仅新增触发点，不改 `ResourceExtractionService` 内部逻辑。
- 预计修改内容：在模块页与指令中提供「检测当前服务器资源」入口；展示阶段 / 来源 / 缓存文件名 / 指纹 / 失败原因；探针本阶段允许空实现，允许收尾于「未发现目标资源」。

**任务 8：快捷键接入业务模块**

- 目标：业务模块开关可被快捷键绑定并生效，且与既有界面设置行绑定不冲突。
- 涉及目录：`ui/keybind/`（接入）、`feature/`（模块绑定 ID）。
- 影响范围：`ModuleKeybindManager` 的绑定对象由界面设置行扩展到模块；绑定机制本身不改。
- 预计修改内容：模块启用状态与快捷键回调对接；绑定 ID 命名统一为 `module.<模块ID>`；触发时机保持「界面关闭时且不处于录制态」。

**任务 9：自检与状态播报**

- 目标：模块启用时缺项一次性说清，不允许半运行状态。
- 涉及目录：`core/module/`、`feature/identity/`。
- 影响范围：新增；沿用既有 `ClientChat` 与中文播报口径。
- 预计修改内容：模块启动自检收集全部缺项（环境未就绪 / 身份库为空 / 资源未就绪等）；失败时自动关闭模块并说明原因；运行期状态变化按去重播报，不刷屏。
