## 1. 我理解错在哪（84 号的问题）

84 号里我把「玩家敲指令」当成一条**跳变线索**，处置沿用第 72 号的裁定（复位到 GO_WILD 重新前往野外挖矿）。
用户要的不是这个：他在家 / 出生点敲指令，是要**模块别挖**——重新前往野外也好、原地挖也好，
只要还在挖就是错的（家会被凿穿），正确动作是**暂停**。而且用户明确：不分指令内容，
只要是他敲的服务器指令，一律默认暂停。

## 2. 现在的口径（最终）

| 线索 | 处置 | 落点 |
| --- | --- | --- |
| **玩家敲的服务器指令**（`/home`、`/spawn`、`/tpa`… 任意指令，不含本模块自己发的） | **立刻暂停挖矿**（关模块）+ 播报原因 | `AutoMinerModule#onClientCommand` |
| 没有指令线索的位置跳变（插件传送、别人把你传走） | 维持原样：复位到 GO_WILD 重新前往野外挖矿 | `MiningStateMachine#manualTeleportDetected` |

**为什么不看指令内容**：用户口径是「检测到我输入什么什么指令……检测到了都默认暂停」——
「玩家敲了服务器指令」本身就等于「我要接手」，不去猜哪条指令会传送。

**为什么不加跳变确认**：`/spawn` 这类指令的落地跳变可能发生在任何状态（打怪、进食、卸货途中），
等到跳变再判就漏了；而暂停是安全动作，早一刻停没有代价。因此**一敲就停**。

**为什么不会自我触发**：模块自己发的 5 条传送指令（前往挖矿 / 卸货 / 补给 / 挂机修复 / 死亡返回）
在 `ServerCommandRunner#executeCommand` 里先记账（`markOwnCommand`），
`onClientCommand` 用 `isOwnCommand`（原文 + 5 刻窗口）跳过，不会自己把自己暂停。

**播报**（`error` 通道，不受「状态播报」开关静默）：

```
§c✗ 检测到手动指令 §8/home §8▸ 已暂停挖矿（避免在新位置继续挖）
```

**恢复**：重开模块即可（与既有「暂停」语义一致，用户口径里也说了这是默认暂停）。

## 7. 实机失败复盘（同日，用户「没用啊 你看我日志 我输入了还是在寻路」）

### 7.1 现象（`run/logs/latest.log` 原文）

```
[01:22:24] §e⚠ 检测到传送 §8▸ 重新前往野外挖矿     ← 跳变路径命中（旧口径，没改）
[01:22:33] (yiyiaddon/stardew) [星露谷] 界面观察：ChatScreen   ← 玩家打开聊天栏打字
[01:22:34] 正在傳送到 home。                        ← 服务器执行了玩家敲的 /home
[01:22:34] FAR AWAY FROM PATH FOR 1 TICKS. Current distance: 47807.26  ← Baritone 发现位置巨跳
[01:22:41] §f§l[自动挖矿]§r§l§c§l已关闭              ← 玩家手动关（此前模块一直开着）
```

关键：**整段没有任何「检测到手动指令」**，而模块从 01:22:24 到 01:22:41 一直处于启用态
（`01:22:59 已开启` 之前没有第二次开启），所以「暂停」确实一次都没发生。

### 7.2 根因（代码级，与本次改动无关的既有陷阱）

本模块的订阅所有者为 `EVENT_OWNER = "module." + MODULE_ID`（`AutoMinerModule :137`），
而 `ModuleEventBridge.attach(module)` 的第一件事就是 `ClientEventBus.unsubscribeAll(owner)`
（`ModuleEventBridge :31`），随后只按 `module.subscribedEvents()` 重订阅。
启用时序是 `applyEnabled(true)` → `attach` → `onEnable()`（`ModuleManager :274-276`）。

84 号把 `CLIENT_COMMAND` 写在了**构造函数**里，而构造函数只在 `AddonModules.bootstrap()`
注册模块时跑一次、早于任何一次 `attach` ⇒ **第一次启用就被 `unsubscribeAll` 清掉，且永远不会挂回来**。
结果：出包口的指令事件根本没进本模块，玩家敲什么都不会暂停。

（对比：`StardewFarmModule :459-465` 把订阅写在 `onEnable()` 里——`onEnable` 在 `attach` 之后执行，
所以那种写法不会被清；本模块必须在 `subscribedEvents()` 里声明。）

### 7.3 修复

| 文件 | 位置 | 改动 |
| --- | --- | --- |
| `AutoMinerModule.java` | `:744-756` | `subscribedEvents()` 增加 `CLIENT_COMMAND`（含陷阱说明注释） |
| 同上 | `:780-781` | `onEvent` 增加 `case CLIENT_COMMAND -> onClientCommand(event);` |
| 同上 | 构造函数 | 删除构造期 `ClientEventBus.subscribe(...)` 与随之无用的 `ClientEventBus` import |
| 同上 | `onClientCommand` javadoc | 补「必须声明式订阅、不能构造期订阅」的约束 |

行为口径不变（第 2 节），只是**真正接上了**。派发顺序也确认过：`AddonModules.bootstrap`
先 `EventDispatcher.init()`（:57）再 `ModuleManager.bootstrap(...)`（:59），
所以同一刻内先出包派发、后模块 tick——玩家敲指令的那一 tick 就会先暂停，
不会先被跳变判成「传送」而多发一条 RTP。

### 7.4 顺带查出的第二个缺陷（**未改**，待用户拍板）

`ownTeleportSettleTicks`（我方传送落地后的容错窗）会**吞掉**窗口内的一切跳变，
且每吞一次就把窗口重置一次（`MiningStateMachine :1408-1413`），进 MINING 时还会补满 100 刻
（`:702-703`）。本次日志正是如此：我方 RTP 于 01:22:29 落地 → 容错窗覆盖到 01:22:34 →
玩家 01:22:34 的 /home 巨跳被当成「我方落地修正」吃掉 → 模块在家里继续挖（用户报的正是这个）。

- 靠 7.3 的修复，**玩家敲指令**这条路已经安全（指令先暂停，跳变根本轮不到）；
- 但**菜单 / GUI 点击触发的传送**（不发指令包）仍可能落在容错窗里被吞掉，从而在家里继续挖。
  这条属于第 72 号报告裁定过的「无指令线索传送 → 重新前往野外」，未擅自改动。
- 待用户决定：是否把「无指令线索的巨跳」也改成暂停，或收窄/改成一次性消费容错窗。

## 10. 实机停机复盘：RTP 插件是「两段传送」，被误判成手动传送（同日）

### 10.1 用户反馈

<i>「[自动挖矿]✗ 检测到传送 ▸ 已暂停挖矿（避免在新位置继续挖）？我第一次挖矿不得传送吗
卸货不得传送吗？我没想到..」</i>

### 10.2 日志原文（第一轮即可复现，第二轮一模一样）

```
01:35:23  [自动挖矿] 已开启 → ✓ 前往野外        ← 我方发 /rtp，ownTeleportPendingTicks = 600
01:35:23  RTP » 請勿移動，否則傳送將取消！
01:35:27  [自动挖矿] ✓ 开始挖矿                   ← 第一段位置变化（>2 格）→ GO_WILD 判定成功 → 进 MINING
01:35:28  RTP » 你已被隨機傳送！                  ← 第二段：真正的大跳变
01:35:28  [自动挖矿] ✗ 检测到传送 ▸ 已暂停挖矿      ← 被当成手动传送
```

### 10.3 根因（两个因素叠加）

1. **RTP 插件分两段传送**：第一段（01:35:27）被 `ownTeleportPendingTicks` 正常认领，pending 随即清零；
   第二段（01:35:28，约 20 刻后）只剩 `ownTeleportSettleTicks` 能兜。
2. **9.3 第 1 条把兜底条件写死了**：`jumped` 要求跳变 > 32 格，
   而 9.3 又要求修正窗内跳变 ≤ 32 格才认领 —— 两条互斥，修正窗等于失效 ⇒ 第二段必然被判成手动传送。
   （9.3 第 2 条「不续期」让窗口更短，同样不利。）

### 10.4 修正（改回无条件认领，但保留 /home 那条修复）

```java
boolean ownLanding = jumped
    && (ownTeleportPendingTicks > 0
        || (!playerCommandWindow && ownTeleportSettleTicks > 0));
```

- 「正在等自己落地」（pending）→ **一律认领**，玩家指令窗口内也认领：
  这样「你敲了句 `/w` 正好撞上自家第二段落地」不会被白停一次。
  代价（已知边界，见 9.4）：你在自家传送等待中敲了**传送指令**，那一跳会被认领走，
  该次不会停机 —— 属于第 72 号以来「我方传送优先」的既有取舍。
- 「落地后修正窗」（settle）→ 玩家指令窗口内**不**认领（保住 7.4 的修复：你敲 /home 的那一跳绝不被吞），
  窗口外照旧认领（插件第二段传送、落地位置修正都发生在这里）。
- 修正窗恢复「吞一次即续期 100 刻」（原实现口径）。
