## 〇、最终结论：整段回退（用户 2026-09-19 实机两次反馈后裁定）

实机两次反馈：

1. 「会乱跳，挖不属于男中音标好的格子，挖一下跳一下，还挖头顶上的方块」→ 当时收紧为「候选必须是当前目标的紧邻」；
2. 「本来是向下挖的，老是挖头顶上两个格一直卡死」→ **该优化整段回退**。

**回退方式**：`MiningFastBreakController.java` 已恢复到改动前的原始状态，用
`git diff --stat -- …/MiningFastBreakController.java` 校验为**无差异**（byte-identical），
`.\gradlew.bat build --console=plain` → **BUILD SUCCESSFUL**。

**为什么值不回票价**（登记为「不要再试同类改动」的依据）：
服务端主破坏槽是单例，唯一能并行的是「延迟破坏槽」（把一块交给服务端后台按 1.0 阈值自己挖）。
第二块只能从 Baritone 的 `PathExecutor#toBreak()` 里取，而那是**整条剩余路径**的方块并集（可达几百格），
Baritone 挖矿时又不停重算路径 —— 无论怎么筛（离玩家最近的 / 只认同种方块 / 收紧到紧邻当前目标），
都无法保证「这一块一定是 Baritone 接下来真要挖的那一块」，一旦选错：
块被提前挖掉 → Baritone 缓存抖动、重新选目标 → 表现为乱跳、挖错格、向下挖时去挖头顶。

理论收益只有约 1.5 倍，代价是动摇秒破控制器（改过三轮才稳的那块），**结论：不做**。
下面的章节保留当时的取证与实现记录，供以后判断同类需求时参考。

## 一、取证：服务端到底允许几块「同时在破坏」

对照 `26.1.2/01-开发参考库/Minecraft原始源码/net/minecraft/server/level/ServerPlayerGameMode.java`：

| 位置 | 事实 |
| --- | --- |
| `:206-217` START 分支 | `isDestroyingBlock` / `destroyPos` 是**单例**：第二块 START 到达时走 `abort destroying since another started`，把**前一块的累计进度作废**（发回方块更新包） |
| `:218-238` STOP 分支 | `destroyProgress = getDestroyProgress * (ticksSpent + 1)`；`>= 0.7F` → 立即 `destroyAndAck`；**否则**若 `!hasDelayedDestroy` → `isDestroyingBlock = false`，把这批登记进**延迟槽**（`delayedDestroyPos` / `delayedTickStart`） |
| `:109-131` `tick()` | `if (hasDelayedDestroy) {…} else if (isDestroyingBlock) {…}` —— 延迟槽与主槽**每刻只推进一个** |
| `:116-119` 延迟槽完成 | `delta * (ticksSpent + 1) >= 1.0F` → **服务端自己** `destroyBlock(延迟槽坐标)`，不需要我方再发包 |

结论：
- **真正「两块同时累积进度」不可能**（主槽单例，第二个 START 顶掉第一个）；
- 但**延迟槽**是合法的第二条车道：STOP 发早一点（未达 0.7）就把那块交给服务端后台自挖，同时**主槽空出来**；
- 延迟槽也是单例 → **并行上限就是 2 块**（1 主槽 + 1 延迟槽），与用户裁定的「就 2 块」一致。

## 二、方案

**主槽**照旧服务 Baritone 当前瞄的那块（不改变任何既有行为）；**延迟槽**用来提前挖「Baritone 计划中的下一块」：

1. 第二块从 Baritone 自己的 `PathExecutor#toBreak()` 里取 —— 那是它当前路径上**本来就要挖**的方块集合
   （`PathExecutor#onTick:166-180` 对剩余 movements 求并集），因此**不存在「挖了不该挖的方块」的风险**；
2. 筛选条件：非当前目标、不在交接失败冷却 / 待确认集合 / 「挖不动」黑名单里、交互距离内、
   可破坏（非空气、`defaultDestroyTime >= 0`）；**两档候选**：
   - 第一档（优先）：与当前目标**同一种方块**（材质/硬度/所需工具一致，提前挖最保守）；
   - 第二档：当前工具能在 `LOOKAHEAD_MAX_TICKS = 40` 刻内按 1.0 阈值挖掉的**任意**路径方块
     —— 延迟槽只有 1 个，交接一块挖得极慢的方块等于把车道停摆，用速度上限卡掉它就够。
     实机截图暴露的必要性：隧道里是**深板岩 + 圆石混着**的（Litematica 投影显示 76x 深板岩圆石），
     只认同种方块会一块都挑不出来、车道空转。

   每档内取**离玩家最近**的一块（＝隧道推进方向上的下一块）；
3. 只交接 `delta < 0.7` 的块（`delta >= 0.7` 时这一发 STOP 会直接挖掉方块、不占延迟槽，属于主槽的活）；
4. **包序**：先 `START(候选)` → `STOP(候选)`（把候选塞进延迟槽、腾出主槽）→ 再 `START(当前目标)`。
   顺序反了当前目标会占着主槽，候选的 START 会把它的进度顶掉。

**为什么这是纯加速**：交接失败（延迟槽已被占 / 主槽被别人的 START 顶掉）只会让那块永远挖不掉，
由 `sweepDelayed` 的预测超时兜底 —— 丢记账 + 该坐标冷却 + 整体退避，之后交给主槽 / Baritone 正常处理。
主槽与原版路径完全不受影响。

## 四、预期收益

以 `r` = 主槽达标刻数、延迟槽需 `1.0/0.7 ≈ 1.43r` 计（客户端刻推演）：

- 串行（改动前）：1 块 / `r + 方块间隔`
- 并行（改动后）：约 **3 块 / 2r** → **约 1.5 倍**隧道推进速度

实测拿不准的变量（服务端是否吃下早 STOP、`toBreak()` 与 Baritone 当前瞄准的重合度）都会自动退化回串行，不会更慢。

## 六、收紧：第二块必须「紧挨当前目标」（同日实机反馈后修改）

实机反馈：「会乱跳，挖不属于男中音标好的格子，挖一下跳一下，还挖头顶上的方块」。

**根因**：候选范围放得太宽。`toBreak()` 是 Baritone **整条剩余路径**上打算要挖的全部方块（可达几百格），
而挖矿时 Baritone 会不停重算路径（`MineProcess` 用 `REVALIDATE_GOAL_AND_PATH`）——
从中挑「离玩家最近的」，很容易挑到一块「重算后就不在计划里」的远处方块。它被我们提前挖掉后，
Baritone 的世界缓存抖动（`PathExecutor#recalcBP`）并重新选目标，表现就是瞄来瞄去 + 挖掉不在标记里的格子。

**改法**：`pickLookaheadTarget` 增加硬条件 —— 候选必须是当前目标的**紧邻**（切比雪夫距离 1，含斜角，
`isAdjacentToCurrentTarget`）。这样提前挖的永远是**同一张开挖面**上的下一块（隧道两格高的头顶块、
或同一面墙上并排的块），Baritone 下一步本来就要挖它，不存在「跳」。同种方块优先、异种方块受
`LOOKAHEAD_MAX_TICKS = 40` 上限约束的取舍不变。

**如果收紧后仍乱跳，就整段回退这条并行车道**（收益约 1.5 倍，不值得拿「挖错方块 / 挖不烂」去赌）。
