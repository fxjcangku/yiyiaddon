## 1. 为什么要有这一套

第二十八章那套（`debug.log` 一次性埋点）在两类问题上天生不够用：

1. 现象是**多刻状态机 + 网络包时序**（本轮的「卸货 / RTP 后秒破·连锁·ESP 全失效」），
   需要「每个刻的状态快照 + 每次发包裁决的统计」，日志打点表达不了；
2. 需要**修复前 / 修复后两个会话横向对比**才能结案（次数从 1152 降到 2 这类判据）。

于是把它独立成「重武器档位」：运行时事件探针 → HTTP 采集 → JS 分析 → 一案一档。

## 3. 工具契约（与 Java 骨架一一对齐）

事件体：`{"run","tag","location","msg","data"}`，服务端补 `ts`（毫秒）与 `seq`（每会话自增），
逐行落 `日志-<会话名>.ndjson`；端口固定 `7777`。

| 路由 | 用途 |
| --- | --- |
| `POST /event` / `POST /events` | 单条 / 批量事件 |
| `POST /mark` | 复现开始 / 结束打标记（分析时单独列出，也是「复现窗口」的分界） |
| `POST /clear?run=&备份=0` | 清空会话（默认先备份成 `.bak-<时间戳>`） |
| `GET /logs?run=&tag=&location=&msg=&since=&limit=&tail=&raw=1` | 查事件（服务端按需重读文件，永远拿到最新） |
| `GET /runs` / `GET /export?run=` / `GET /health` | 会话清单 / 导出原始 ndjson / 存活计数 |

《分析.js》六种用法（全部实测）：

```powershell
node 04-埋点修复/工具/分析.js --列表
node 04-埋点修复/工具/分析.js --案例 <名>                      # 总览 + 心跳节奏 + 会话对比
node 04-埋点修复/工具/分析.js --案例 <名> --分组 data.pos --前N 10
node 04-埋点修复/工具/分析.js --案例 <名> --空档 ts --最小间隔 500
node 04-埋点修复/工具/分析.js --案例 <名> --位置 FastBreak.begin --时间线
node 04-埋点修复/工具/分析.js --案例 <名> --空档 ts --JSON
```

## 4. `开发习惯.md` 新增第三十三章（第 218~224 条）

| 条 | 内容要点 |

| 218 | **启用门槛三条**：用户报的 bug + 第二十八章走完仍定性不了 + 用户同意；每个探针必须对应案例档里的一条判据 |
| 219 | **目录约定**：一案一夹、`进行中`/`已修复` 两类、会话名分开落盘、案例档逐项填全 |

| 221 | **必须用现成两个 JS**，禁止每次另写一次性脚本；会话名固定 `修复前` / `修复后`；结论落到具体数值 |
| 222 | **结案三件**：删插桩（grep 0 命中 + build EXIT=0）→ 停采集服务（端口不监听）→ 归档并写复盘 |
| 223 | **埋点代码禁止进入任何发布产物**（jar / 混淆版 / `origin`） |
| 224 | **假设先写、数据后采**；事后补充的假设必须注明「采集后补充」 |
