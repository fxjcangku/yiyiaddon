## 2. 卸货时误报「挖矿任务已取消」的原因与修法

### 2.1 原因（取证，非推测）

进物流态（卸货 / 补给 / 修补）时 `onStateEnter` 会调 `module.getBaritone().stop()`；
Baritone 的 `stop` 命令自己会 `logDirect` 一条「已取消」，而本模块把 Baritone 的日志出口整个接管了
（`settings.logger.value = this::relayBaritoneMessage`），于是这条被我方**主动收摊的副产物**
被当成「挖矿任务被别人取消了」播给玩家。实机 chatlog 里这条消息紧跟每一处主动 stop 出现
（连锁接管、战斗收摊、物流传送到点，都是一样）。

### 2.2 修法：两道闸门（`MiningPathing#relayBaritoneMessage`）

1. **状态门**：只有状态机处于「采掘中 / 前往野外」时，才把「已取消 / 无法找到路径」转成挖矿播报。
   物流、补给、修补、进食、战斗这些状态一律不转（`isMiningIntentState()`，取不到状态机时按不播处理）。
2. **静默窗**：本模块自己 `stop()` 或重下发 `startMining()` 之后 40 刻（2 秒）内不转播
   （`enterRelayQuietWindow()`，两处调用点已加）。这类动作的「已取消」是自己制造的，没有信息量。

原有 3 秒同类节流保留。真实意义上的「挖矿目标不可达」（Baritone 找不到路且不是我方主动收摊）照旧播报。

## 3. 连锁挖掘：为什么不提示 / 为什么像没生效

### 3.1 取证结论（用户实机 chatlog，`run/logs/chatlog.json`）

不是不提示，是**只接管了矿脉的一小部分**，且没接管的块被静默丢掉了：

```
19:48:10  [自动挖矿] 连锁挖矿 ▸ 识别到 3 块可挖矿脉，已接管挖掘
19:48:41  [自动挖矿] 连锁挖矿 ▸ 识别到 3 块可挖矿脉，已接管挖掘
19:49:04  [自动挖矿] 连锁挖矿 ▸ 识别到 3 块可挖矿脉，已接管挖掘
19:49:34  [自动挖矿] 连锁挖矿 ▸ 识别到 4 块可挖矿脉，已接管挖掘
19:49:35  [自动挖矿] 连锁挖矿 ▸ 识别到 1 块可挖矿脉，已接管挖掘
```

连续几条都是 3 / 4 / 1 块，而且括号里从来没有「N 块够不到」的说明。代码对照后确认旧实现有两处静默丢弃：

- `origin.distSqr(neighbor) > rangeSqr` → **直接 `continue`，既不计数也不播报**（超出「连锁搜索距离」的块）；
- 派发阶段 `!isValidTarget(...) || controller.isBlocked(...)` → `queue.poll()` **丢掉了事，同样不计数**
  （玩家走远后够不到的块、被判挖不动的块）。

于是一条脉只看得到 3 块、也真的只挖 3 块，玩家自然读成「连锁没生效」。

### 3.2 改法（`MiningVeinMiner`）

| 改动 | 说明 |
| --- | --- |
| BFS 沿整条脉走到 `SCAN_RADIUS = 8` | 搜索距离（默认 4）只决定「挖哪些」，不再决定「看得见几块」；剩余部分照实统计，交给 Baritone 走过去挖 |
| 新增 `beyondRangeCount` / `queuedCount` / `skippedCount`，`veinSize` 改为「本脉共几块」 | 逐类计数，**不再静默丢块** |
| 播报补全 | `识别到 N 块可挖矿脉，已接管挖掘§7（本脉共 M 块：X 块够不到，Y 块超出搜索距离，交给 Baritone 走过去挖）` |
| 完成播报补漏挖交代 | 有丢块时补 `§7（另有 N 块挖不动或走远了够不到，已交回 Baritone 补挖）` |
| 新增 `wentOutOfReach(...)` | 把「走远了够不到的矿」与「已经被挖掉的矿」区分开，只统计前者 |
| 新增 `MIN_CHAIN_BLOCKS = 2` | 只扫出 1 块时不做连锁：不为一块停一次 Baritone；对应「不要刷屏」 |

按 26.1.2 服务端源码复核过：`ServerPlayerGameMode#handleBlockBreakAction` 对 START/STOP 只校验
交互距离与保护，**不校验朝向**，所以「交给 Baritone 走过去挖」与 Direction.UP 的既有做法都没有协议风险。

## 4. 新增：水中卡死「破坏脱困」一级（用户第 5 条）

### 4.1 位置

在既有水中阶梯的最前面插一级，形成三级阶梯（全部在 `tickMining` 的水中分支）：

```
水平停滞 10 秒（含「被水面顶住上下弹跳」）
  → ① 破坏卡住玩家的方块（本轮新增，WaterEscapeBreaker）
  → ② 寻路到最近陆地（旧 :501-522 抽成 startWaterEscapePathing()）
  → ③ 20 秒未脱困 / 反复 3 次 → RTP 换区
```

为什么需要①：被地形封在水里时，`findNearestLand()` 找到的那个「最近陆地」Baritone 根本走不到
（路径不可达），最后只能等到超时换区。先挖开头顶/四周，玩家自己就浮上去了。

### 4.2 实现要点（`fsm/WaterEscapeBreaker.java`，新文件）

- 候选顺序：**头顶 → 头侧四向 → 脚侧四向**（头顶优先，对应「上下跳动」的典型场景），
  只要「非空气、非流体、硬度 ≥ 0、在交互距离内」的方块，最多 9 个候选、一次最多挖 6 块。
- 破坏通道：直接调原版 `gameMode.startDestroyBlock / continueDestroyBlock`——
  秒破开着时这两个入口被 `MultiPlayerGameModeFastBreakMixin` 接管，因此享受秒破的速度与协议；
  秒破关着时走原版进度累积。**本类不拼任何包**（复用底座，不另造第二份）。
- 单块 5 秒挖不动换下一块；挖完 / 已浮出水面即收摊。
- 视角：破坏期间 `faceBlock` 对准作业面——此时 Baritone 已停，是唯一可见写入者，与「视角交回男中音」的口径不冲突。
- 与连锁避让：`AutoMinerModule#onTick` 传 `fsm.state() == MINING && !fsm.isWaterBreaking()`，
  两者共用同一个服务端破坏槽位，同时发包会互相顶槽。
- 顺带修掉一处旧缺口：脱困流程结束在「上岸」这一帧时，旧代码只清标志、不播报也不重起 mine
  （要等状态机的 mine 自愈分支最多 6 秒）。现在上岸分支统一收尾：播报「已脱离水域 ▸ 继续挖矿」+ 重起 mine。

## 5. 待实机验证项（第 59 / 193 条口径）

1. 挖掘时视角跟随方块（含上下）、平面走路不再抖（上一轮删视角跟随的效果复核）。
2. 卸货 / 补给 / 修补 / 战斗期间**不再出现**「挖矿任务已取消 ▸ 正在重新扫描目标矿」；
   挖矿途中 Baritone 真的找不到路时仍会有「挖矿目标不可达」提示。
3. 连锁：播报能说清「本脉共 M 块、接管 N 块、剩余为什么没接管」；单块矿脉不再连锁（无 1 块的连锁播报）。
4. 水中卡死：先出现「破坏周围方块脱困」，挖开头顶后能浮出水面并自动继续挖矿；开阔水域则直接走寻路脱困。
5. 苦力怕：引信点燃后撤、其他怪物贴脸杀（上一轮改动，一并复核）。
