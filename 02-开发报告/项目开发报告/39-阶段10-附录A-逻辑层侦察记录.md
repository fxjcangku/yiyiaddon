## 0. 开工前必须先说清的四处更正（与 37 号不一致，以源码为准）

### 0.1 「矿石识别三件套」是死代码，不是本轮要搬的识别层

`37-阶段10` 第 5 节「做」里写「矿石识别与单目标锁定（`VanillaMiningRecognizer` / `OreRecognizer` / `OreResult`）」。实测**这 3 个类没有任何调用方**：

- 全仓 grep `VanillaMiningRecognizer|DefaultMiningAdapter|MiningServerAdapter|OreRecognizer|OreResult`（`26.1.2\src`）共 29 行命中，**全部落在定义文件与它们互相 import 的那几行内**，无一处实例化或调用：
  - `mining/adapter/DefaultMiningAdapter.java:3-4`（import）、`MiningServerAdapter.java:3`（import）、`VanillaMiningRecognizer.java:12`（唯一实现类）。
  - 无 `new VanillaMiningRecognizer(`、无 `new DefaultMiningAdapter(`、无 `recognizeOre(` 调用点。
- `VanillaMiningRecognizer` 还是**写死矿种清单**的实现（钻石/绿宝石/残骸/金/铁/煤/铜/红石/青金石/石英，`VanillaMiningRecognizer.java:19-66`），**不读模块的「目标选择」**，与 `AutoMinerModule` 真正的目标判定毫无关系。

**结论（复刻口径）**：真正的「识别 + 单目标锁定」是模块自己的 4 个方法，不是那 3 个类：

### 3.2 `tick()` 主干（`:172-201`，逐字）

```java
public void tick() {
    if (mc.player == null || mc.level == null) return;

    // 死亡事件拦截（最高优先级）
    if (mc.player.isDeadOrDying() && !playerWasDead) {
        playerWasDead = true;
        transitionTo(MinerState.DEATH_HANDLING);
        return;
    }

    // 复活检测
    if (playerWasDead && !mc.player.isDeadOrDying()) {
        playerWasDead = false;
        transitionTo(MinerState.RESPAWN_WAIT);
    }

    stateTick++;

    switch (state) {
        case IDLE -> tickIdle();
        case GO_WILD -> tickGoWild();
        case MINING -> tickMining();
        case UNLOADING -> tickUnloading();
        case SUPPLY -> tickSupply();
        case EATING -> tickEating();
        case REPAIR -> tickRepair();
        case DEATH_HANDLING -> tickDeathHandling();
        case RESPAWN_WAIT -> tickRespawnWait();
    }
}
```

> 口径：`stateTick` **在分派前自增**，因此每个状态的首帧 `stateTick == 1`；`transitionTo` 内 `stateTick = 0`（`:211`）。

`transitionTo` / `onStateEnter` / `onStateExit`（`:203-261`）：

- `transitionTo`：同态直接 return（`:204`）→ `onStateExit(旧)` → 换态并 `stateTick = 0` → `broadcastStateTransition(旧,新)` → `onStateEnter(新)`。

## 13. 复刻要点与坑（逐条）

1. **两个「同一字段两个名字」**：`getUnloadThreshold()` / `getFullLoadStacks()`（`AutoMinerModule.java:1369-1370`）指向同一个 `unloadThreshold`；FSM 用后者。复刻时任选一个名字即可，但**不要建两个字段**。
2. **状态判据全部是「唯一一份」**：`isSeedMiningEnabled` / `isSilkTouchMode` / `isShulkerPackerEnabled` / `isInNether` 四处，页面、指令、FSM、自检都必须调它们（第 169 条）。
3. **`countOreStacks()` 返回「组数」不是「堆数」**（`总数 / 64`），阈值文案也写「X 组」（`AutoMinerModule.java:823-825`、`MinerFSM.java:1718-1719`）。
4. **`isAdjacentTo` 与 `openContainer` 的邻域判据必须同为切比雪夫 ≤ 1**（`MinerFSM.java:1012-1018`、`ContainerHelper.java:228`），否则「Baritone 认为到了、模块认为没到」→ 开箱死锁。
5. **容器必须等 stateId 连续稳定 2 tick** 才发槽位操作（`ContainerHelper.java:304-332`），抢跑会被服务端回滚。
6. **`quickMove` 只能走 `handleContainerInput(..., ContainerInput.QUICK_MOVE, ...)`**；旧框架的 `InvUtils.shiftClick` 在 26.1.2 **发包无效**（`ContainerHelper.java:291-294` 注释是实测坑）。
7. **丢弃的槽位映射** 快捷栏 `0-8 → 36-44`、主背包 `9-35 → 9-35`、副手 `45`（`ContainerHelper.java:193-195`、`:208`）——写错会出现「快捷栏垃圾永远丢不掉」。
8. **`retainKnownServerState` + 新 sequence** 是秒破不产生客户端空气墙的关键（`AutoMinerPacketProtocol.java:21-29`）；ABORT 不带 sequence（`:44-47`）。
9. **种子模式的破面锁定**：`start`/`continue` 必须同 `seedBreakFace`，否则服务端视为换面、进度重置（`MinerFSM.java:784-789`）。
10. **补给成功判据必须是数量达标**，不能用 `hasFoodToEat()`（`MinerFSM.java:1268-1271` 注释）。
11. **耐久阈值的夹紧**：`min(阈值, 最大耐久)`，否则满耐久工具会被判「需修复」形成死循环（`MinerFSM.java:1526-1529`）。
12. **修补后放回原槽**，不能固定放回 0 号槽（`MinerFSM.java:1798-1807` 记录了这个旧 bug）。
13. **KillAura 只关自己开的那个**：`killAuraWasOnBefore` 卫语句（`MinerFSM.java:1763-1779`）——用户原先开着的 KA 不许被模块关掉。
14. **`isCustomGoalActive()` 而非 `isPathing()`** 做物流寻路重发判据（`BaritoneExecutor.java:301-314` 注释）。
15. **`blockReachDistance = 4.5f` / `allowSprint = true` / `assumeExternalAutoTool = false`** 三处硬编码（`BaritoneExecutor.java:155`、`:164`、`:182`）。
