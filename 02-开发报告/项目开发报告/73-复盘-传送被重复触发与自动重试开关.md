## 1. 两个设置原本的语义（用户说不知道干嘛的）

| 设置 | 字段 | 默认 | 作用 |
| --- | --- | --- | --- |
| 传送等待时长 | `teleportDelay` | 8 秒 | 发出传送指令后等这么多秒；期间位置没变化即判定「传送未生效」 |
| RTP冷却时长 | `rtpCooldown` | 60 秒 | 判定「传送未生效」后，等这么久才**重发**一次指令（等服务器 RTP 冷却过去） |

用户把两者都设成 3 秒（他服务器 RTP 本身有 3 秒冷却）。

## 2. 根因：「传成功又被传一次」＝ 冷却期不看位置

`tickGoWild` 原逻辑：

```
阶段1 发指令 → 阶段3 每 tick 查位置变化(>2格=成功) → 阶段4 超时(仍原地)：进冷却 → 冷却结束重发
```

**冷却等待分支（原 765-771）只做倒计时，完全不检测位置**：

```java
if (teleportCooldownTicks > 0) {
    teleportCooldownTicks--;
    if (teleportCooldownTicks == 0) stateTick = 0;   // ← 直接准备重发
    return;
}
```

于是当**服务器 RTP 排队延迟 > 传送等待时长**时：第一次指令其实已经生效（人已被传走），
但超时判定先一步成立 → 进冷却 → 冷却期倒计时完 → **重发第二条指令** → 人被连传两次。
用户设 3 秒等待 + 服务器 3 秒冷却，正好卡在这个边界上，所以必现。

## 3. 修复

**修复 A（核心）**：冷却等待期也检测位置 —— 已生效就地转 `MINING`，不再重发。

```java
if (teleportCooldownTicks > 0) {
    teleportCooldownTicks--;
    if (Math.sqrt(mc.player.blockPosition().distSqr(teleportStartPos)) > 2) {
        teleportCooldownTicks = 0;
        teleportRetries = 0;
        teleportRetryNoticeShown = false;
        module.getSoundNotifier().notifyTeleportSuccess();
        module.info("§a✓ 传送已生效 §8▸ 开始挖矿");
        transitionTo(MinerState.MINING);
        return;
    }
    if (teleportCooldownTicks == 0) stateTick = 0;
    return;
}
```

**修复 B（按用户要求加开关）**：新增设置 `teleportRetryEnabled`（默认 `true`）与同名的控制台开关行。

- 关掉后：判定「传送未生效」也**不再重发指令**，只继续等传送生效（阶段 3 每 tick 都在查位置）；
  提示「⚠ 传送未生效 ▸ 自动重试已关闭，继续等待传送生效」**只播一次**（`teleportRetryNoticeShown`），不刷屏。
- 该开关是用户服务器场景的正解：他服务器的 RTP 延迟本来就不可控，让服务器自己完成传送即可。

**修复 C**：控制台两行说明改写，并在三行**下面各加一条 `Note` 中文注释**
（用户 2026-09-18：「没懂啊 能不能加下面加中文注释」；`Note` 是本项目控制台既有的行下注释构件，见
`ConsoleWidgets.Note`）：

| 行 | 行内说明（tooltip） | 行下注释（Note，白话） |
| --- | --- | --- |
| 传送等待时长 | 发出传送指令后等多少秒：这段时间内位置没变化就算「传送未生效」 | §8人还在原地没动，就认为这次传送没生效<br>§8服务器传得慢（比如 RTP 要排队几秒）就把这个数调大 |
| RTP冷却时长 | 判定「传送未生效」后等多久才重发指令：等服务器 RTP 冷却过去，避免冷却期空发 | §8判定「没生效」之后，等这么久才再发一次指令<br>§8为了躲开服务器自己的传送冷却；只在下面开关打开时才会用到 |
| **传送失败自动重试**（新） | 关掉后：超时不再重发传送指令，只继续等传送生效 | §8关掉后：超时也不再帮你发指令，就一直等你传过去<br>§8服务器有传送冷却 / RTP 排队时建议关掉，免得「传走了又被传一次」 |

**注意**：`ConsoleWidgets.Note` 是**单行、不自动换行**的构件（`MinecraftText.draw` 一行绘制，超出面板宽度直接被裁），
因此每条注释都拆成了两行短句（首版一长句在实机被裁到「又被传一…」，见用户截图）。

JSON 读写已同步（`toJson`/`fromJson` 均在 `rtpGuiEnabled` 旁），额外字段缺失时回落默认 `true`（不改变既有存档行为）。

## 4. 待实机验证项

1. 服务器 RTP 排队 3 秒左右时：不再出现「传成功又被传一次」；日志/播报最多一条「✓ 传送已生效 ▸ 开始挖矿」。
2. 打开「传送失败自动重试」：行为与旧版一致（超时 → 冷却 → 重试 ≤3 次）。
3. 关掉该开关：超时只播一次「自动重试已关闭，继续等待传送生效」，随后传送真正生效时正常进 `MINING`。
4. 控制台「传送」页三行的说明文案与开关显示正常。
