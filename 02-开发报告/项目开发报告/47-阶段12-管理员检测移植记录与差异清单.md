## 八、玩家头像（方案 A，已完成）

**背景**：第一版头像走 `ItemIconCache`（把 `PLAYER_HEAD` 物品渲染成图标），实机**完全不显示**。
查清原因后按用户 2026-09-16 裁定改走方案 A。

**`ItemIconCache` 为什么不行（设计层面不匹配，不是参数问题）**：

1. `ItemIconCache.keyOf(stack)` 的缓存键是「注册表物品 id + `ITEM_MODEL` 组件 + 图标边长」，
   **不含 `PROFILE` 组件**。所有玩家头颅的键完全相同（都是 `minecraft:player_head|32`）——
   即便采集成功，也只能得到「第一个被采集到的玩家」那张脸，其余玩家会共用它。
2. 实机表现是「什么都不画」。`draw()` 在命中缓存后必定贴图并返回 true，
   所以要么它一直返回 false（一直没采集成功），要么采集到的是一张全透明贴图。
   原因指向它的实现路径（「借位渲染 + 两版底色相减截取」）对 3D 特化物品不成立。

**方案 A 的实现**（`ui/render/PlayerFaceCache.java`，新增）：

| 环节 | 做法 |
|---|---|
| 取像 | `PlayerSkin#body().texturePath()` → `TextureManager` → `GlTexture`，用 `glGetTexImage` 把 0 级画面一次性回读到 CPU |
| 建图 | `Image.makeRasterFromBytes(RGBA_8888 / UNPREMUL / sRGB)`；行序即上传行序，第 0 行是图像顶行，**不需要翻转** |
| 绘制 | 只画两块 8×8：脸在 (8,8)、帽子层在 (40,8)，先脸后帽子层叠画；`SamplingMode.LINEAR` |
| 缓存 | 按皮肤贴图路径缓存，上限 256 张；回读失败的路径记入失败集合，**不逐帧重试** |
| 皮肤来源 | Tab 名单上的人走 `PlayerInfo#getSkin()`（服务器已下发，**不走网络**）；vanish / 已离线的人退回 `DefaultPlayerSkin`（按 UUID 派生）。**全程不需要 Mojang 会话服，断网也有头像** |

**实机验证（2026-09-16 17:25，`long.kkwmc.cn`）**：

- 选择器 8 名在线玩家**每人一张不同的头像**（黑发 / 橙发 / 棕发 / 灰发 / 绿白发 / 黑金 …），
  证明「每人一张」成立，不是共用同一张；
- 8 行头像与名字一一对应、方向正常（无上下颠倒）；
- 全程无新崩溃报告。

**首页账户条**（`ui/page/HomePage.java`，改既有文件）：后端数据卡顶部新增一条：

```
[头像 32×32]  玩家名（加粗）
              ID <完整会话 UUID>                      正版 / 离线
```

- 身份一律取**会话账户**（`ClientIdentity`），与后端统计口径一致（同 `ClientIdentity` 的既有约定：
  正版链路下服务器会重写实体 UUID，用实体 UUID 会对不上）；
- 头像取本地玩家实体上已解析好的 `PlayerSkin`（`client.player.getSkin()`），**不发任何网络请求**；
  不在世界时退回默认皮肤；
- 卡片总高随之增加：`DATA_H` 拆成 `ACCOUNT_H + DATA_H`，`getTotalHeight` / `statusCardY` /
  `drawDataCard` 三处同步改，绘制与命中共用同一组算式（该页既有约定）。

**实机验证**：首页账户条显示 `yiyijia` / `ID 1deb8ae7-6b2f-4bd3-96f4-1aa1f6a8f145` / `正版`（绿）+ 头像。

## 九、「检测隐藏玩家」过滤 NPC（已按用户裁定修复）

**实机发现的误报**：选择器的候选里出现了一个「隐藏玩家（不在 Tab 列表）」分组，组内是
**`右键我前往新手任务地点`** —— 那是服务器的新手向导 NPC（Citizens 一类的插件 NPC，
以玩家实体形态存在、名字带提示语、不在 Tab 列表里）。若不处理，模块一启用就会命中「隐藏」判据
→ 固定触发警报 + 断线，**模块直接不可用**。

**这不是本项目写错**：判据就是旧项目原文「实体在但 `getPlayerInfo(uuid) == null`」逐字搬运，
在带插件 NPC 的服务器上旧项目同样误报。用户 2026-09-16 裁定：**「能正常识别玩家过滤 npc 就行」**。

**修法**（`AdminDetectorModule#isHiddenFromTab`）：在「不在 Tab 列表」之上再加两条独立信号，
命中任一条才判隐藏：

| 信号 | 依据 | 覆盖的场景 |
|---|---|---|
| **本次会话里在 Tab 列表见过他** | vanish 的轨迹必然是「先可见、后消失」；插件 NPC 从建立那一刻就不在 Tab 列表，永远进不了这份记忆（`seenInTab`，只增不减） | 管理员先现身、再隐藏 |
| **他没有自定义名字** | 真实玩家的名牌来自档案名 / 计分板队伍，不占用自定义名字组件；插件 NPC 靠自定义名字显示「导游」「右键我前往新手任务地点」这类铭牌 | 模块中途开启、丢掉前半份记忆；管理员在你进服前就已隐身 |

**残留边界（诚实登记）**：服务器若给**真实玩家**设了自定义名字，且该玩家在你见到他之前就已隐身，
则判不出来 —— 这是客户端侧无法消除的固有盲区（客户端没有任何接口能直接问「你是不是 NPC」）。

**生命周期**：`seenInTab` 与 `nearbyThreats` 同生命周期（启用 / 关闭 / 断线三处都清空）。
**用户可见文案零改动**：命中的原因文字仍是旧原文的「隐藏」，变的是判定条件，不是播报。

**验证状态**：`compileJava` 通过；**「站在向导 NPC 附近启用模块、确认不断线且威胁数为 0」这条实机验证
尚未完成**（自动化输入的鼠标焦点被用户手动中断），登记在下一节。
