## 二、逐项记录

### 2.1 TAB 补出多余空格、补完即失效

**现象**：在聊天栏输入指令后按 TAB，补全结果末尾被追加一个空格；此后继续按 TAB 不再产生候选。

**取证**：解压 Brigadier 1.3.10 源码包，读 `SuggestionsBuilder`：

- `SuggestionsBuilder.suggest(text)` 只做两件事——记录候选文本本身、记录 `StringRange.between(start, 输入长度)`；**没有任何追加空格的代码路径**。
- `if (text.equals(remaining)) return this;`：候选与已输入内容完全相同则不产生候选。

结论：原版补全不会追加空格。多出来的空格来自新项目自己写的 `withTrailingSpace()`。

**根因**：新项目 `ClientCommandSuggestions` 自造了 `withTrailingSpace()` 并在三处调用，把候选文本尾部补空格。补全把光标定位在「参数起点 + 候选长度」，补出的空格让下一段参数起点算错，导致后续补全整体失效。

**修复**：删除 `withTrailingSpace()` 方法及其三处调用，候选文本原样输出。

**验证状态**：编译通过；实机待复测。

### 2.2 `.module 切换 <模块> ` 与 `.h <指令名> ` 之后 TAB 仍继续冒候选

**现象**：`.module 切换 <模块> ` 之后按 TAB，仍然继续列出模块名，可以无限往下补。

**取证（新旧对照）**：

- 旧项目这两个参数是 Brigadier 命令树上的两级节点，第二级是**叶子**：给出模块名（或分类）之后按 TAB 不再有任何候选。
- 新项目 `ModuleCommand.complete` 没有按参数位置收口，只要第一个参数是「切换」类动作就永远返回模块名列表。

**修复**：

- `command/ModuleCommand#complete` 增加位置收口：本指令最多两个参数，第二个已给出即返回空候选。
- `command/HelpCommand#complete` 同样收口：只补第一层指令名，给出指令名之后按 TAB 不再出候选（旧项目该参数同样是叶子）。

**验证状态**：编译通过；实机待复测。

### 2.3 「资源检测完成」卡片用了自造字段与另一套量纲

**现象**：新项目检测完成后的卡片多出旧项目没有的字段；星露谷档案计数与旧项目不是一套量纲。

**取证（关键词全项目检索）**：

- 「资源分类」在旧项目 `src` 中命中 **0 次**。
- 「资源档案已建立」在新项目 `src` 中命中 **0 次**（旧项目原文存在，新项目当时未复刻）。

结论：字段与卡片都是新项目自造，不是旧项目资产。

**修复（按旧项目口径回退）**：

- 删掉自造字段「资源分类」及其 `countsText()`，改回旧项目原文「资源状态 ▶ 星露谷资源」（`ServerResourceService` 播报块原文）。
- 就绪判定改回「扫到的星露谷逻辑对象数」，而不是另一套计数。
- 补上旧项目档案卡：`[星露谷农场] 资源档案已建立` ＋ 两行六格（作物 / 种植盆 / 肥料、药剂 / 水壶 / 洒水器）。
- 计数格的列宽按旧项目 `countCell()` / `countCellPx()` 同一口径：以 `洒水器 ▶ 888` 的像素宽为格宽，用全角空格 `　` 与半角空格补位，行首 `§r` 以跳过标签对齐。
- `ResourcePhase.NO_CONTENT` 文案对齐旧项目 `NOT_STARDEW` 口径：`非星露谷资源`。
- 播报去重键带上模块名，避免「服务器核心」与「星露谷农场」两条口径的同一阶段互相吞掉。

**验证状态**：编译通过；实机待复测（需在多人服务器上跑一次资源检测，核对五字段卡片与六格档案卡）。

### 2.4 旧项目 `.stardew 标记成熟 黄瓜` 标红且 TAB 改写输入

**现象**（用户截图）：输入 `.stardew 标记成熟 黄瓜`，整段标红、无任何回执；按一下 TAB 后变成 `.stardew 标记成熟 "辣椒"`。

**取证**：用真实 Brigadier 1.3.10 复刻旧项目命令树（`stardew → 标记成熟 → argument("作物ID", 参数类型)`，候选提供器照抄 `StardewFarmModule.cropCompletions` 的过滤逻辑），逐例打印候选与「应用第一条候选」的结果：

```
OLD_WORD（StringArgumentType.word()）
  [stardew 标记成熟 黄瓜]   解析失败(标红)  候选=["黄瓜"]      Tab → "黄瓜"
  [stardew 标记成熟 黄]     解析失败(标红)  候选=["黄瓜", 黄瓜] Tab → "黄瓜"
  [stardew 标记成熟 "黄瓜"] 解析失败(标红)  候选=[]            Tab 不动

NEW_WHOLE（整词参数）
  [stardew 标记成熟 黄瓜]   解析成功  候选=["黄瓜"]      Tab → "黄瓜"
  [stardew 标记成熟 黄]     解析成功  候选=["黄瓜", 黄瓜] Tab → "黄瓜"
  [stardew 标记成熟 黄瓜 ]  解析成功  候选=[]            Tab 不动
```

同时从 decompile 的 `CommandContextBuilder#findSuggestionContext` 与 `CommandDispatcher#getCompletionSuggestions` 读到：参数解析失败时该参数节点不会进入 `nodes`，补全上下文塌回到上一层字面量节点，`startPos` 落到参数起点，候选列表不再受已输入内容约束；TAB 套用的是**当前高亮**那条（高亮随鼠标移动），因此会把已输入的中文整词替换成列表里被高亮的别的作物。

**根因**：`StringArgumentType.word()` 只认 ASCII `[0-9A-Za-z_.+-]`，中文一个字符都读不进去，返回空串并把游标留在原地，随后抛「多余字符」语法异常。旧项目原本为此另设了一条 `StringArgumentType.string()`（带引号）的作物名参数，玩家必须打 `"黄瓜"` 才能解析，这正是带引号候选的来源。

**修复（旧项目）**：

- 新增自研整词参数 `WHOLE_WORD`：读到下一个空格（或行尾）为止，不做任何字符校验，中文原样收下，解析永不失败。`.stardew 种植` 与 `.stardew 标记成熟` 的作物参数统一改用该参数类型。
- `CROP_SUGGESTIONS` 只给**不带引号**的整词候选（cropKey ＋ 中文名），删掉重复的带引号候选 `"黄瓜"`。
- `StardewFarmModule.cropCompletions(String prefix, boolean quoted)` 去掉 `quoted` 形参与「带引号输入不补全」的旧守卫；`addCompletion` 原样给出整词。
- 同步删除已无用的 `ARG_CROP_NAME`、`CROP_KEY_SUGGESTIONS`、`CROP_NAME_SUGGESTIONS` 与 `argument(CommandContext, String...)` 辅助方法。
- 顶层的 `季节` 分支本来就因为同一原因用字面量节点而非参数节点，本次未改动，且与整词参数口径一致。

**连带发现**：mods 目录里玩家实际加载的那份 jar 是 2026-09-12 的构建，比当时的源码旧三天。

**验证状态**：旧项目 `compileJava` 通过、`assemblePersonal` 打包成功（产物 class 数 592、ASM 结构自检 0 失败）；jar 已覆盖到实际游玩实例的 mods 目录；**实机验证未做**（需重启客户端后实测 `.stardew 标记成熟 黄瓜` 与 `"黄瓜"` 两种写法）。
