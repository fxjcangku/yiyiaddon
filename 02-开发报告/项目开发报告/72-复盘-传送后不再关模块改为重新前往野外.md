# 72 - 复盘：传送后模块自关导致「秒破与连锁失效」→ 改为自动重新去野外挖

- 日期：2026-09-17
- 触发：用户「然后我传送之后 配置秒破跟连锁都失效了 重启模块才恢复」
- 涉及文件：`feature/mining/fsm/MiningStateMachine.java`
- 验证：`./gradlew build --console=plain` → **BUILD SUCCESSFUL（EXIT=0）**；**实机待确认**

---

## 1. 取证（chatlog 铁证）

```
19:48:21  §c✗ 检测到手动传送 §8▸ 已停止挖矿（避免在新位置继续挖）
19:48:25  自动挖矿 · 启动报告 … 已开启        ← 用户 4 秒后手动重开
```

即：**不是秒破/连锁失效，而是整个模块被它自己关掉了** —— 模块一关，秒破与连锁自然全停，
用户重开模块（「重启模块」）就恢复，与他的描述逐字吻合。

## 2. 根因

`manualTeleportDetected()`（`MINING` 态下单刻位置跳变 > 32 格即判定「玩家自己传送了」）的收尾是：

```java
module.error("§c✗ 检测到手动传送 §8▸ 已停止挖矿（避免在新位置继续挖）");
if (module.isEnabled()) ModuleManager.setEnabled(AutoMinerModule.MODULE_ID, false);   // ← 关模块
```

该设计的初衷（用户 2026-09-17 提的「挖矿中敲 /home 回家，模块还在继续挖」）是对的：不能在家/主城继续挖。
但代价是**任何传送都会把模块关掉**，玩家必须手动重开。

## 3. 用户裁定与改动

用户 2026-09-18 裁定：**自动重新去野外挖**。收尾改为：

```java
module.getSoundNotifier().notifyStuck();
module.getBaritone().stop();
module.info("§e⚠ 检测到传送 §8▸ 重新前往野外挖矿");
transitionTo(MinerState.GO_WILD);   // 重走一遍传送流程，在新矿区继续挖
return true;
```

- 行为：传送后**不停模块**，状态机复位到 `GO_WILD` → 重新执行「前往挖矿指令」（RTP）→ 落地进 `MINING`
  → 秒破与连锁照常工作。原来的诉求（不乱挖主城/家里的方块）仍然成立，因为落点仍是野外矿区。
- 不会形成循环：`jumped` 判定要求 `state == MINING`，而 GO_WILD 的落地跳变发生在 GO_WILD 态，
  且我方传送有 `ownTeleportPendingTicks` / `ownTeleportSettleTicks` 宽限窗消费；
  进 MINING 后 `lastWatchPos` 每刻更新，不会把「上一个矿区的位置」当参照。

## 4. 顺带澄清：其余「模块自动关闭」都有理由播报

全文件共 20 处 `ModuleManager.setEnabled(AutoMinerModule.MODULE_ID, false)`，逐条核对下来
**每一处前面都有一条 `module.error(...)` 说明原因**（传送失败、缺少镐子、工具无经验修补、
目标解析不出方块、卸货/补给指令无效或寻路超时、容器满、无容器等）。
用户实机 21:03:44 / 21:04:56 那两次「已关闭」都**没有**任何理由播报，属玩家自己关的开关。

## 5. 待实机验证项

1. 挖矿中途手动传送（`/home`、`/spawn`、`/tpa` 等）：出现「⚠ 检测到传送 ▸ 重新前往野外挖矿」而不是
   「✗ 检测到手动传送 ▸ 已停止挖矿」，模块**保持开启**，随后自动 RTP 到新矿区继续挖。
2. 模块自带传送流程（卸货 / 补给 / 前往野外 / 挂机修复）不被误判为手动传送（原有宽限窗行为不变）。
3. 不开模块时手动传送不受影响。
