公平性设计（保证「只换输入状态」这一个变量）：每个测试区块都跑中心 3x3 共 9 遍装饰
（对齐 `ChunkPyramid` 给 `FEATURES` 的 `blockStateWriteRadius(1)`，`ChunkPyramid.java:29-35`），
**每一遍安装的是「那一遍所属区块自己的」快照**——因为原版那九遍本来就发生在不同时刻、读到的邻域状态不同；
每遍结束只统计「本遍新写进被测区块的矿位」，最后取并集。

### 3.3 本轮定位并修掉的一处读取语义偏差（如实登记）

`WorldGenRegion#getHeight(type,x,z)` 返回 `chunk.getHeight(...) + 1`（`WorldGenRegion.java:397-399`），
而 `ChunkAccess#getHeight` 是 `getFirstAvailable - 1`（`ChunkAccess.java:190-202`）。
影子层直接走 `ServerLevel` 会**少 1**，使 `OreFeature.place` 的高度判据
`yStart <= level.getHeight(OCEAN_FLOOR_WG, xprobe, zprobe)`（`OreFeature.java:46`）系统性变严。
已按 `WorldGenRegion` 语义在影子层补回这 1。**实测结论：补回后全部数字一格未变**（第七节已排除项 A），
即这条偏差不是本残差的成因，但作为「影子层必须逐条对齐原版读取语义」的教训保留在代码注释里。

## 五、装置自证对照（本轮新增的硬判据）

快照口径如果给出「与旧口径完全一样」的数字，存在两种完全相反的解释：

1. 输入状态真的对钻石放置没有影响；
2. 状态根本没被送进放置链路（装置缺陷）。

光看快照口径的数字**分不出这两者**，所以本轮补了两个期望值可判定的对照：做法与快照口径完全一致
（同样安装「装饰开始前」快照 → 建影子层 → 重放矿步骤），**唯一多出来的动作**是在安装之后
把中心区块整片改写成一种统一方块。两个对照都走同一条高度图判据（`OreFeature.java:46`），
因此二者差异只能来自方块状态本身。

| 对照 | 改写的方块 | 期望 | 实测（10 区块合计） | 逐区块实测 |
| --- | --- | --- | --- | --- |
| 对照1 | 紫水晶块（不可替换、非空气） | 预测必须为 **0** | **预测 0**（漏报 243 / 错报 0） | 10/10 区块全为 0（45、9、29、21、22、27、21、18、18、33 真值 → 预测全 0） |
| 对照2 | 石头（可替换） | 预测必须显著多于真值 | **预测 290 > 249（旧口径）/ > 243（真值）** | 45、18、25、29、21、29、34、34、33、22 |

**判定：装置有效。** 把输入改成不可替换方块 → 一个钻石都放不出来（0）；改成可替换方块 → 预测从 249 涨到 290。
这直接证明**放置链路确实以被安装的世界方块状态为依据**，因此第四条里「换了输入却零变化」不是装置缺陷，
而是**真实的现象**。

## 六、缺失输入量化（把「第一轮为什么只有 59%」变成可复核的差值）

数据口径：每个区块以自己为中心取 3x3 区块、y ∈ [-64,79]（9 个 section）；十区块合计 3,317,760 格。

### 6.1 A · 生成期方块状态 vs 最终世界

比较 3,317,760 格，**不同 325,476 格（9.81%）**，其中：

| 子项 | 合计 |
| --- | --- |
| 最终是钻石、生成期不是 | 1,319 格 |
| 最终是其它矿、生成期不是 | 19,003 格 |
| 生成期可替换、最终不可替换（**会改变 `nextFloat` 消耗次数**） | 68,161 格 |
| 最终是空气、生成期有方块 | 2,543 格 |
| 生成期是空气、最终有方块 | 32,642 格 |

### 6.2 B · 生成期 `OCEAN_FLOOR_WG` vs 由最终状态补出的同一高度图

共 23,040 列，**不一致 11,968 列（51.94%）**；生成期更高 0 列 / **最终更高 11,968 列**；
最大偏差 17 格，平均偏差约 5 格。方向性是干净的：最终世界的高度总是更高（后续 feature 往上加方块）。

### 6.3 附加取证 · 「装饰开始前」→「第一条钻石 feature 前」

3,317,760 格中**不同 41,065 格（1.24%）**，其中**变成矿石的 1,823 格**——
这就是「结构 / 前置 feature 对矿石放置的影响上限」。

**这三组数字与本轮的对照结果放在一起看，就是本轮最重要的发现**：
缺失输入 A/B/附加三项都真实存在且量级不小（9.81% / 51.94% / 1.24%），
但把它们统统换成真值之后，逐 BlockPos 结果**一格未变**。因此它们**都不是**这 40.7% 残差的成因。

## 八、根因假设判定（明确）

### 8.1 判定

**根因假设【未被证实】——并且本轮取得的是反证。**

判定依据（全部为实机数字）：

1. 用真实「装饰开始前」快照替换输入（口径1、口径2）后，10/10 区块的
   `预测/匹配/漏报/错报` 四个数字与旧口径**逐位相同**，合计仍为 249/144/99/105（查全 59.26% / 查准 57.83%）。
2. 用真实「第一条钻石 feature 前」快照替换输入（口径3，即把世界恢复到钻石 feature 执行前那一刻、
   只重放钻石四条），结果**同样逐位相同**。
3. 本轮新排除的两项（高度 +1 语义、单点扰动）也都不改变结果。
4. 装置自证对照证明状态**确实**进入了放置链路（对照1 → 0；对照2 → 290），
   因此第 1～3 条不能解释成「装置缺陷」。

⇒ 「缺失生成期状态（方块状态 + 高度图 + 结构/前置 feature 影响）」**不是**这 40.7% 残差的成因，
第一轮把残差归因到这一层是**不成立**的。

### 8.2 本轮仍无法区分的微观解释（如实登记，不写成结论）

在「读取面」这一层，尚不能区分下面两种微观情况：

- **(i)** 四份输入在钻石 feature 实际读取的格子上恰好等价。支持它的机制是：
  被测区块自己的「装饰开始前」快照与「最终世界清空矿石后」这两份输入，在**深层可替换类**上几乎同构
  ——原版同一步骤的前置 feature（`ore_dirt`/`ore_gravel`/`ore_granite`… 这些 `discardChanceOnAirExposure = 0`
  的 feature）由我们的重放以**同一随机数流**补回，占位与被清空的矿位同属 `stone_ore_replaceables` /
  `deepslate_ore_replaceables`，因此 `OreFeature#canPlaceOre` 的标签判定与 `nextFloat()` 消耗次数一致。
- **(ii)** 存在某个尚未识别的细节，使状态差异落在钻石 feature 的读取面之外。

两者都不影响第 8.1 条的判定，但决定下一步该往哪查，因此必须在报告里写明而不是二选一。

## 九、下一步定位清单（不改业务、不开新工程）

残差与输入状态无关，下一步必须转向 **state-independent** 方向。按证据优先级：

1. **把「本区块自己的贡献」与「邻区块贡献」分离开**（最高优先）。
   现在 `逐遍新增` 显示：绝大多数区块只有中心遍有产出（`[0,0,0,0,X,0,0,0,0]`），邻遍贡献只有零星 2～3 个；
   而原版邻区块装饰是可以写进被测区块的（`blockStateWriteRadius = 1`，
   `ChunkPyramid.java:29-35`；写权限判据 `WorldGenRegion.java:230-244`）。
   需要新增一个「钻石 feature 执行**之后**」的探针（同一区块装饰过程中，第一条非钻石 feature 之前），
   用「同一次装饰内、钻石四条前后状态差」作为**只含本区块自己贡献的 oracle**，
   再单独判定重放的保真度——这能把「重放本身不准」与「邻遍贡献缺失」彻底分开。
2. **核对邻域快照的「混龄」语义对跨区块写入的影响**。
   第四节注1 已实测到「中心区块在装饰开始前就已含有邻区块写入的 3～4 个钻石」，
   这批钻石被计入 `before` 而不计入预测，属于已知统计边界；它对总量的影响需要量化。
3. **核对写权限判据的边界情形**（`upgrading` 分支与越界高度判据，`WorldGenRegion.java:236-244`）
   与我们的复刻实现是否逐条一致。
4. **归因前先扣除「非 `underground_ores` 来源的钻石」**：化石（`underground_structures` 步骤的
   `fossil_diamonds`）等；口径0-多步骤已实测未带来额外钻石，需要在 oracle 建立后重查。
5. 第一轮登记的「结构放置未参与复刻」在本批区块上命中为 0，暂不作为下一步重点。

**禁止**：在上述定位完成前，不得开始「客户端仅凭 Seed 离线构造该阶段状态」
（`WorldGenRegion` / `ChunkStep` / `GenerationChunkHolder` / `StaticCache2D` + AccessWidener/Mixin）的工程化开发。

## 十、结论边界（必须与数字一致）

1. 本实验证明的是**装饰阶段**：装饰种子派生 → feature 全局索引 → 逐个 `setFeatureSeed` →
   `PlacedFeature` / `OreFeature` 放置，在**给定输入状态**下是否与真实世界逐 BlockPos 相同。
2. 快照口径的输入来自真实区块生成过程中的探针，因此它证明的是「**算法在正确输入下能否复现**」，
   不代表「客户端已经能离线构造该输入」——后者仍未做，也不在本轮范围。
3. 快照纵向只覆盖 y ∈ [-64,79] 的 9 个 section；该范围之外（例如 y > 79）的方块不参与本轮输入重建，
   与本轮钻石判定无关（钻石四条的上界为 y = 16）。
4. 每遍装饰只安装「那一遍所属区块自己的」快照，这是对原版九遍装饰在不同时刻读到不同邻域状态的近似；
   邻区块贡献因此只能近似复刻。
5. 「装饰开始前」快照的邻域是**混龄**的（部分邻区块此前已被装饰），这是真实情况而非缺陷；
   由此带来的统计口径边界（安装后已有钻石计入 `before` 而不计入预测）已在第四节注1 标注。
6. 装置自证对照（对照1/对照2）是**破坏性**输入改写，只用于判定装置有效性，不参与任何精度结论。
7. 残差 40.7%（查全 59.26%）**在本轮之后仍然存在**，且已被证明与生成期状态输入无关。
8. 探针与两个 Mixin 属于开发期插桩（对齐《开发习惯》第三十三章 DebugProbe 口径：一案一份、
   结案整包删除、绝不进发布产物）。本轮**尚未结案**，因此暂不删除；结案时必须删除干净。
