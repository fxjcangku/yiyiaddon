## 三、源码研究结论（26.1.2 本线，逐行取证）

### 3.1 装饰管线（`ChunkGenerator#applyBiomeDecoration:318-412`）

```
origin        = SectionPos.of(chunkPos, level.getMinSectionY()).origin()        // (:319-322)
random        = WorldgenRandom(XoroshiroRandomSource(generateUniqueSeed()))     // (:327)
decorationSeed= random.setDecorationSeed(level.getSeed(), origin.x, origin.z)   // (:328)
possibleBiomes= 中心 3x3 区块所有 section 的生物群系 ∩ biomeSource.possibleBiomes() // (:329-337)
for stepIndex in 0..max(11, featureStepCount):                                  // (:344)
    if structureManager.shouldGenerateStructures():                             // (:346-363)
        for structure in structuresByStep[stepIndex]:
            random.setFeatureSeed(decorationSeed, index++, stepIndex)
            structureManager.startsForStructure(...).forEach(placeInChunk)
    if stepIndex < featureStepCount:                                            // (:365-399)
        possibleFeaturesThisStep = { 各生物群系该步骤 feature 的全局索引 } → 升序   // (:366-382)
        for globalIndexOfFeature in sorted:
            random.setFeatureSeed(decorationSeed, globalIndexOfFeature, stepIndex)  // (:388)
            feature.placeWithBiomeCheck(level, this, random, origin)                // (:392)
```

三个必须点明的语义：

1. **每个 feature 的随机数流互相独立**：`setFeatureSeed` 每次重置种子
   （`seed + index + 10000 * step`），所以某个 feature 的漂移不会通过随机数流传染给别的 feature；
   传染只通过**方块状态**发生。
2. **`placeWithBiomeCheck` 不消耗随机数做生物群系抽取**
   （`PlacedFeature:38-40`：只是把 `Optional.of(this)` 塞进 `PlacementContext`），
   生物群系只由 `BiomeFilter` 在候选点上判定 —— 而生物群系层本实验已复现到 100.0000%。
3. **结构放置与 feature 放置在同一个步骤里、同一个循环内**，结构先写、feature 后写。

### 3.2 `OreFeature`（`OreFeature.java:24-189`）—— 本 PoC 的决定性机理

```java
// place(:24-50)
float dir = random.nextFloat() * PI;
x0/x1/z0/z1 = origin ± sin/cos(dir) * (size/8.0)
y0 = origin.getY() + random.nextInt(3) - 2;
y1 = origin.getY() + random.nextInt(3) - 2;
yStart = origin.getY() - 2 - maxRadius;  sizeXZ = 2 * (ceil(spreadXY) + maxRadius);
for xprobe ... for zprobe ...
    if (yStart <= level.getHeight(Heightmap.Types.OCEAN_FLOOR_WG, xprobe, zprobe))   // (:46)
        return doPlace(...);
return false;                                                                        // 不放置

// doPlace(:110-162)
for i in 0..size-1: size 次 nextDouble() + 椭球剔除（纯随机数）
try (BulkSectionAccess sectionGetter = new BulkSectionAccess(level)) {
  for 每个椭球: for 椭球内每格:
     if (!level.isOutsideBuildHeight(y) && !tested.get(idx)) {     // (:132-135)
        tested.set(idx);
        if (level.ensureCanWrite(orePos)) {                        // (:137) ← 影响随机数消耗！
           blockState = section.getBlockState(...);                // (:143)
           for (TargetBlockState t : config.targetStates)
              if (canPlaceOre(blockState, sectionGetter::getBlockState, random, config, t, orePos)) {
                 section.setBlockState(...); placed++; break; }    // (:146-150)
        }
     }
}

// canPlaceOre(:168-181)
if (!targetState.target.test(orePosState, random)) return false;   // TagMatchTest：不消耗随机数
return shouldSkipAirCheck(random, config.discardChanceOnAirExposure)
        ? true : !isAdjacentToAir(blockGetter, orePos);
// shouldSkipAirCheck(:183-189)
if (discard <= 0) return true;        // 不消耗
if (discard >= 1) return false;       // 不消耗
return random.nextFloat() >= discard; // ← 消耗一次 nextFloat()
```

由此得到**四条硬结论**（它们是理解全部实验结果的钥匙）：

1. **候选点的方块状态会改变随机数消耗次数。** `discard_chance_on_air_exposure ∈ (0,1)` 时，
   只有目标方块通过可替换标签判定，才会消耗一次 `nextFloat()`；一旦某个候选点的状态与生成期差一格，
   该 feature 在该装饰遍**此后所有矿脉**的位置都会整体漂移。
2. **`ensureCanWrite` 决定是否进入 `canPlaceOre`**（`:137`），因此它同样影响随机数消耗次数；
   原版判据 = 目标格所在区块与「本次被装饰区块」的切比雪夫距离 ≤ `ChunkStep#blockStateWriteRadius`
   （`ChunkPyramid`：`FEATURES` = 1，即 3×3），本 PoC 已逐项复刻。
3. **`OreFeature.place` 依赖 `getHeight(OCEAN_FLOOR_WG)`**（`:46`）：矿脉是否放置取决于「矿脉底部
   yStart 是否 ≤ 该列高度图高度」。高度图是**状态派生量**，且在不同生成阶段取值不同。
4. **矿物写入走 `LevelChunkSection#setBlockState`，不经过 `Level#setBlock`**（`:147`），
   所以「矿石被写到了哪里」无法从 `WorldGenLevel` 层观测，只能事后读世界。

| --- | --- | --- | --- |
| `ore_diamond` | 4 | 0.5 | `diamond_ore`、`deepslate_diamond_ore`（均 TagMatchTest） |
| `ore_diamond_medium` | 8 | 0.5 | 同上 |
| `ore_diamond_large` | 12 | 0.7 | 同上 |

### 3.3 装饰期真正的输入状态是什么（本 PoC 最重要的研究结论）

`ChunkGenerator` 的步骤依赖（`ChunkPyramid`）：`FEATURES` 依赖 `CARVERS, 1`。
也就是说，**当区块 C 执行装饰时，它的 3×3 邻域只保证处于 `CARVERS` 状态** ——
邻域里的结构、地物、后续装饰**都还没写**；C 自己此刻也只有「噪声 + 地表 + 雕刻器」的结果。

因此，要逐 BlockPos 复现装饰结果，必须拿到 **「post-CARVERS / pre-FEATURES 的区块方块状态」**，
而不是「全部生成完成的世界」的状态。本 PoC 只有后者，这是全部偏差的入口。

## 七、失败案例与根因定位

### 7.1 已定位（有实测证据）

**根因层：装饰开始前的「生成期区块方块状态」不可得，且它对结果有决定性影响。**

证据链：

1. 机理侧（源码）：`OreFeature.canPlaceOre:176-179` + `shouldSkipAirCheck:183-189` —— 候选点状态
   决定是否消耗 `nextFloat()`；`ensureCanWrite:137` 同样决定是否进入判定。
2. 实验侧（扰动）：只改候选点状态、其余输入不动 ⇒ 10/10 区块随机数流被打断、预测集合整体变化
   （6.5 节）。
3. 结构侧（污染扫描）：判定时刻确实存在「矿物步骤之后才写上去」的方块（最多 354 个候选点），
   这些点与真实生成期状态**必然不一致**（6.6 节）。
4. 一致性侧（三口径）：改变「重放哪些 feature」不改变任何结果 ⇒ 差异不在 feature 集合，
   而在放置当时的输入状态（6.3 节）。
5. 环境侧（对照）：关掉 C2ME 结果不变 ⇒ 不是模组化 worldgen（6.8 节）。

**缺失的确定性输入（明确命名）**：

- **A. 装饰开始前的区块方块状态（post-CARVERS / pre-FEATURES）**：中心区块与 3×3 邻域此刻
  都只有「噪声 + 地表 + 雕刻器」的结果，结构、地物、后续装饰尚未写入。本 PoC 只有「全部生成完成
  的世界」这一份状态，把它当装饰期状态用，必然在候选点状态上产生系统性差异。
- **B. 生成期高度图（`OCEAN_FLOOR_WG` 在装饰时刻的取值）**：`OreFeature.place:46` 用它决定
  「矿脉是否放置」，而**是否放置会决定 `doPlace` 是否消耗随机数**（跳过 `doPlace` 即少消耗一整段
  随机数），所以它同样会让整条流整体漂移。本 PoC 读到的高度图来自**已完全生成**的区块
  （含后续装饰抬高的部分），与装饰时刻的取值不保证相同。
  实测旁证（同一区块、同一遍口径）：`ore_dirt` 累计候选 4191 次却产生 8828 次 `getHeight` 调用
  （约 2.1 次/候选）；钻石四条同样多次探测（如 `(3,-1)` 的 `ore_diamond` 累计候选 105 次 /
  `getHeight` 28 次 ≈ 3 次/次放置）。**探测次数本身不消耗随机数，但「探测循环最终通过与否」会**，
  因此这是与 A 并列的一条缺失输入，必须单独验证，不能默认它对钻石无影响。
  （本 PoC 未做「把高度图替换成生成期取值」的对照实验，故此处只登记为待验证项。）
- **C. 结构放置的确定性复现**：结构在 `applyBiomeDecoration:346-363` 里先于 feature 写入本区块，
  既改变了候选点状态，也会直接放置矿石（化石 `fossil_diamonds`）。本 PoC 不放置结构，
  只在事后读它的结果。

### 7.2 已排除

| 候选原因 | 排除依据 |
| --- | --- |
| 生物群系不可复现 | 100.0000%（138240/138240，90 区块） |
| feature 全局索引 / 步骤数不一致 | 索引表交叉核对：步骤 11、feature 164、钻石索引 44 项全同 |
| 装饰种子派生或 `setFeatureSeed` 写法错 | 与 `ChunkGenerator:327-328,388` 逐行同源；若错，重合率应≈0，实测 20%~95% |
| 写半径判据不一致 | 复刻 `ensureCanWrite`（切比雪夫 ≤ 1 + 越界高度）；三口径结果逐位一致 |
| 「只重放钻石」漏掉其它放置路径 | 加了 `underground_structures` 口径，结果逐位不变 |
| 模组化 worldgen（C2ME） | 关闭 C2ME 后统计结果完全一致（6.8 节） |
| 服务端对象缺失导致方向不可行 | **不成立**：影子 `WorldGenLevel` 已跑通，只需 13 个方法（6.1 节） |
| 引擎自身不确定 | 同输入两遍结果一致（10/10 区块） |

### 7.3 尚未隔离（如实登记，禁止当成已知结论使用）

`(3,-1)` 区块的污染扫描只发现 7 个 `glow_lichen`（对随机数流无害），查全却只有 38.89%。
这说明还存在**本 PoC 未能显式观测**的状态差异。按证据强度排序的两个候选：

1. **3×3 邻域的状态语义错**（本报告倾向的解释）：原版装饰中心区块时邻域只到 `CARVERS`，
   而我们重放的 9 遍装饰全部作用在「已完全装饰」的区域上；邻域里多出来的装饰物/结构/后续方块
   会改变候选点状态。污染白名单不可能覆盖全部这类差异（例如紫水晶洞内部的空气、
   水/岩浆、滴水石等都不在白名单里）。
2. **空气的可替换性歧义**：雕刻器挖出的空气（生成期就是空气）与紫水晶洞/结构内部挖出的空气
   （生成期是可替换石头）在最终世界里**长得一模一样**，本装置无法区分；
   前者无害、后者会造成一次多余的 `nextFloat()` 消耗。

两者都需要「拿到 post-CARVERS 状态」才能真正判定 —— 这与 7.1 的结论一致。

### 7.4 失败案例（可直接复查的样本）

- `(0,0)` 漏报 `(14,-51,11)`、`(15,-50,12)`：六邻全为 `deepslate`，孤立 2 格。
- `(0,1)` 漏报 `(8,-58,17)`、`(8,-58,18)`、`(9,-58,17)`、`(9,-58,18)`、`(9,-57,17)`：六邻含多个
  `deepslate_diamond_ore`，呈「同一矿脉位移」特征。
- `(1,0)` 「被考虑但未写入」`(22,-58,13)`、`(22,-58,14)`：六邻含 `tuff`，说明候选点状态
  与生成期不一致导致判定被拒。
- `(-1,-1)` 反向案例：预测 37 / 真值 21 / 错报 25 —— 预测明显偏多，属于随机数流被打断后的
  「额外矿脉」。
- `(-2,3)`：污染候选点 354 个（紫水晶洞），查全 45.45%。

## 九、仍未解决的问题 与 是否具备进入正式开发阶段

### 仍未解决

## 附录 B 已知实验缺陷（如实登记）

1. **`NoiseTerrainProbe` 在当前运行已关闭**：它在服务端线程上 `CompletableFuture.join()` 等待区块生成，
   在关闭 C2ME 的环境下会长时间阻塞服务端 tick（实测单 tick > 200 秒，触发 ModernFix 看门狗）。
   关闭后它输出「比较 0 格」，即**本报告不含地形层逐方块结论**。
2. **污染扫描是白名单下界**，不覆盖空气/水/岩浆/滴水石等类别（见 6.6）。
3. **「坐标错位」无全量口径**，只有样本级 6 邻域代理（见 6.2）。
4. **单点扰动在 10/10 区块都观察不到漂移**，这是设计上的对照（流末效应），不是反证；
   全量扰动才是主证据。
5. 测试世界为**单人集成服务端**：本实验需要读真实区块真值并原地重放，故不能直接在多人服务器上跑。
   但这不影响「影子上下文在客户端可构造」这一结论（6.1 节的 13 个方法调用面即证据）。
