## 一、结论摘要（一屏看完）

1. 现有自动挖矿的目标来源是「矿物配置 → 方块类型集合 → Baritone `mine`」，**全项目没有 target provider 抽象层**。
2. 种子挖矿的最小接入点是**已经存在**的 `MiningPathing#pathToOre(BlockPos)`（注释原文即「种子模式」），
   现役调用方 `MiningVeinMiner#chaseLeftovers` 已经是「停 mine → pathToOre 走过去 → 秒破逐块破坏」这条链路。
   因此**不需要**新增控制器，也**不需要**在几十个文件里撒 `if (seedMiningEnabled)`。
3. **本次任务的核心前提不成立**：客户端无法按 seed 复刻原版矿物分布。26.1.2 源码四条硬证据见第五节；
   旧项目源码里已写下同一结论（第六节）。因此「Seed 精准预测 BlockPos」与「Seed 真实性验证」两条
   在本版本线上做不出来，硬做即等于用伪预测冒充精准算法（用户明令禁止）。
4. 旧项目对应物是 `mining/prediction/OrePredictor.java`（实测扫描版，264 行），本项目移植时整块留白，
   登记在 `AutoMinerModule` / `MiningSettings` / `MiningStateMachine` 三处类头注释。
5. 待用户三选一（第七节）：A 移植实测扫描做唯一目标来源（可交付）；B 客户端复刻 worldgen（不可能交付）；
   C 先只做页面与接入层。

## 四、Seed 最小接入点（唯一一处分流）

**接入点**：`feature/mining/fsm/MiningStateMachine.java:1221-1252` 的 `tickMining()`「启动采集引擎」分支。

- 现状：无条件 `module.getBaritone().startMining(module.getMiningTargets())`（:1248）。
- 改法：该分支内加一次来源判断——种子模式从新目标源逐点取坐标 → `pathToOre` + 秒破既有破坏链路；
  取不到就维持等待态（Fail-Closed），**不回落**普通模式。
- 影响面：状态机只碰这一个分支；寻路、破坏、自愈、卸货、补给、修复、食物、战斗、传送全部不动。

**结论：不需要新建 `SeedMiningController`，不需要第二套采集循环。**
旧项目 `MinerFSM.tickSeedMining()` 自带的那套（`breakSeedBlock` / 破面锁定 / `ensureBestToolForSeedTarget` /
`seedPathRetries`）**不移植**——那是「第二套挖矿」，属本项目明令禁止形态。

### 5.2 四条硬证据：这一层客户端做不到

| # | 事实 | 出处 |
| --- | --- | --- |
| 1 | `Level` 没有 `getSeed()`；seed 只在服务端 `ServerLevel` → `WorldGenSettings`(SavedData) → `WorldOptions` | `ServerLevel.java:1764-1766`、`WorldOptions.java:22,40` |
| 2 | 唯一 `WorldGenLevel` 实现 `WorldGenRegion` 的构造**必须传 `ServerLevel`**，客户端无法构造 → `PlacedFeature.place / placeWithBiomeCheck` 没有合法入参 | `WorldGenRegion.java:63,81-91` |
| 3 | `OreFeature` 依赖生成期地形：`getHeight(OCEAN_FLOOR_WG)` 与生成期方块状态（target 判定 + 空气暴露判定）→ 必须真跑完整地形生成（NoiseChunk + Surface + Carver） | `OreFeature.java:46,145-147,168-181` |
| 4 | `globalIndexOfFeature` 来自 `FeatureSorter` 对「该维度全部生物群系 feature 列表」的排序 → 依赖服务端整包数据包，第三方服可自定义 | `FeatureSorter.java:106-122` |

补充事实：

- `RandomState.create(HolderGetter.Provider, ResourceKey<NoiseGeneratorSettings>, long)` 是 public static，
  客户端注册表在手时可以造（`RandomState.java:28-34`），但**只有它不够**——它只给噪声地形，不给装饰管线所需的
  `WorldGenLevel`。
- `BiomeFilter` 不消耗随机数，但需要 `PlacementContext.topFeature()`（只有 `placeWithBiomeCheck` 才填，
  直接 `place()` 会抛 `IllegalStateException`）与 `generator.getBiomeGenerationSettings(biome)`。
- 客户端能拿到：维度、`registryAccess`（`Level.registryAccess():1091-1092`、`RegistryAccess.lookupOrThrow():22-24`）、
  已生成区块的真实方块状态与高度。
- 客户端拿不到：world seed、生成期 proto-chunk、`ChunkGenerator` 实例（`LevelStem` 不含 seed，且属服务端注册表）、
  服务端是否存在自定义数据包 / 假矿插件。

**因此：单靠一个用户输入的 long + 客户端，做不到 BlockPos 级精准预测。**
能做的只有「实测扫描已下发区块的真实矿位」——这正是旧项目的选择。

## 七、必须拍板的前提冲突与三个选项

用户本次要求中，「客户端按 Seed 精准预测矿石 BlockPos」与「Seed 真实性验证（多样本比对）」两条前提，
在 26.1.2 当前架构下不成立（第五节）。请三选一：

### 选项 A（推荐，可交付、可实机验收）

移植旧项目「实测扫描」作为**唯一目标来源**，按用户给定边界重构：

- 只读现有矿物配置（`getTargetBlock()` 三选一），不建第二份矿物列表；
- 已加载区块分帧扫描真实矿位 → 缓存 → 按既有 ESP 体系渲染；
- 目标经既有链路消费：`pathToOre` 走过去 + 秒破 `mineRequested` 破坏，不新增任何控制器；
- 独立「种子挖矿」页（复用 `PanelScreen` / `ConsoleWidgets` / `SettingToggle` / `SettingTextBox` /
  `SettingNumberBox` / 主题色槽），玩家可见文案全中文；
- Fail-Closed：未启用 / 区块未扫描完 / 无矿位 → 取不到目标即等待，**不回落普通挖矿**；
- 代价：种子的「真实性」无法验证。种子字段只能是**格式校验 + 仅记录**，页面状态文案按真实能力写，
  不出现「验证通过」这类结论。

### 选项 B（严格照本次要求）

客户端自建 `WorldGenLevel` + `ChunkGenerator`(NoiseBasedChunkGenerator) + `RandomState` +
完整装饰管线 + `FeatureSorter` 索引 + 自建区块生成，再按 `setDecorationSeed` / `setFeatureSeed` 复刻。

- 仅对「原版数据包 + 无假矿插件 + 区块未被改动」的服务器有效；
- 工程量与运行代价极大，首版不可能交付；
- 属《开发习惯》第 163 条「非框架必需的大型新增」，须用户单独授权。

### 选项 C（分两步）

先只做 A 的配置页 + 独立页面 + 接入层（不含扫描引擎），把 worldgen 预测拆成后续独立阶段。

## 九、验收口径（选项 A 落地后适用）

1. 开关关闭 → 现有挖矿行为与开发前逐项一致；
2. 开关开启 + 种子空 / 格式非法 → 只显示对应状态，不生成目标、不回落普通挖矿；
3. 区块未扫描完 / 无矿位 → 等待，不放行；

5. 精准采集 / 时运 / 食物 / 回家 / Baritone 行为与之前一致；
6. 清空种子、关闭开关、更换目标 → 缓存完全失效；
7. 换维度 / 重进服务器 → 不串数据（点位与设置按服隔离，第 236 条）；
8. `.\gradlew build --console=plain -q` EXIT=0；
9. `runClient` 进世界一次，日志出 `yiyiaddon initialised`、无新崩溃报告；
10. 精准度：实测矿位与真实方块逐一比对（本题下为恒等，可做到 100%，与「预测」不是同一件事，
    报告里必须按实测口径描述）。
