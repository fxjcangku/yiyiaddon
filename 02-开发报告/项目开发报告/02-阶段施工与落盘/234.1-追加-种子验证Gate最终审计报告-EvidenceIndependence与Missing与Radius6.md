## 三、234 的旧 grouping 算法（口径第三节）

```
旧：对每一批证据
    按 (目标区块, 写入者) 分桶
    桶内做 26 邻域连通分量
    一个连通分量 = 一份「独立证据」
```

它把「连通性」当成了「独立性」的判据。问题在于：**空间上断开 ≠ 世界生成事件不同**。

## 四、Minecraft 26.1.2 Ore placement provenance 源码结论（口径第五、六节）

逐行核对本线 26.1.2 源码（不是记忆、不是别的版本）：

| 位置 | 事实 | 推论 |
|---|---|---|
| `ChunkGenerator#applyBiomeDecoration:327-388` | 每次装饰前 `random.setDecorationSeed(levelSeed, origin.getX(), origin.getZ())`；每个 placed_feature 再 `setFeatureSeed(decorationSeed, featureIndex, stepIndex)` | 真实「一次放置」的 provenance = **（写入者区块 → decorationSeed）+ 生成阶段 + placed_feature 序号** |
| `PlacedFeature#placeWithContext:42-60` | 一次 placed_feature 调用把 placement 展开成一串坐标，用**同一个 `RandomSource`** 逐个 `feature.place(...)` | 同一次放置的多个产出共享随机流 |
| `OreFeature#doPlace:71-166` | 一条矿脉 = 多个椭球并集；`BitSet tested` 去重；每格还要过 `canPlaceOre` 规则测试 | **被规则拒掉的格子留下空洞 → 同一次放置完全可能空间断裂成多簇** |

**结论**：用 26 邻域连通簇当独立性判据，等于把「一份 provenance 被地形切断」误判成「多份证据」，
是**系统性多计票**。这正是本轮要把旧口径摘掉的原因。

## 五、现有 Predictor 能否识别真实 placement identity（口径第六节）

**不能，而且离得很远。** 正式层 `PredictedOre` 的字段只有：

```
position / oreType / certainty / source(恒 UNATTRIBUTED) / originViewer / conflictingWriters
```

没有 placementId、没有 veinId、没有 rngSeed、没有生成阶段序号。因此：
**正式层最细只能到「哪个区块的装饰写进来」这一级**。任何声称「逐 placed_feature / 逐矿脉身份」
的独立性判据，在当前正式层都是**没有数据支撑的**。

## 六、最终 Evidence Unit 定义（口径第七、八、九节）

**conservative independence 原则**：

> 无法证明两个证据独立 → 视为**同一单元**；
> 而不是「无法证明它们相同 → 就拆成两个」。

落地（[SeedValidationEvidenceGroup.java](../../../src/main/java/com/yiyiaddon/seed/validation/SeedValidationEvidenceGroup.java)）：

```
单元键 UnitKey = (目标区块 pack, 写入者 pack | NO_VIEWER, 来源 oreSource, 矿物 oreType)
一个桶 = 一个有效证据单元（桶内绝不裂票）
同一坐标被重复描述 → 只保留第一条（不重复计票）
单元号 unitId = splitmix64 混合单元键（与 HashMap 迭代序 / identityHashCode / tick 顺序无关，可复现）
```

- `spatialComponents()`（26 邻域簇数）**降级为 presentation / debug 信息**，不参与任何票数计算；
- 旧口径以 `buildLegacySpatialForAudit()` 形式保留，**只用于审计对照**，不参与判定。

### 9.1 如实登记的两条局限

1. provenance 只到「写入者区块」这一级 → 同一写入者的多条**互不相关**矿脉也会并成一个单元，
   代价是「少算票」。方向是安全的（宁可少算）。
2. 同一次放置若跨两个目标区块（写半径 1 允许），会在两个目标区块下各算一个单元 —— 如实登记。

## 七、UNKNOWN provenance 的处理（口径第十一、五十二节·硬红线）

`originViewer == null` 时，键取哨兵值 `NO_VIEWER`，于是：

**同一目标区块内所有来源未知的候选，天然合并成恰好一个单元** ——
不因为空间隔了两格就声称两个独立世界生成事件。

> 这是本轮对本线**全部实测证据**的默认情形：正式层来源分类恒为 `UNATTRIBUTED`、写入者多数为未知。
> 也就是说，234 那套「空间连通簇」在正式层实际上**没有任何 provenance 依据**在支撑它。

## 十、最终 Validation Policy 与阈值（口径第十三、十四、十五、二十一、二十二节）

唯一阈值来源：[SeedValidationPolicy.java](../../../src/main/java/com/yiyiaddon/seed/validation/SeedValidationPolicy.java)

```java
VERIFY_MIN_CONFIRMED_UNITS   = 8     // 曾经确认的有效证据单元
VERIFY_MIN_CONFIRMED_CHUNKS  = 3     // 覆盖的不同目标区块
VERIFY_MIN_CONFIRMED_RATIO   = 0.50  // 曾经确认单元 ÷ 已观察单元
INCONCLUSIVE_MIN_OBSERVED_UNITS = 8
CONFLICT_MIN_DETERMINISTIC_UNITS = 2 // 硬冲突判据（本阶段不可达）
```

判定顺序：**硬冲突 → 验证 → 证据不足 → 收集中 → 未验证**（fail-closed）。

### 10.1 阈值数字有没有改变

**没有改变 8 / 3 / 0.5。** 但口径明确：**禁止为了保住 8/3/0.5 反过来去设计分组**。
本轮的实际顺序是：

1. 先按源码结论把分组收紧成 conservative independence（第 6 节）；
2. 用**新口径**重新实测正确种子与四个错误种子（第 11、12 节）；
3. 拿实测值核对 8 / 3 / 0.5 是否仍然成立 —— 结论是**余量反而变大**，因此沿用。

### 10.2 阈值依据（新口径实测余量）

| 阈值 | 正确种子实测 | 错误种子实测 | 余量 |
|---|---|---|---|
| 单元 ≥ 8 | 首次达标 **8**；满覆盖 **53** | ≤ 2（开发端）；≤ 1（正式产物） | ≥ 4 倍 |
| 区块 ≥ 3 | 首次达标 5~8；满覆盖 49 | ≤ 2 | ≥ 1.5 倍 |
| 比例 ≥ 50% | 100.00% | ≤ 3.92% | ≥ 12 倍 |

**分子分母口径**（口径第二十二节）：`ratio = 曾经确认单元 ÷ 已观察单元`，**两边都是单元维度**，
不存在「分子按单元、分母按候选方块」的混合口径。候选方块级别的数字只用于界面展示，不参与判定。

### 10.3 各状态含义

| 状态 | 何时 |
|---|---|
| VERIFIED | 三条阈值同时满足（**锁存**：普通 MISSING 不撤销） |
| INCONCLUSIVE | 已观察单元 ≥ 8 但未达阈值（**MISSING 只算「看过」，不算负票**） |
| COLLECTING | 已观察单元 1~7 |
| CONFLICTING | 需要 ≥2 个「确定性候选却观察为非矿物」的单元 —— **本阶段不可达**（正式层不产出 DETERMINISTIC） |

## 十七、Radius6：之前为什么卡在「加载地形」（口径第二十九、三十节）

### 17.1 现象（234 记录）

234 报告把 `clientSeedRadius6Smoke` 记成「客户端长时间停在加载地形，拿不到读数」，
并据此把该用例标为「233/234 唯一没完整跑完的性能 smoke」。

### 17.2 最终根因（本轮定案）

**两个原因，主因是测试装置自身的缺陷：**

1. **主因 · 装置状态机漏分支**（harness 缺陷，与产品代码无关）：
   `SeedRadius6Smoke.Phase` 定义了 `WAIT_WORLD / PREPARE / EXPAND / MEASURE`，
   但 `tick()` 的 `switch` **没有 `WAIT_WORLD` 分支**。玩家进入世界后阶段永远停在
   `WAIT_WORLD`，`prepare()` 永不执行 ⇒ 装置表现就是「进了世界一动不动、日志静默」。
   这与「客户端在加载地形」在日志上无法区分，因此 234 的归因偏了。
   修复：删掉多余的 `PREPARE`，补 `case WAIT_WORLD -> prepare(client)`；卡顿统计也不再被
   「未进世界」阶段污染。
2. **次因 · 运行目录冷启动**：`radius6` 目录首次全新创建时，Bobby 要从服务器整片下载区块，
   客户端确实会长时间停在加载地形（234 观察到的表象）。运行目录沿用「由 `visual` 目录复制而来
   （Bobby 缓存已预热）」的做法后不再出现。

**没有**为了修这个测试去改 Production `SeedMiningService`（口径第三十六、四十四节）。

### 17.3 顺带修掉的一处装置缺陷

同一目录里 `radius6` 实例的 `config/module-state.json` 残留着「覆盖半径 = 1」（来自上一次
`visual` 运行的复制），装置在跑的中途被服务层重新读回，于是采样里出现了
`范围 6（9 个目标区块）` 与 `候选 0 条` 两条被污染读数（见 `R3`）。
处理：跑前删除该实例的 `module-state.json`，让装置自己写入的 `覆盖半径 = 6` 成为唯一来源。
干净重跑（`R3b`）全部 6 次采样都是 169 个目标区块。

## 二十五、仍存在的限制（如实清单）

1. **provenance 只到「写入者区块」这一级**：正式层没有逐 placed_feature / 逐矿脉身份，
   因此单元是**偏保守**的；同一写入者的多条无关矿脉会被并成一个单元（少算票，方向安全）。
   要真正做到「一矿脉一票」，需要后续阶段引入 placement / vein 级 provenance，本轮**不做**。
2. **同一次放置跨两个目标区块会被算两个单元**（写半径 1 允许），如实登记、不假装不存在。
3. **阈值是实测余量，不是数学证明**：不能宣传成「100% 证明服务器真实 Seed」，
   也不能由 4 颗错误种子外推成「所有错误种子永远无法通过」。
4. **CONFLICTING 不可达是刻意设计**：正式层不产出 DETERMINISTIC ⇒ 硬冲突判据凑不满 2 个单元。
   证明不了安全，就宁可永远停在 INCONCLUSIVE（fail-closed）。
5. **Radius6 的读数依赖运行目录预热**：全新目录会让 Bobby 整片下载区块，客户端长时间停在加载地形；
   本轮的读数取自预热过的目录，这一点在装置与报告里都有登记。
6. **MISSING 已证明「对合法调度敏感」，未证明「对所有历史状态敏感/不敏感」**：
   三个全新世界只覆盖三种请求顺序，结论严格限定在实测范围内。
7. **production Validation smoke 依赖「世界种子 = 声明种子」这一世界前提**（§20.2 的过程记录）：
   装置本身不校验世界真实种子（单人世界会打警告）。专用服务器路线（`runSeedValidationServer`）没有这个前提。
