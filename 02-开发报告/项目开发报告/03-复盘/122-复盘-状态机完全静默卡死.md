# 122-复盘-状态机完全静默卡死（mine 进程活着却不在寻路）

日期：2026-09-19
项目：yiyiaddon（新项目，Fabric 26.1.2 客户端模组）
旧项目对应物：无（「挖不动自愈」是本项目自建能力，见字段区注释与开发报告 77/79；本次为它扩一档判据）
用户原话：「还有幽冥脉络下面的钻石块 没办法识别 就卡住了状态机了」
（追问确认：卡住表现 = **完全静默、聊天栏一条播报都没有**；那块方块 ID = `minecraft:deepslate_diamond_ore`，是真目标矿）

---

## 一、取证：静默卡死反推出的状态

目标矿没问题（`deepslate_diamond_ore` 属于「锚点 + deepslate 变种」扩展，见
`AutoMinerModule#isTargetFamily` / `#getTargetBlocks`），所以问题在卡死检测本身。

三条「卡死」看门狗的门槛（`MiningStateMachine#tickMining`）：

| 看门狗 | 触发条件 | 为什么在你这次不触发 |
| --- | --- | --- |
| 挖不动快速自愈（15 秒） | `isPathing()==true` + 秒破空闲 + 5 秒没破坏过方块 + 低速（`:1207-1212`） | 要求**必须在寻路** |
| mine 退出重启（`stateTick>120`） | `!isPathing() && !isMiningActive()`（`:1135`） | mine 进程还活着（`isMiningActive()==true`） |
| 原地抖动 / 速度过低 | 3 分钟持续低速（`:1193` / `:1256`） | 满足，但要等 3 分钟 —— 之前就是「静默几分钟」 |

「完全静默」反推出当时的状态只能是：
**`isMiningActive()==true`（Baritone mine 进程活着）+ `isPathing()==false`（根本没在寻路）** ——
即 mine 进程停摆（算路失败 / 目标不可达 / 扫不到可达目标），三条看门狗里**一条都不满足**，
只剩 3 分钟的兜底，所以表现为「站着不动、聊天栏什么都没有」。

（已排除的另一种可能：秒破 `isActive()` 永久挂住。那条路有 `MAX_ATTEMPTS` → `fail()` → 拉黑 600 刻的
收敛链，最多几十秒就会让位原版，不是永久态；而且它成立时 `isActive()` 为真，同样落不到任何看门狗上，
但不会「静默到 3 分钟」——这条已在本次判据里用 `!isActive()` 排除。）

## 二、修复：把「mine 活着但不推进」也纳入 15 秒自愈

改 `feature/mining/fsm/MiningStateMachine.java`：

| 位置 | 改动 |
| --- | --- |
| `:1207-1231` | 抽出 `idleNoBreak`（界面关闭 + 过 mine 启动宽限 30 秒 + 5 秒未破坏方块 + 低速 + 秒破空闲 + **`!mc.gameMode.isDestroying()`**）；原判据 = `idleNoBreak && isPathing()`；**新增第二档** = `idleNoBreak && isMiningActive()` |
| `:1215-1220` | `!mc.gameMode.isDestroying()` 是第二档的安全阀：Baritone 用原版通道慢慢挖硬方块（黑曜石 / 远古残骸，超过 5 秒）时不算静止，避免误判 |
| `:1232` | `mineStalledNoPath` 记录本次是哪一档（只影响播报用词） |
| `:1246-1250` | 播报区分：第二档出「§e⚠ 挖矿进程停摆（没在寻路）§8▸ 重置采掘目标脱困」，第一档仍是原文案「挖不动面前的方块」 |
| `:406-413` | 字段区注释补上第二档的由来 |
| `:411-418` | 新增 `mineStalledNoPath` 字段 |

行为：静态卡死从「静默 3 分钟」变成「约 50 秒」（30 秒启动宽限 + 5 秒无破坏 + 15 秒判定）后
**重下发 mine 脱困**；若同一位置连续两次仍停摆 → 走既有兜底「重新前往野外换区域」。
恢复动作用的是既有那条链路（`ignoreSpawnerForNow()` + `stop()` + `startMining(getMiningTargets())`），
没有新增第二套脱困逻辑。

## 三、边界（说清楚，避免预期错位）

1. 本次修的是**卡死检测的漏网**，不保证「那块矿一定挖得到」：如果它确实不可达（封死 / 保护 / 算路失败），
   模块会在约 50 秒后重下发一次，再 15 秒仍无进展就换区（RTP），**不会再静默干等**。
2. 未动既有的第一档判据（在寻路却不动），避免削弱「挖不动面前的方块」那条已实机验证过的脱困。
3. 若实机看到「§e⚠ 挖矿进程停摆（没在寻路）」这句，说明命中本次新增的分支；
   若还是完全静默，说明还有第三条路（那需要 chatlog 定位）。

## 四、构建与验证

- `.\gradlew.bat build --console=plain -q` → **EXIT=0**（2026-09-19，本机）。
- **未实机**。实机验收项：
  1. 再遇到挖不了的目标矿：最长约 50 秒内出现「挖矿进程停摆（没在寻路）▸ 重置采掘目标脱困」，人重新动起来；
  2. 连续两次仍无进展 → 「✗ 方块挖不动反复卡死 ▸ 重新前往野外换区域」正常换区；
