## 二、改法调整：混入 → 集成层（报告 171 的修正）

171 首版把修复写成 `@Inject` 到 `baritone.Baritone.<clinit>` 的混入。26.1.2 实测生效；但 26.2 的实测里该混入看起来在**准备阶段就被丢掉**（配置 8 条、日志只 `Prepared 7`、从未出现 `Mixing BaritoneExecutorDaemonMixin into baritone.Baritone`）。

据此把实现改为**集成层调用**：新增 `integration/baritone/BaritoneThreadPool#daemonize()`，由 `YiyiAddon#onInitialize` 在**任何世界加载之前**调用；同时删掉那个混入类与配置项（第 169 条：同一件事只留一份实现）。

新实现的三条依据（都可指认）：

1. `baritone.Baritone` 的 `<clinit>` 只建池对象、不创建线程；线程在**第一次提交任务**时创建，实测首个池线程出现在进世界之后，因此模组初始化时换工厂足够。
2. 用的是它的公开入口 `Baritone.getExecutor()`（字节码即 `getstatic threadPool; areturn`），`setThreadFactory` 只影响后续新建线程，池的容量 / 队列 / 保活语义不变。
3. 幂等、且对「池里已有线程」只记调试日志，不做破坏性动作。

## 三、更正：26.2「混入不生效」的观察被**测试环境污染**污染（重要教训）

继续排查时发现两个验收实例的 `mods/` 里**同时躺着混淆包与个人版 jar**：

```
26.1.2 mods: fabric-api-…jar  yiyiaddon-1.0-beta1-26.1.2.jar  yiyiaddon-1.0-beta1-personal+26.1.2.jar
26.2   mods: fabric-api-…jar  yiyiaddon-1.0-beta1-26.2.jar    yiyiaddon-1.0-beta1-personal+26.2.jar
```

Fabric 对同 ID 的两个候选只加载其中一个，日志里不出现 Duplicate 告警，**无法从日志判断到底加载了哪一个**。也就是说：那几轮「26.1.2 生效 / 26.2 不生效」的对比结论**不可靠**——两条线跑的可能是不同的 jar。

清理原因也查清了：验收脚本会在放包前删掉 `mods/` 里其它 `yiyiaddon-*.jar`，但前一次客户端仍在运行、jar 文件被占用，`Remove-Item -Force` 静默失败（脚本没把这一步当错误处理）。

**更正口径**：混入在 26.2 上到底会不会被丢掉，**本次没有定论**（不排除同样只是环境问题）。改走集成层的决定仍然保留，理由改为：实现更直白、两条线同一份代码、可读可测，不依赖混入框架的内部行为。

**教训（今后验收必须遵守）**：跑验收前先确认 `mods/` 里只有本次要验的那一个 `yiyiaddon-*.jar`（脚本的清理步骤要核对结果，不能只看它接着跑下去了）。
