# 复盘：后台「重新校验」失败 13 个 —— Mojang 拒绝 Cloudflare Workers 出口（已修复：双源回退）

日期：2026-09-21

## 一、用户反馈

后台「安全监控」点「重新校验」，弹窗返回「已刷新：更新 0 个玩家 / 跳过（已有XUID） 0 个 / 失败 13 个」，
即 13 个玩家全部校验失败、状态一个都没更新。用户问「为什么不可以刷新」。

## 二、诊断过程（全部为实测，非推断）

| 步骤 | 方法 | 结果 |
|---|---|---|
| 1 | 本机 PowerShell 请求 `api.mojang.com/users/profiles/minecraft/Notch` | **200**，返回正确 UUID —— 接口本身是活的 |
| 2 | 在 Worker 内加临时诊断路由，探测 4 个上游 | `api.mojang.com` **403**、`api.minecraftservices.com` **403**、本域自请求 522；403 响应体是 Cloudflare 防火墙拦截页（XHTML），带不带浏览器 UA 都一样 → 与 UA 无关 |
| 3 | 同时探测候选备源 | `playerdb.co` **200 且返回 UUID 与官方一致**；`mc-heads.net` 406；`laby.net` 403(error 1106)；`minecraft.wiki` 403 —— 均为对机房 ASN 的封锁 |
| 4 | 查 D1 真实数据 | 13 个玩家 **XUID 全为空**（第三方启动器登录，客户端 `user.getXuid()` 给不出值），10 个「正版」是旧项目迁移来的历史标记 |
| 5 | 用真实玩家名跑两源对照（只读诊断） | 官方 **13/13 全 403**；playerdb **12/12 真实玩家 200**，仅测试号 `probe_test` 400（不存在） |
| 6 | 摸清 playerdb 的「查不到」返回码 | **400** + `{"code":"minecraft.invalid_username"}`（不是 404），映射时必须一起处理 |

## 三、根因

`resolvePremium()` 在拿不到 XUID 时回退到按游戏名查正版档案，而这条回退路径只剩 Mojang 官方一个来源：

```
resolvePremium → lookupMojangProfile → fetch api.mojang.com
                 └ 403（非 200 也非 404）→ 返回 null → failed++
```

**Mojang 官方 API 按 ASN 拒绝 Cloudflare Workers 的出口 IP**（实测恒 403），而 Workers 的出口 ASN 固定为
Cloudflare（13335），无法更换；本地能通是因为家宽 IP 未被拒。叠加第 4 条（客户端给不出 XUID），
等于**正版校验这条链路在当前架构下 100% 失效**——旧项目的 Java 后端跑在普通服务器 IP 上，所以那时是好的。

## 四、修复

`worker.js`：

1. `lookupMojangProfile()` 改为双源：主源 `api.mojang.com` → 备源 `playerdb.co`，任一源给出结论即缓存；
   两源都不可用时仍返回 `null`（不写入离线结论，语义与修复前一致，不会误伤正版）。
2. 新增 `queryOfficialProfile()` / `queryMirrorProfile()`：分别把 200/404(400)/其他 映射为
   档案 id / `false`（确认不存在）/ `null`（不可用）。
3. 新增 isolate 级 `officialBlocked` 标记：官方源一旦返回 403 即置位，本轮后续查询直接走备源，
   避免每次白打一次必失败的 403（省掉一半上游请求；新 isolate 自动重置，官方恢复后无需改代码）。
4. `mojangCache`（1 小时）沿用，`false`（确认不存在）同样缓存，避免离线名反复打上游。

**新增第三方依赖（如实记录）**：`playerdb.co`。取舍理由——后台即时可用、无需给所有玩家重发模组；
风险是它属第三方服务，若限流或下线，则退化为「不可用」（**不会**产生错误结论，与修复前表现一致，无回归）。
替代方案：把名称查询下放到模组（玩家本机 IP 可正常访问 Mojang），代价是要给所有玩家重发 jar；
两者可随时切换，代码里只差 `queryMirrorProfile` 一个函数。

## 五、顺带修掉：面板「崩溃与异常 200」是分页长度冒充总数

用户截图里 KPI「崩溃与异常 200」，而 D1 实际 `crashes` 0 行 + `anomalies` **558 行**。

- 根因：`/api/admin/crashes` 与 `/api/admin/anomalies` 返回的 `total` 写的是 `rows.results.length`，
  而两条查询都带 `LIMIT 200` —— **分页长度当总数**；`/api/admin/command-activities` 连 `total` 都没有（`LIMIT 120`）。
- 修复：三条路由各补一条真实 `SELECT COUNT(*)`，`total` 返回真实总数；面板 KPI / 分段标签 / 卡片标题
  改用 `total`（缺字段时回退列表长度），列表被截断时补一行 `.hint`「共 N 条，仅列出最近 M 条」。
- 异常数据本身正常：`high_speed/high` 311 条 + `teleport/medium` 247 条，涉及 9 名玩家，2026-08-28 至 2026-09-21 累计，非刷屏。

  单次查询 18–33ms（首个 339ms 含那次 403）。

  `/sw.js` = `yiyiaddon-v5`；`/api/config` 正常；`/api/chat/online` 正常返回 4 人在线；
  三条后台列表路由未带凭证均 401（路由在、鉴权正常）；临时诊断路由已删除并确认 404。
