# 复盘：自动挖矿「自用模式」卖矿链路

日期：2026-09-20

## 一、用户需求

用户在自己常玩的服务器上挂机挖钻石，需要模块在**挖够就自己去卖掉**再回来接着挖。用户原话：

> 「假设我想挖到25组钻石就输入/cd 打开菜单 发包点击 点击回去主城 寻路到npc 发包交互一键出售
> 然后在打开/cd 回去生成服 然后继续rtp进入挖矿状态机」

需求在讨论中被用户逐条收窄，最终口径：

| 项 | 最终口径（用户拍板） |
| --- | --- |
| 开关位置 | 控制台顶栏，「启用」开关旁边再加一个「自用模式」开关 |
| 配置位置 | 控制台新增一栏「自用模式」页 |
| 点位 | **只绑食物箱**：不要矿物箱、不要挂机修复点（「只是不用绑定矿物箱子 挂机点位 其他都一样的」） |
| 触发 | 存够设定组数（默认 20 组，带加减框）**或**背包先满，谁先到算谁 |
| 耐久 | 不管（时运镐挖矿自带经验，靠经验修补自修） |
| 背包满 | 「背包满了直接触发出售」（垃圾自动丢弃照常在跑） |
| 卖完回程 | `/cd` → 「跨服传送」→ 勾选框选服（生存世界#1 / 资源世界#1）→ 落地直接接 RTP |
| 收购 NPC | 固定坐标 `-24424, 66, -5355`，显示名「黑市商人[收购]」，实体 ID 是 `minecraft:player` |
| 死亡返回 | 死亡返回指令填 `/back`，落地**就地接着挖**（不再重发 RTP） |
| 静默 | 「我要的是不抢鼠标 不交互页面出现」 |
| 卡顿 | 要有超时 + 重试（「服务器有时候看卡了怎么办」），原地重试，不带着矿乱走 |
| 指令 | 「指令不需要你管 我自己填」——全部走设置项，默认值预填，代码里不写死任何服务器指令 |

按第 171 条（移植不得夹带新功能），本条属**用户明确指令新增**，已先讨论定稿再动手；用户最终指令「开始吧」。

取证到的两点事实：

1. **收购 NPC 不能按实体类型识别**：用户给的实体 ID 是 `minecraft:player`（插件用假玩家实体伪装的 NPC），
   按类型排除「玩家」会把 NPC 一起排掉。实现改为**坐标寻路为主 + 显示名核对**
   （`stripFormatting` 剥掉 `§` 颜色码与空白后做包含比对），只排除玩家自己。
2. **出售界面是服务端推来的容器**：`MiningContainer#isOperatingContainer` 认不出（不是我方发包开的），
   会真弹出来抢鼠标。因此 `AutoMinerModule#onOpenScreen` 的门控加了一条
   「处于我方菜单流程中（`MiningPersonalSell#isMenuFlowActive`）→ 只 cancel 不收容器」，
   与 RTP 选单那条完全同源（收掉容器等于把菜单关掉，槽位就永远点不到了）。

## 三、修改内容

### 新增文件

**`service/MiningPersonalSell.java`** —— 出售流程的动作层，不含阶段逻辑：

- 流程标志：`beginFlow / endFlow / reset / isMenuFlowActive`（给 `onOpenScreen` 做静默门控）；
- 菜单：`menu / hasMenu / menuHasKeyword / clickKeyword`（关键词匹配剥颜色码与空格）；
- 出售目标：`matchesTarget`（**填登记 ID 走精确匹配、填名字走包含比对**）、`clickTarget / menuHasTarget /
  findTargetSlot`、`canResolveTarget`（自检用，按文本缓存的探测，不每帧遍历注册表）、
  `countTargetInBag`（主背包 0~35）；
- 背包：`isInventoryFull()`（36 格全非空）；
- NPC：`npcPos() / npcStandPos() / findNpc() / interactNpc(Entity)`
  （`faceEntity` + `markOwnContainerOpen` + `gameMode.interact`；站位取 NPC 正面一格）；

**`ui/console/MiningPersonalPage.java`** —— 自用配置页 + 顶栏开关：

- 分组：自用模式说明 → 出售物品（**留空跟随目标选择页 + [点击选择] + [当前值] + [↻]**）→ 触发组数（1~36 加减框）→ 出售流程

  → 收购 NPC（X / Y / Z / 名字关键词）→ 卡顿与重试（单步超时 1~60、单步重试 0~10）→ 末尾说明；
- `ModeSwitch implements ConsoleHeaderBar.Extra`：文字「自用模式」+ 开关，画在模块开关左侧；
- 两行「回程目标服」用 `SettingToggle` 做成**互斥勾选**（取消勾选不生效，只把视觉拉回来，不会两个都空）。

### 状态机（`MiningStateMachine`）细节

- **触发**（`tickMining` 优先级 3.5）：`personalMode` 打开时，`personalSellReady()` 或
  `personalSell.isInventoryFull()` 命中即转 `SELL_TRAVEL`；同时把原有的两条修补分支整体
  包进 `if (!module.isPersonalMode())`（自用模式不管耐久）。
- **四态**：`tickSellTravel`（发流程指令 → 点回城关键词 → 等传送 → 落地稳定 → `SELL_PATH`）、
  `tickSellPath`（**寻路到 NPC 正面一格**：`npcStandPos()` 按实体 `getYRot()` 算 `x = -sin(yaw)`、
  `z = cos(yaw)` 偏一格，`GoalNear(pos, 1)`；每 20 刻按需刷新，兜住落地瞬间实体未同步；到 2 格内转
  `SELL_TRADE`，含独立的停滞监测，不复用卸货那套「允许破坏挡路方块」的话术——城里拆人家方块是事故）、
  `tickSellTrade`（循环：点出售矿石 → 等菜单刷新 → 点「全部」→ 等刷新 → 点「确认出售」→ 等结算，
  直到背包该矿石清零）、`tickSellReturn`（收菜单 → 发流程指令 → 点跨服关键词 → 点目标服 → 等落地 → 交回 `GO_WILD`）。
- **静默**：整条链全程 `beginFlow()`，只在**离开整条链**（转 `GO_WILD` / 停机）时 `endFlow()`，
  态与态之间不中途松开；`SELL_TRAVEL / SELL_RETURN` 全程持续按「我方传送」认领位置跳变
  （回城与跨服都是点菜单触发的，没有指令线索，不认领会被手动传送检测判成玩家干预而停机）。
- **超时与重试**：每步 `sellStepTicks` 计时，到 `stepTimeoutTicks` 就按设置重试本步
  （`sellStepOutcome`：继续等 / 回本步起点 / 用完停机），重试上限内部再夹一道硬上限 10；
  单步彻底失败走 `sellAbort` —— 停机 + 播报「出售流程中断」，绝不带着一身矿继续往下走。
- **防连点**：菜单里这些槽位同屏存在，用 `menu.getStateId()` 变化判「服务端已处理完上一次点击」，
  不等刷新连点会点到上一屏的按钮（数量还没选上就点确认 → 一颗都卖不出去）。
- **防死循环**：一次「全部」只提交一屏上限，所以做成轮次循环；连续 2 轮一颗没少即判
  「收购菜单没有成交」停机，另有 64 轮总上限。
- **死亡**：`tickRespawnWait` 末尾自用模式转 `MINING`（就地接着挖），不再走 `GO_WILD`
  ——否则 `/back` 刚落地的位置又被 `/wild` + RTP 送走，等于白做。
- **播报**：新增 4 条 `SELL_*` 文案（回城那条带「带 N 组 矿名」）；`RESPAWN_WAIT` 按模式区分文案。

## 六、下一阶段开发规划

### 一、下一阶段目标

用户在自己服务器上开「自用模式」跑一轮完整链路，确认六个环节都对得上。

### 二、执行原因

这套流程全部依赖用户服务器的插件行为（`/cd` 菜单长什么样、点哪个槽回主城、市场菜单的槽位名、
跨服列表长什么样、对假玩家实体右键是否就是开收购界面），客户端侧无法离线验证。

### 三、前置条件检查

- 已完成：设置项 / 保存读取 / 四态链 / 静默门控 / 超时重试 / 自检 / 控制台页 / 使用说明，编译通过；
- 依赖：用户进服务器，按控制台「自用模式」页填一次配置（出售矿石填「钻石」或 `minecraft:diamond`、
  回程目标服勾一个、死亡返回指令填 `/back`）。

### 四、任务拆分（按链路顺序验收）

1. 目标：确认触发与回城；涉及：`tickMining` 触发块 + `tickSellTravel`；
   验收：攒够设定组数（可先把组数调到 1~2 组试）后自动播报「开始出售 ▸ 回主城 · 带 N 组 钻石」，
   人落到主城大厅，**界面全程没弹出来、鼠标没被抢**；
2. 目标：确认寻路与出售；涉及：`tickSellPath` + `tickSellTrade`；
   验收：走到「黑市商人[收购]」旁边，收购菜单在后台打开，背包钻石一颗颗减少直到清零，
   播报「出售完成」；
3. 目标：确认回程与接回挖矿；涉及：`tickSellReturn`；
   验收：回到勾选的那个服，落地后自动 RTP 换区继续挖；
4. 目标：确认死亡分支；涉及：`tickRespawnWait`；
   验收：死亡后 `/back` 落地就地继续挖（不重新 RTP）；
5. 目标：确认卡顿重试；涉及：`sellStepOutcome`；
   验收：服务器卡顿时能看到「…未响应 ▸ 重试 N/M」，重试用完则停机播报；
6. 目标：确认自检与点位页；涉及：`selfCheck` + `MiningPointPage`；
   验收：自用模式下自检不再报矿物箱 / 挂机点，点位页只剩食物箱一张卡。

### 五、验收标准

- 六项全过，且模块运行期间**没有一次界面弹出与鼠标抢占**；

## 七、后续纠偏（同日：用户逐条纠正）

| 4 | 「出售矿石的名字 我可以自己改 不是做成选择器懂？填名字跟id都能识别我选的是挖什么钻石」 | **撤掉选择器**，`personalSellTarget` 改为**单行文本**（`SettingTextBox`，与「流程指令」同一构件、同一宽度）。匹配层 `matchesTarget` 双路：能解析成登记 ID（`minecraft:diamond`）就按 ID 精确匹配，否则按物品显示名做包含比对（两边都先剥颜色码与空白），所以填「钻石」也认。配套：`MiningTargetControls` 里为选择器加过的全部代码（候选总数、状态文字、清空按钮、守卫）一并删除，该文件回到零 diff；`MiningConsoleScreen` 状态条与 `MiningConfigDigest` 详情改为**回显用户填的原文**（原先按 ID 解析显示名，填名字会显示成「空气」）。名字有歧义时（「钻石」也会命中「钻石块」）填 ID 更稳，已写进使用说明与设置行提示 |

| 5 | 「方块列表选择器加上 我们服务器还有收圆石 那些。至于出售物品那些自动联动目标选择器 我选什么就显示出售什么懂吗？ 这样子就不会错了」 | **定稿口径**（推翻了第 4 项的「纯文本行」）：<br>① **留空 = 跟随目标选择页**——新增 `MiningSettings#personalSellItem()`（手选优先，留空按 主世界矿石 → 下界矿石 → 普通方块 取目标），匹配层、状态机触发、播报、状态条、配置详情全部改走它。目标页给的是登记 ID（时运是掉落物、精准是原矿物品），跟随状态因此与正在挖的矿天然同源，**填错这件事从根上没了**。<br>② **加「点击选择」按钮**（与「目标选择」页同一套行形态：`点击选择 + 当前值 + ↻`），候选为**全部物品**（剔除空气、单值准入），选中即写入 `personalSellTarget` 覆盖跟随，↻ 清空回到跟随——服务器另收圆石这类方块就靠它。<br>③ **为什么用物品列表而不是方块列表**：时运模式卖的是掉落物（「钻石」不是方块，方块表里根本没有），而圆石、钻石矿石、原木这些方块物品本来就在物品列表里；方块表里没有物品形态的（水 / 岩浆 / 火 / 耕地）选了也进不了背包、卖不掉。<br>④ 自检里那条「与当前采集模式不符」的硬拦**删除**（它只判「是不是某座矿的产物」，范围太大，且会把圆石这类非矿方块误伤），只留「未指定（目标没选也没手选）」与「识别不到这个物品」两条；`isSellItemCandidate` 随之删除。<br>⑤ 名字匹配层（ID 精确 / 名字包含双路）保留，用于兼容早前手填过物品名的存档。 |

第 4 项同时修正了一处**本次引入的回归**：`ConsoleHeaderBar#onClick` 接附加件时写成
`switchLeft - GAP - extrasWidth()`，附加件为 `null` 时比绘制侧多减一个 `GAP`（12px），
快捷键徽章热区左移 —— 已改为与绘制共用同一条 cursor 递推，并删掉多出来的 `extrasWidth()`。

| 6 | 「有没有自动纠错功能弹渐入渐出那个框 只能选一个方块 然后假设我想卖的方块是圆石 我选了精准采集模式 那不是掉的是石头吗 有没有纠错功能」 | **跟随跟的是「产出」，不是「目标本身」+ 三处纠错**：<br>① 新增 `AutoMinerModule#expectedSellItem()` = 「当前目标 + 当前采集模式」实际会进背包的那件物品 —— 矿石走等价产物映射表，普通方块走新表 `BLOCK_NON_SILK_OUTPUT`（`stone→cobblestone`、`deepslate→cobbled_deepslate`、`grass_block→dirt`；沙砾掉燧石是概率、黏土掉 4 个球，按单件推导必然错，故不收）。<br>② 新增 `sellItemFilter()` = 手选优先，留空则 `expectedSellItem()` —— 所有消费点（匹配、触发、播报、状态条）都改读它。<b>顺带修掉第 5 项遗留的边界</b>：跟随石头、没开精准时，卖的是背包里真有的圆石，不再一颗都数不到。<br>③ 三处纠错：**选择器加入时**（guard 复用 `sellItemMismatchReason()` 拒收并说明「当前只会掉『石头』，不是『圆石』」）、**切采集模式时**（`syncTargetsOnModeSwitch()` 改成返回提示文案，自动把手选值换成会掉的那件，`MiningTargetControls#pickLootMode` 用 `TooltipLayer.notify` 弹那个渐入渐出的提示框）、**启动自检时**（新增第三条「与目标 / 采集模式不符」，拦住而不是让他白跑一趟）。<br>④ 删掉只剩死路的 `equivalentSellItemForMode`（被 `expectedSellItem()` 取代，两份近似逻辑不留）。 |

**纠错口径**：手选是用户主动动作 → **拒收 + 说明原因**（不擅自改）；切模式是系统动作导致原选择失效 →
**自动改 + 弹提示**（他扫一眼就知道被改了什么，也能再改回去）。跟随状态（留空）两者都不参与 —— 它本来就是现推的产物，不可能错。
