# 108 - 复盘：发包防踢限速拦下平台层批量交互包（星露谷装水 / 破坏变慢）

- 日期：2026-09-19
- 触发：用户实机反馈「发包防踢开着的话，星露谷的发包装水跟发包破坏会变慢」
- 涉及文件：`core/net/ClientPacketSender.java`、`platform/network/BlockPacketSender.java`、
  `feature/tactical/AntiKickBypassModule.java`（仅类注释）
- 验证：`./gradlew build --console=plain -q` → **EXIT=0**；**未实机**（需重启开发客户端）

## 1. 定性：不是移植偏差，是旧项目同款行为

链路（全静态可证）：

```
星露谷/自动农场/自动箱子/村民补给/开挖容器
  → platform/network/BlockPacketSender（player.connection.send）
  → Mixin 拦 Connection.send
  → core/net/SendInterceptor.intercept（绕过判定 false，规则数 > 0）
  → SendGate.evaluate → 发包防踢模块 onSendRule
```

`BlockPacketSender.breakBlock / useOnBlock / interactBlock / tillBlock` 全是 `player.connection.send(...)`
（[BlockPacketSender.java:55-95](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/platform/network/BlockPacketSender.java)），
因此会被防踢模块的两条判据拦下：

| 判据 | 位置 | 对星露谷的影响 |
| --- | --- | --- |
| ④ 限制发包（**默认开**） | `AntiKickBypassModule:592-624` | `USE_ITEM_ON / USE_ITEM` 超「每秒最多放几个」（默认 **8**）→ `SendDecision.cancel()` **直接丢弃**；`START_DESTROY_BLOCK` 超「每秒最多挖几个」（默认 **8**）→ 同样丢弃。服务器卡顿 / 拉回冷却期（`stressed`）时两类包**一律丢弃** |
| ⑤ 网络延迟（默认关） | `AntiKickBypassModule:640-645` + `SendDelayService` | 豁免名单只有 KeepAlive / AcceptTeleport / MovePlayer / PlayerAction，**`USE_ITEM_ON` 不在内** → 开了「网络延迟」后装水每个包排队 20~80ms（默认区间），同 tick 连发的包被摊成数秒 |

而星露谷这两种动作**天生是同 tick 连发一批**：

- 装水（补水）：`REFILL_MAX_PACKETS = 32`，一次按「容量 − 当前水量」连发，最多 32 个 `UseItemOnPacket`
  （[StardewFarmExecutor.java:678-688](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/stardew/task/StardewFarmExecutor.java#L678-L688)）；
- 批量收割 / 破坏：`sendBatchActions()` 同一 tick 连发 8~15 个包（`interactBlock` 或 `START+STOP` 破坏）。

**结论**：一批只有前 8 个能出去，其余被丢弃 → 服务端只处理了一部分 → 验证阶段发现没达标 →
下一轮再补（再被丢一部分）→ 观感就是「装水 / 破坏变慢」，严重时表现为卡在补水环节。

旧项目 `tactical/AntiKickBypass.java:675-700`（限速丢弃）与 `795-801`（`shouldDelay` 豁免名单）
**逐字相同**，旧项目农场包的发送同样是 `farm/FarmPacketOps.java:107/140/168` 的 `player.connection.send`
→ 旧项目同样会拦，属继承行为，不是本次移植引入的偏差。

## 2. 用户决策

2026-09-19 实机确认后用户选择：**让模块自己的批量交互包绕行防踢**（与发包秒破同一机制）。
口径：防踢的限速与随机延迟只作用于玩家手动操作的包（挖掘 / 放置 / 聊天等），
不拦「模块按任务节奏主动发起的批量交互」。

## 3. 实现

| 文件 | 改动 |
| --- | --- |
| `ClientPacketSender` | 新增公共绕行入口 `sendBypassingGate(Connection, Packet)`：连接由调用方给出（避免两边各取一次 `Minecraft` 连接不一致），内部仍走 `PacketSendBypass.run` → `Connection.send`。类注释新增「谁能额外绕行」：只给平台层方块交互适配器用，业务模块仍禁止自行拼包绕行 |
| `BlockPacketSender` | 三处发包改走绕行：`sendUseOnBlock`（覆盖 `useOnBlock` / `interactBlock` / `tillBlock`）与 `breakBlock` 的 START / STOP；`breakBlock` 返回值改为「START 是否发出」（原来只要 player/level 存在就返回 true），连接不可用时如实返回 false，让调用方按失败重试。类注释新增「为什么绕行发包闸门」 |
| `AntiKickBypassModule` | 类注释新增「不拦谁（用户 2026-09-19 决策）」，写明平台层交互包绕行、本模块限速只作用于玩家手动操作，避免后来者重复判成 bug |

## 4. 影响面

- 走 `BlockPacketSender` 的全部调用方：星露谷（`DefaultStardewAdapter`）、自动农场（`TillTask` /
  `PlantTask` / `HarvestTask` / `ContainerTask` / `BatchPlantTask` / `BatchHarvestTask`）、
  自动箱子（`ChestInteractionService`）、村民补给（`VillagerSupplyRunner`）、
  矿物容器（`MiningContainer`）、附魔容器（`EnchantContainer`）、`PacketService`
  → 其交互包不再被防踢限速丢弃 / 随机延迟。
- 发包秒破、飞行绕过等原本就走核心绕行通道，行为不变。
- 玩家手动挖掘 / 放置 / 聊天：判据不变，防踢仍按其设置生效。
- 这些包也不再进入 `EventDispatcher.enqueueSent` 观测流（与其它绕行直发一致）。

## 6. 遗留与风险

- 脚本自己的批量包不再有本地限速保护：若服务器按「每秒包数」判踢，风险回到模块自身的任务节奏上。
  真要再收一层，应在模块内部做节奏控制（本轮**未做**，等用户提出）。
- 旧项目的「载具包不在延迟豁免名单」这一保留缺陷未动。
- 全部改动**未 commit**。

## 7. 补记（同日）：自动挖矿 / 秒破与防踢的三处交互

用户追问「发包防踢会不会影响自动挖矿的秒破」，复查出三条，**只做第 ① 条**（用户选择）：

| # | 交互 | 结论 | 本轮 |
| --- | --- | --- | --- |
| ① | 自动挖矿秒破的发包层 `feature/mining/fastbreak/MiningPacketProtocol`（`sendStart/sendStop/sendAbort`）走 `player.connection.send` | 在防踢限制内：`START_DESTROY_BLOCK` 超「每秒最多挖几个」（默认 8）被**丢弃** → 那一格这一秒挖不动；服务器卡顿 / 拉回冷却期（`stressed`）→ START **一律丢弃** → 秒破停摆。STOP / ABORT 被放行，网络延迟也豁免 `PLAYER_ACTION` | **已修**：三个发包改走 `ClientPacketSender.sendBypassingGate`（取号与 `retainKnownServerState` 顺序一字未改），类注释登记为「唯一的行为差异」 |
| ② | 自动挖矿换工具槽：`MiningFastBreakController:713-718` 直发 `ServerboundSetCarriedItemPacket` | 视图 `Kind.OTHER` → 不在延迟豁免名单 → 开启「网络延迟」后每个换槽包被排队 20~80ms | **未做**（用户未选） |
| ③ | 「发包秒破」AIM 模式接管原版 START：`PacketInstantBreakModule.onSendRule` 取消原版包后自己直发 | 注册顺序上防踢在前（`AddonModules:94-95`）+ `SendGate` 取第一个非放行 → 原版 START 被防踢判超限 `cancel` 时**秒破规则不执行** → 那一下既没原版也没秒破，方块不动。秒破自身发包走 `ClientPacketSender` 绕行，所以不是被限速，而是**抢不到包** | **已修**：给 `SendGate` 加规则优先级（`register(ownerId, priority, rule)`，默认 0 = 原注册顺序口径），秒破用 `GATE_PRIORITY = 100` 注册 → 与启用顺序无关地先于防踢判定。**没有**改 `AddonModules` 的构造顺序：秒破默认关、运行时才开，单靠列表顺序保证不了先注册 |

- 三条都是**旧项目同款**（`AutoMinerPacketProtocol` 逐字移植、旧实现同样 `connection.send`），
  不是本轮移植引入的偏差。
- ③ 的修法在核心闸门上新增**规则优先级**：`SendGate.register(ownerId, priority, rule)`，
  快照按「优先级降序 + 同优先级注册序号升序」重建。不显式传优先级的模块全部是
  `DEFAULT_PRIORITY = 0` → 判定顺序与改动前逐条一致，只有秒破（`GATE_PRIORITY = 100`）被提前。
- 验证：`.\gradlew build --console=plain -q` → **EXIT=0**；实机部分：用户 2026-09-19 复测
  「星露谷好像没事了」「没事了」→ ①②已通过；②未做，③待实机复测。
- 复测建议：防踢默认开（限制挖掘 8/秒）→ 自动挖矿 + 秒破连续挖，应恢复本来的破坏节奏，
  不再出现「挖一下停一下」；玩家手动挖超过 8 个/秒仍应被限速。
