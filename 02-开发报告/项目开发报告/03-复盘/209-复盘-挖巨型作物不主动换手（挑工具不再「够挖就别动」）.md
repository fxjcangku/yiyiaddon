# 209 · 挖巨型作物不主动换手：挑工具不再「够挖就别动」

- 日期：2026-09-22
- 触发（用户原话）：「可以了！！！！可以挖了！！！菠萝可以了 其他还没种出来 等菜熟了我测试
  **但是没有主动拿背包的工具 或者带有效率的东西挖**」
- 相关：[199](199-复盘-破坏速度属性不是挖不动的判据（巨型菠萝两道客户端闸撤销）.md)（同一格的四道客户端闸）、
  [196](196-复盘-非零硬度承载体用了零硬度秒破（方块闪一下又回来）.md)（非零硬度载体那条路）、
  [204](204-复盘-特殊变种口径扩成动作加手持（按服务器学工具与本服三种巨型预置）.md)（口径指定工具时锁手；
  `effectiveDigSpeed` 由 `1.0-beta2.md` 第 18 条成因三引入，未单独落复盘）

## 一、现象

巨型菠萝能挖掉了（第 199 / 203 条的成果），但模块**从不主动去背包里换工具**：
手里是什么就拿什么挖，带效率附魔的那件一次都没上手。用户的观感是「挖得慢、而且不像在用工具」。

## 二、成因：挑工具那段代码从来没被执行过

`ensureDigTool` 的第一句是一道早退：

```java
float delta = digProgress(mc, pos, state);
if (isWorkable(delta)) return delta;   // 手上这件够挖 → 什么都不动
int slot = bestDigSlot(mc, state);     // 挑工具（含效率附魔）
```

而 `isWorkable` 判的是「估算所需刻数 ≤ `BREAK_MAX_REQUIRED_TICKS`」。本服载体的硬度是 0.4，
**空手**（采掘速度 1.0）每刻进度 0.0833、约 9 刻就能挖掉 —— 远在上限之内，于是：

- 第一句永远成立 → 永远早退 → `bestDigSlot` 一次都没跑；
- 第 18 条成因三专门为效率附魔写的 `effectiveDigSpeed`（本体速度 + 向附魔数据要来的采掘加成）
  因此从没被用上，挑工具「看不见效率附魔」这个问题实际上是**换了种方式继续存在**。

根源是把两个不同的问题混在了一个上限里：

| 问题 | 该用的判据 |
| --- | --- |
| 这一格**能不能**挖（不能就别开永远挖不完的会话） | `BREAK_MAX_REQUIRED_TICKS` |
| 这一格**用哪件**挖（越快越好） | 候选件的 `effectiveDigSpeed` 排序 |

原来的写法用前者顺手把后者的入口也堵上了。

## 三、改动

1. 删掉早退与随之无用的 `isWorkable`（上限只留给「能不能挖」那条路，那条路现在由服务端裁决，
   见第 199 条：客户端估算不再用来拒挖）。
2. 挑选口径改为「**永远拿最快的那件**」：`bestDigSlot` 的比较基准从 `0` 改成**手上这件** ——
   只有**严格更快**才返回槽位，否则返回 -1（什么都不动）。

```java
Inventory inventory = mc.player.getInventory();
float bestSpeed = effectiveDigSpeed(inventory.getItem(inventory.getSelectedSlot()), state);
int best = -1;
for (int slot = 0; slot < StardewInventoryService.MAIN_SLOTS; slot++) {
    float speed = effectiveDigSpeed(inventory.getItem(slot), state);
    if (speed > bestSpeed) { bestSpeed = speed; best = slot; }
}
```

3. 空槽 / 非工具仍按空手（采掘速度 1.0）算 —— 手上是 0 进度的自定义假道具时会被空槽比下去、
   自动退回空手（第 197 / 198 条那条兜底不变）。
4. 口径指定工具时（`specialToolHold != null`）照旧锁手不换，第 204 条约束不受影响。

## 四、为什么"严格更快"就够，不会再抖动

- 比较基准是**手上这件**，不是 0：手里已经是最快的那件时，循环里没有任何一格能比它快 → 返回 -1；
- 同速（含"都只能空手"）不换手 → 不会在两件一样快的工具之间来回倒手；
- 一旦换过去，新手上就是最快的那件，下一轮自然返回 -1 —— **单调收敛，换手最多一次**。

## 五、第二轮：背包里有工具，仍然三格全空手

第一轮改完复测，用户反馈「三次都是用手，可是我的背包有工具」。日志（`run-26.1.2/logs` 19:07 段）
连续三格 `选中槽=4 选中物品=0 minecraft:air`，**全程没有「破坏 换手待同步」** ——
那行只在真的换了手时才打，所以 `bestDigSlot` 每次都返回 -1。

用户当时背包里是这两件（他截图确认）：

| 物品 | 基底 | 对 `chorus_plant`（`mineable/axe`）的客户端速度 |
| --- | --- | --- |
| 金锄 | `minecraft:golden_hoe` | 锄头不匹配 axe 标签 → **1.0** |
| 小破镐（效率 X） | `minecraft:wooden_pickaxe` | 镐子不匹配 axe 标签 → **1.0**，效率因此也不叠加 |

原版 `ItemStack#getDestroySpeed` 只认「这件是这一格的正确工具」才给速度，其余一律 1.0；
而效率附魔的叠加条件是「本体速度 > 1」（`Player#getDestroySpeed` 的 `if (f > 1.0F)`）。
于是「金锄 1.0、效率木镐 1.0、空手 1.0」三者同分，**"严格更快"这条判据永远不成立** ——
工具一件都挑不出来。而服务端认的显然不是客户端这个读数（用户手动拿它们挖更快）。

### 改动：第二条判据「有工具就拿工具」

```java
// ① 算得出更快的：取最快那件（不限是不是工具）
if (speed > fastestSpeed) { fastestSpeed = speed; fastest = slot; continue; }
// ② 算不出快慢、手里不是工具、而这件确实是工具 → 按口径换上去
if (heldIsTool || speed < heldSpeed || !isTool(stack)) continue;
if (tool < 0 || miningEfficiencyBonus(stack) > toolEfficiency) { tool = slot; ... }
return fastest >= 0 ? fastest : tool;
```

- `isTool` 判据 = 带原版 `DataComponents.TOOL` 组件（镐 / 斧 / 锄 / 锹 / 剪），**与客户端算得出多少无关**；
- ② 类里**同分优先带效率附魔的那件**（附魔数据本身读得到），所以「金锄 + 效率 X 木镐」会选中效率木镐；
- 防抖：手里已经是工具时 ② 不触发（不会锄头与镐子互倒）；手里已经最好就返回 -1。

### 教训（补）

4. **"客户端算不出"不等于"用不上"**：服务端常常按自己的口径放行，客户端只是个估算器。
   当某件东西在服务端口径下确实更好、而客户端算不出差别时，判据要退回**物品的客观属性**
   （是不是工具、带不带效率附魔），而不是客户端那个算不出来的数字。
5. **判据要按"玩家会怎么选"设计**：玩家的心智是「有工具就拿工具」，不是「哪件 getDestroySpeed 大」。
   凡是"玩家一眼能看出、代码却算不出"的差别，都该找一条能算的近似判据补上（这里就是 TOOL 组件 + 附魔数据）。

## 六、第三轮：换手成功了，却连换 4 轮后误报「砸不掉」

第二轮改完，换手确实生效了（日志 `选中物品=1 minecraft:wooden_pickaxe` / `iron_axe`），
但紧接着出现新症状：

```
19:13:46 破坏 换手待同步 目标=4805,85,-5598 选中物品=1 minecraft:wooden_pickaxe
19:13:47 破坏 换手待同步 …（同格、同件）
19:13:47 破坏 换手待同步 …
19:13:48 破坏 换手待同步 …
19:13:48 特殊变种砸不掉 ▸ 已停止        ← 轮数用尽，判失败停手
```
19:15:42~44 又重演一次。**同一格连换 4 次手**，然后这一格被判"砸不掉"、停手，
剩下的巨型作物就没人管了 —— 这正是用户看到的「还有一个菠萝没收」的一个来源。

成因：`ensureDigTool` 换手成功后返回 `Float.NaN`，调用方本轮不开挖、等属性同步；
而**任务之间会把借来的手还回去**（`restoreHandNow` / 暂放回收），于是下一轮手上又不是那件工具，
`bestDigSlot` 再挑一次 → 又换 → 又 NaN …… 每轮都在"换手"，一次工都没开，
`BREAK_MAX_ATTEMPTS` 先用尽。

而"等同步"这件事本身已经没有价值：那个读数只用来估算**按住多久**，估算离谱时
`holdTicksFor` 本来就退回固定时长，放不放行由服务端裁决（第 199 条已经撤销"估算用来拒挖"）。

### 改动

换手后**本轮直接开挖**：

```java
int slot = bestDigSlot(mc, state);
if (!holdDigSlot(mc, slot)) return digProgress(mc, pos, state);
return digProgress(mc, pos, state);   // 不再返回 NaN 空转一轮
```

- `Float.NaN` 分支与「换手待同步」日志一并删除（不留死代码）；
- 顺序安全：换手包（选中槽切换 / 热键栏交换）与随后的 START 走同一条连接、按序到达，
  `syncHeldSlot` 还会在发 START 前把当前选中槽再声明一次。

### 教训（再补）

6. **"等一等"这种自我延迟，在多轮重试的循环里会变成致命循环**：一轮空转本身无害，
   但循环体里有"归还资源"的动作时，空转就会被无限延长，最后把重试预算耗光、误报成设备故障。
   凡是"下一轮再做"的写法，都要先问一句：**下一轮开始时，前提条件还在吗？**
7. 估算精度不值得用一次开工机会去换：客户端读数只影响"按多久"，服务端才是权威。
   把精度当成败判据（拒挖）、为了精度推迟开工（空转），都是把辅助量当成了主判据。

## 七、验证

- `GetDiagnostics`（语言服务器）：该文件 0 诊断（无编译错误 / 无未使用符号）。
- **待实机复测**（用户当晚）：进服后让模块收地上的巨型菠萝，日志应出现
  `破坏 开始挖掘 … 选中物品=<背包里最快的那件>`，而不是 `选中物品=空` / `选中物品=…apple`。

## 六、教训

1. **"早退"是隐形的一刀**：`if (够用) return;` 这类优化会把后面整段功能变成死代码，
   而且从日志上看不出来（没有报错、没有跳过记录）。挑工具要真的生效，
   必须让它**每格都被走到**，而不是"只在挖不动时兜底"。
2. **一个上限不该管两件事**：`BREAK_MAX_REQUIRED_TICKS` 是"值不值得挖"的闸，
   被顺手用成"值不值得换工具"，结果两者一起失效。判据按问题分开，注释里写明它不负责什么。
3. 「能挖」与「挖得好」是两个验收口径：第 199 条验收的是前者（方块掉了），
   用户复测时看的是后者（手里拿了什么）。**验收时要问一句"玩家会怎么看这件事"**。
