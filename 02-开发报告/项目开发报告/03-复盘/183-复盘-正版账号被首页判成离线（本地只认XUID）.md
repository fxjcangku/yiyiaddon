# 183 - 复盘：正版账号被首页判成离线（本地只认 XUID，而这个环境恒无 XUID）

日期：2026-09-21
分支：`master` + `port/26.2`
验证：两线 `compileJava` EXIT=0；**线上库已取证**；实机显示待玩家重进游戏确认

## 一、用户反馈与证据

用户原话：「我明明正版号给我判成离线了 好多个号都这样」，截图是游戏内首页账户条：
`离线：9cbf1d2e`（红色）。

查线上 D1（`yiyiaddon-users`）最近 30 条记录：

| name | uuid | UUID 版本 | xuid | gamertag | is_premium（后端口径） |
| --- | --- | --- | --- | --- | --- |
| 9cbf1d2e | `ed3b6780-8437-4fd8-99c6-…` | **v4** | **NULL** | NULL | **1** |
| Phoera1n | `3a943890-e0ec-4495-…` | v4 | NULL | NULL | 1 |
| TureCJ | `efc1f1b9-5a74-40af-…` | v4 | NULL | NULL | 1 |
| Fxx1shy | `3dec5c52-5c0b-4269-…` | v4 | NULL | NULL | 1 |
| wosinima | `00000000-0000-3008-…` | v3 | NULL | NULL | 0 |

两条结论直接落地：

1. **后端判得是对的**：`9cbf1d2e` 等号在库里都是 `is_premium = 1`（`resolvePremium` 按名字查 Mojang 档案
   得到的结果），后台面板显示的也是正版。
2. **错的只有客户端首页**：`ClientIdentity.premium()` 当时只有两条判据（XUID 非空 / 开发环境装了 DevAuth），
   而这些会话的 **XUID 恒为空**（`users.xuid` 整列都是 NULL）—— 于是所有正版号在首页一律显示「离线」。

## 二、根因

- 该运行环境（第三方启动器链路）**不把 XUID 放进会话属性**，`User#getXuid()` 永远为空；
  旧口径把「没有 XUID」直接当成「不是正版」，于是「好多个号都这样」是必然结果，不是个例。
- 同一批号的会话 UUID 全是 **v4**（正版随机分配），而真正的离线会话是 **v3**（用户名 MD5 派生，
  库里 `wosinima` 那条 `00000000-0000-3008-…` 就是）。判别信息一直在手边，只是没用上。

## 三、改法（两层，都不新增网络请求）

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| 本地判据补一条 | `platform/ClientIdentity.java` | `premium()` 增加 `hasSessionCredentials()`：**会话 UUID 为 v4 且 access token 有效**（`0` / `null` / 空串 / 短串都不算）即算正版。判据与 `AccountChecker` 的两条本地特征同源 |
| 首页采纳后端结论 | `service/HomeStats.java`、`service/RegisterService.java` | `/api/register` 的 `is_premium`（后端按 Mojang 档案核验，与后台面板同一口径）回填进 `premiumVerified`；`premium()` = 后端核验为正版 **或** 本地判据成立 |

两条设计口径：

- **只升不降**：`premiumVerified` 仅在为真时置位、断线复位。后端在 Mojang 暂时不可达时也会保留既有结论、
  绝不把已确认正版降级（`worker.js` 的 `resolvePremium`），客户端同样不让一次查询失败把界面上的「正版」
  打回「离线」。
- **本地判据按「像正版就算正版」收口**：界面只有正版 / 离线两档，没有「无法确定」这个选项，
  因此宁可在极少数场景下把伪造 v4 的会话算成正版，也不再出现「正版被显示成离线」。
  最终口径仍以后端为准。

顺带的影响面：`ReportPayload` 的 `gamertag` 字段是「本地判正版才填」，之前一直为空，改后对正版会话会正常上报
（库里 `gamertag` 列因此有了内容）。

## 四、没改的地方（说明理由）

- `AccountChecker`（自动登入模块的「账号检测」播报）保持原样：它对「v4 但无 XUID」的结论是
  **「无法确定」**而不是「离线」，不属于本次误判；且它只用于播报，不参与登录决策。
- 后端 `resolvePremium` 不动：它已经先看 XUID、再按名字查 Mojang（含镜像回退），
  且对「查询失败」与「确认离线」区分对待，口径正确。

## 五、实机验证（2026-09-21 19:58，用户用 26.1.2 个人版进服）

查线上 `users`（同一晚 19:47~19:58 的记录）：

| 玩家名 | UUID 版本 | xuid | gamertag | is_premium |
| --- | --- | --- | --- | --- |
| PPJ28（用户测试号，装了新包） | v4 | NULL | **true** | **1** |
| Estrela03 / Phoera1n / ZZArvin / Fxx1shy / 9cbf1d2e | v4 | NULL | false | 1 |
| wosinima / 488733225 | **v3** | NULL | false | **0** |

三条结论：

- v4 会话全部 `is_premium = 1`，且 `xuid` 依旧全为 NULL —— 说明认出来的不是 XUID，正是本次补的判据在起作用；
- v3 会话（离线派生 UUID）仍然 `is_premium = 0`，**没有把离线会话洗成正版**；
- `gamertag` 只有 PPJ28 为 true，因为它是唯一装了新包的客户端（本地判据成立才会填这个字段），
  其余玩家还在用旧的发布包 —— 因此这一列可以当「客户端是否已升级到本修复」的旁证。
