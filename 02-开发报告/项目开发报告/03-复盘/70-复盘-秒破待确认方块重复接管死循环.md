# 70 - 复盘：「一直不挖前面的方块」——秒破对待确认方块的重复接管死循环

- 日期：2026-09-17
- 触发：用户实机「一直不挖前面的方块」（上一轮同现象的延续：卸货 → RTP 后变慢、连锁无提示）
- 定位方式：TRAE-debugger 插桩取证（会话 `mining-stall-after-rtp`），非静态猜测
- 涉及文件：`feature/mining/fastbreak/MiningFastBreakController.java`
- 验证：`./gradlew build --console=plain` → **BUILD SUCCESSFUL（EXIT=0）**；**post-fix 实机待用户确认**

## 1. 证据（pre-fix，约 103 秒窗口，1218 条上报）

裁决计数：

| 事件 | 次数 |
| --- | --- |
| `FastBreak.start begin` | **294**（≈2.9 次/秒） |
| `FastBreak.start cooldown` | 178 |
| `FastBreak.start same-target` | 145 |
| `VeinMiner.root root-scan` | 131 |
| `FastBreak.mineRequested accepted` | 13 |
| `VeinMiner.resume chain-finished` | 5 |

心跳（连续 5 秒完全不变）：

- `AutoMinerModule`：`state=MINING`、`miningActive=true`、`pathing=true`、`fbActive=false`
- `FastBreak.tick`：`ready=true`、`phase=IDLE`、**`pending=1`**、`retries=0`、`blocked=0`、`pos=null`
- `VeinMiner.tick`：`queue=0`、`veinActive=false`、`suspended=false`、`lastBroken` **每 ~6 秒才换一次**

排除掉的假设：状态机异常（C）、秒破未启动（D）、连锁逻辑故障（E —— 131 次扫根只有 5 次成队，
是因为多数矿脉只有 1 块 < `MIN_CHAIN_BLOCKS=2`，属设计行为）。

## 2. 根因

`begin` 每秒 ~3 次而 `pending` 恒为 1、`retries`/`blocked` 恒为 0 —— 只可能是**同一个方块被反复
`begin → STOP → handOffToPending`**，而 [handOffToPending](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/mining/fastbreak/MiningFastBreakController.java#L608)
旧实现无条件 `pending.put(pos.asLong(), new PendingBreak(..., player.tickCount, ...))`，
**每次覆盖都刷新 `sentTick`**。后果链：

1. `sweepPending` 的超时判据 `tickCount - sentTick > STOP_RESEND_AFTER_TICKS(20)` 永远命中不了
   → 既不排进重试、也不拉黑，**失败永远不被发现**；
2. 与此同时我们每 ≤20 刻对同一方块再发一次 START，而服务端破坏进度只记**一个** `destroyBlockPos`
   → 进度被我们自己反复清零；
3. 于是这块「谁都挖不烂」：秒破在空转，原版也拿不到连续进度，`lastBroken` 只能靠偶发成功推进
   —— 用户看到的就是「一直不挖前面的方块」。

## 3. 修复（两处，最小改动）

| # | 位置 | 改动 |
| --- | --- | --- |
| 1 | `handOffToPending` | 同 `pos` 已在 `pending` 中时**不覆盖**，保留最早那条的 `sentTick`（`MAX_PENDING` 安全阀只在真正插入时判），使超时/重试/拉黑链路如实生效 |
| 2 | `start()` / `mineRequested()` | 目标已在 `pending` 中 → **不接管**（`PASS` / 拒绝派发 `pending-await`），放行原版把它挖掉；原版挖掉后 `sweepPending` 下一 tick 认账并写入 `lastBroken` |

设计要点：修复 2 不会造成「永久放行」——`pending` 里的方块若在 20 刻内没被任何人破坏，仍会走
重试（≤3 次）→ 拉黑 600 刻 → 交原版，链路与旧的「挖不动让位」完全一致。

## 4. 待实机验证项（post-fix，日志对比）

| 指标 | pre-fix | 期望 post-fix |
