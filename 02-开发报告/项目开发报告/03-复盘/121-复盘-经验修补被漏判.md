# 121-复盘-经验修补被漏判（带经验修补的铲子被判「没有经验修补」）

日期：2026-09-19
项目：yiyiaddon（新项目，Fabric 26.1.2 客户端模组）
旧项目对应物：`AutoMinerModule.hasEnchant`（旧 `:927-942`）→ 本项目 `MiningStateMachine#hasMending` / `MiningContainer#hasMending`（本轮把两处私有实现合并到 `platform/identity/ItemIdentifier`）
用户原话：「[自动挖矿]⚠ 铁锹 没有经验修补 ▸ 不回去挂机点修复，继续挖矿 我的包里明明有经验修补的铲子」

---

## 一、取证：判据为什么会在带附魔的工具上判成「没有」

旧写法（`MiningStateMachine:2928-2940`、`MiningContainer:303-315` 两份私有实现，完全相同）：

```java
var lookup = mc.level.registryAccess().lookupOrThrow(Registries.ENCHANTMENT);
var holder = lookup.get(Enchantments.MENDING).orElse(null);   // 从注册表取 minecraft:mending 的 holder
return holder != null && enchantments.getLevel(holder) > 0;    // 拿这个 holder 去查等级
```

问题出在「**拿注册表的 holder 去查物品上的附魔表**」这条路依赖 holder 的**实例同一性**：

| 事实 | 证据 |
| --- | --- |
| 物品附魔表是 `Object2IntOpenHashMap<Holder<Enchantment>>` | `ItemEnchantments:37` + `:50 getLevel(Holder)` → `enchantments.getInt(enchantment)` |
| `Holder.Reference` **没有覆写** `equals/hashCode` → 走引用相等 | `net/minecraft/core/Holder.java`（`Reference` 内只有 `is(ResourceKey)` 等谓词，无 `equals`） |
| `Holder#is(ResourceKey)` 自身也是 key 的引用比较（`this.key() == key`） | `Holder.java:179-182` |

于是只要物品上那条附魔的 holder **不是注册表里那一个实例**，`getLevel` 就查成 0 级 → 判成「没有经验修补」。
两种常见触发：

1. **服务器用数据包 / 插件给的自定义「经验修补」**（id 形如 `xxx:mending` 或别的名字，显示名照抄「经验修补」）——
   玩家看到的是「经验修补」，模块去查 `minecraft:mending` 自然查不到；
2. **内联附魔**（`Holder.Direct`，附魔数据直接写在物品上，没有注册表 key）——实例天然对不上，连 key 都没有。

工具提示仍然正常显示「经验修补」，因为 tooltip 是遍历物品**自己**的附魔条目渲染的（`ItemEnchantments#addToTooltip`）——
所以「玩家看得见、模块读不到」这种现象只可能出在上面两条路上，与物品本身无关。

## 二、修复：按物品自己的附魔条目比对（不再依赖注册表 holder 实例）

新增唯一实现 `platform/identity/ItemIdentifier#hasMending(ItemStack)`（该类本来就是物品识别的落点，
它的 `collectEnchantments` 已经在用 `unwrapKey().identifier()` 取附魔 id）：

| 判据 | 覆盖 |
| --- | --- |
| `holder.is(Enchantments.MENDING)` | 原版 `minecraft:mending`（`ResourceKey` 是 interned 的，引用比较成立） |
| `unwrapKey().identifier().getPath().equals("mending")` | 自定义命名空间的同名附魔（`xxx:mending`） |
| 显示名 ∈ {经验修补, Mending} | 连 key 都取不到的内联附魔，按玩家看到的名字认 |

同时看 `minecraft:enchantments` 与 `minecraft:stored_enchantments`（与 `extractEnchantments` 口径一致）。

调用点全部改为该实现，删掉两份私有重复：

| 文件 | 改动 |
| --- | --- |
| `platform/identity/ItemIdentifier.java` | 新增 `hasMending` + `isMending` + `MENDING_NAMES`（`:313-362`）；新增 `Enchantments` / `Set` import |
| `feature/mining/fsm/MiningStateMachine.java` | 删除私有 `hasMending`，5 处调用改 `ItemIdentifier.hasMending(...)`（`:2191 / :2203 / :2954 / :3015 / :3024`）；删掉 `Enchantments` / `ItemEnchantments` / `Registries` 三个不再使用的 import；新增 `ItemIdentifier` import |
| `feature/mining/service/MiningContainer.java` | 删除私有 `hasMending`，`shouldKeep` 改 `ItemIdentifier.hasMending(stack)`（`:290`）；删掉 `Enchantments` / `ItemEnchantments` / `Registries` 三个不再使用的 import；新增 `ItemIdentifier` import |

修复后的行为：带经验修补（含自定义 / 内联「经验修补」）的工具低于耐久阈值时走
优先级 2a → 回去挂机点联动杀戮光环修复；「没有经验修补」那条提示只在**真的没有任何经验修补附魔**时出现。

## 四、收尾：被提示的其实是一把僵尸掉的烂铁铲（用户澄清）+ 只扫镐子

用户事后澄清：「对不起 原来我刚刚背包里有一把 烂掉的铁铲 打僵尸掉的」（截图：`minecraft:iron_shovel`，
耐久 7/250，无附魔）。

也就是说**本轮最初的「漏判」其实不存在** —— 被提示的那件就是真没附魔的工具，提示按设计正确；
用户那把带经验修补的下界合金锹剩余 2019 耐久，压根没进流程。121 的改动照旧保留（把两处「按注册表
holder 查等级」的脆弱写法合并成 `ItemIdentifier.hasMending`，对原版 `minecraft:mending` 行为不变）。

但顺着这件事暴露了一个**连带的真问题**，本轮一并修掉：

`handleUnrepairableTool()` 原先调 `findDamagedToolSlot(false)`，而这条「不要求经验修补」的路
取的是「背包里剩余耐久最低的**任意**工具」（`isRepairableTool` 含镐/铲/斧/锄/剑）——
一把僵尸掉的烂铲子剩余耐久天然最低，会**顶掉**真正受损的镐子，于是：

- 刷出与挖矿无关的铲 / 斧 / 锄 / 剑的「没有经验修补」噪音；
- 更严重的是让「镐子修不了 → 换镐 / 停机」那条判据失效（挑中的是铲子，走的是「继续挖矿」分支）。

改法（用户裁定「只对镐提示」）：

| 位置 | 改动 |
| --- | --- |
| `MiningStateMachine#findDamagedToolSlot(boolean)` | 单件判据抽成新方法 `isDamagedToolCandidate(stack, requireMending)`；`requireMending == true`（修复/换槽）沿用「可修复工具 + 带经验修补」，`requireMending == false`（提示扫描）改为只认「镐子 + 无经验修补」 |
| `MiningStateMachine#handleUnrepairableTool()` | 删除已成死代码的 `if (!isPickaxe(tool))` 分支（非镐工具不再进这个方法）；注释与记账口径同步改为「受损镐子」 |

即：剑 / 铲 / 斧 / 锄不带经验修补不再有任何播报，也不再参与受损工具的挑选。

## 五、同类隐患（**未改，等用户发话**）

同一个「从注册表取 holder 再查等级」的写法还有两处，影响的是别的附魔：

| 位置 | 用途 |
| --- | --- |
| `feature/mining/AutoMinerModule.java:1582-1593` `hasEnchant(stack, key)` | 挖掘时的精准采集 / 时运判定、目标矿分类 |
| `feature/autofarm/task/FortuneTool.java:119` | 自动农场的时运工具判定 |

同样的坑：服务器给的自定义 / 内联附魔会一律判成 0 级。改法与本次一致（改成按附魔条目比对），
但会动到挖掘分类与农场逻辑，所以本轮没有擅自改 —— 需要改说一声。

## 六、构建与验证

- `.\gradlew.bat build --console=plain` → **EXIT=0**（2026-09-19，本机；第四节改动后再次验证）。
- **未实机**。实机验收项：
  1. 背包里同时有「僵尸掉的烂铲子 + 一把无附魔受损镐」→ 提示的应是**镐**，不再提铲子；
  2. 该镐且背包无其余镐 → 停机；背包还有别的镐 → 继续挖矿；
  3. 只有烂铲子、没有受损镐 → 完全无提示、不刷屏；
  4. 带经验修补（含自定义 / 内联「经验修补」）的工具低于耐久阈值 → 走「回挂机点修复」（121 回归项）。
