## 一、事件

用户在自己的星露谷服（jmy.seasonmc.xyz，26.1.2 开发客户端）实机反馈三件事：

1. 大白菜熟了、模块一直显示「正在收获」，地里一动不动，收不掉；

「主手非空 + 热键栏 9 格全满 + 副手本来就空」，`prepareHarvestHand()` 直接落到副手兜底那条路。

### 2. 为什么副手收不掉

`hand=OFF_HAND` 且副手为空时，服务端对这次方块交互的处理与主手不一条路（Bukkit 侧对
「空副手右键」的事件派发与主手不同，各服插件普遍只认主手空手右键）。原版客户端手动收菜
永远发 `MAIN_HAND`，所以「空手右键」的通用口径就是**主手空手**，副手只是本模块自己的省事写法。

### 3. 「ESP 绿线」是什么

[StardewRenderState](../../../yiyiaddon/src/main/java/com/yiyiaddon/feature/stardew/render/StardewRenderState.java)
里 `TARGET_SIDE` / `TARGET_LINE` / `TARGET_TRACER` 都是 `0x00FF64`（绿），
`renderTargetLine` 画的是「玩家眼睛 → 当前任务目标格顶部中心」的射线：

```java
renderer.line(eye.x, eye.y, eye.z, target.getX() + 0.5, target.getY() + 1.0, target.getZ() + 0.5,
    color.argb(), LINE_THICKNESS);
```

截图那条绿线（连同目标格上的绿框）就是**当前任务的指示器**，指向的正是收不掉的那一格。
它不是另一个功能，是同一个故障的指示器：目标认出来了、包也发了，服务端不认。

## 三、改动

只动执行器与状态机两处，不改任何资源识别 / 世界语义判据（多服适配面不动）。

### 1. 取手顺序改为主手优先（`StardewFarmExecutor.prepareHarvestHand`）

原顺序「主手空 → 空热键栏槽 → 空副手 → 暂放副手」在热键栏满时直接退到副手，
于是在只认主手的服上永远收不掉。新顺序在副手之前插入「腾主手」：

```
主手空 → 空热键栏槽 → 【新】把当前手持物暂放进背包空格腾出空主手 → 空副手 → 暂放副手
```

新增 `parkMainHand` / `restoreParkedMainHand`：用「背包槽 ↔ 选中快捷栏槽」的 SWAP
（与 `holdSeed` 把背包种子换进主手是同一个原版动作，方向相反），选中槽原地变空、
物品落到靠后的背包空格，不需要切槽；换回前先把选中槽切回当初那一格，并核对那一格
仍是当初暂放的东西，玩家中途动过就不碰（与 `parkOffhand` 同一口径）。

`restoreHandNow()` 里两处还原都提到玩家判空之前（两个还原方法都先清状态再动手，
避免玩家不在时残留暂放状态带到下一轮）。

### 2. 收割连续失败不再原地秒级刷包（`StardewCoordinator.verify`）

原来只有 `CLEAR_JUNK` 在 `retryCount >= MAX_RETRY` 时给目标格一个 10 秒退避窗口；
`HARVEST` 没有，于是「重试 3 次 → replan（retryCount 归零）→ 又挑中同一格」无限循环，
观感就是一秒一次右键刷一整分钟。现在 `HARVEST` 同样退避 10 秒（`NAVIGATION_BLOCK_RETRY_MS`），
窗口内先去做别的格，到期再回来试一次。

### 3. 取证埋点（`doHarvest` 日志）

```
[星露谷] 收割交互 手=… 手持=… 另一手=… 目标=… 方块 … · 实体 …
```

## 五、未决：被洒水器卡住

本次**没有**为这一条改代码，原因是没有取证到机制：

- 已排除「洒水器所在格是坑」这一最直观的解释：种植盆是 `note_block`（有碰撞）在 y=84、
  作物是 `tripwire`（无碰撞）在 y=85，玩家站面是盆顶 y=85；洒水器绑定点也在 y=85，
  该格方块是空气（本体由展示实体渲染，展示实体无碰撞、不参与玩家移动）。
- 剩余两条候选，都需要一次带时间戳的复现来定：
  1. `StardewDropCollector.nudgeTowardDrop`：掉落物比脚高 0.5 以上时按住「前进 + 跳」，
     若掉落物落在盆顶/洒水器那一侧，表现为贴着方块边反复起跳；
  2. Baritone `GoalNear` 的中间步穿过洒水器所在格后需要跨一格。

## 六、追加（同一轮实机反馈）：洒水器误判「已被挖掉」

用户把洒水器挖掉又放回去，面板仍每轮刷「洒水器已被挖掉 · 已停止」。

根因在 [StardewFarmReporter.watchPointBlock](../../../yiyiaddon/src/main/java/com/yiyiaddon/feature/stardew/task/StardewFarmReporter.java#L94-L98)：
点位巡检只按「该坐标方块是空气」判被挖掉。但本服洒水器本体是**展示实体**、所在格本来就是空气
（与绑定 `SprinklerWorldBinding.capture` 允许空气载体是同一个事实），于是绑定完成的那一刻就满足
`vanished`，稳定 40 tick（`LOST_CONFIRM_TICKS`）后 `critical` 播报并停机；`reset()`（模块每次启停）
会清掉「已播报」记录，再启 2 秒后又报一次 —— 观感就是刷屏。

改法与前面三处同源、共用同一份判据：

```java
boolean vanished = state.isAir()
    && !(type == StardewPointType.SPRINKLER && SprinklerWorldBinding.displayCarrierAt(point.pos()));
```

「空气 + 该格挂着展示实体」= 载体还在，不算被挖掉；真正挖走（展示实体也没了）照旧报警停机。

## 七、追加：菠萝「收获学习」未确认的文案

同一轮日志里菠萝连续三次「收获学习未确认 … 成熟植株状态未发生可验证变化」，
用户以为作物熟了收不掉。其实：

```
[01:37:30] 收获学习验证 作物=pineapple 成熟阶段=stage_2 交互包已发=true
           收获后[状态=GROWING 阶段=stage_2] → 结论=未确认：世界状态无变化
```

`learningMatureStage` 取的是**该格当前阶段**（`StardewFarmExecutor` 353 行），stage_1/2/3 都不是
可收获阶段（那时菠萝刚种下去，01:37:27 还在播种），右键世界当然没变化。判定本身正确，
错的只是文案把「被试探的阶段」说成了「成熟植株」。文案改为：

```
该阶段空手右键后世界没有任何变化（不是可收获阶段，或服务端另有收法）
```

**补充（用户追问「可是已经可以正常收取菠萝了」后回查日志）**：学习其实**已经成功确认**，
就在同一份日志的 90 秒之后：

```
[01:39:09] 收获学习验证 作物=pineapple 成熟阶段=stage_4 交互包已发=true
           收获前[身份=customcrops:pineapple_stage_4 ...] 收获后[状态=EMPTY 阶段=null] 盆保留=true 掉落=2
           → 结论=一次性（已确认）
[01:39:09] [CHAT] 收获规则已确认 ▸ 菠萝，一次性补种
```

即：stage_4 才是成熟阶段，判为「一次性补种」并落库。前面三次「未确认」是探测未成熟阶段，
不是失败。唯一成功文案就是这行，代码里没有「学习完毕」这个字面词，为此把成功文案补上成熟阶段：

```
收获规则已确认 ▸ 菠萝（成熟阶段 stage_4），一次性补种
```
