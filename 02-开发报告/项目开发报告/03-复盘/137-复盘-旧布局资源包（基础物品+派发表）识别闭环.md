## 二、取证（先取证再动手，第 167 条）

### 2.1 包本体

`run-26.1.2/yiyiaddon_resourcepacks/jmy.seasonmc.xyz_25565.zip`
（3,451,122 字节 / 2642 条目，SHA-1 `c990fc4163e1ca8e89430f9584befceb0d0bd4e7`，Java 可完整解压）
与 `run-26.2` 缓存、与客户端原版 `downloads/1deb8ae7-…/d69238f2-…/c990fc41…` **字节相同** ——
服务器没有按客户端版本换包，跨版本进服不是成因。

包内结构：

| 路径 | 条数 |
| --- | --- |
| `assets/customcrops/models/item/**` | 148（12 种作物种子 + 阶段 + 盆/肥料/水壶/洒水器…） |
| `assets/customcrops/textures/**` | 277 |
| `assets/customcrops/items/**` | **0** |
| `assets/customcrops/models/block/**`、`lang/**` | 0 |

`pack.mcmeta`：`pack_format 75` + `supported_formats [32,9999]` + 14 个 `overlays`
（`ia_overlay_1_21_6_plus`、`ia_overlay_modern_atlas` 等，客户端按自身格式挑分支，本包是"一包多版本"）。

### 2.2 这个包到底怎么定义物品（关键证据）

客户端实际生效的 `ia_overlay_1_21_6_plus` 层里，物品定义**不在** `customcrops:items/`，
而是挂在原版基础物品上按 `custom_model_data` 阈值派发：

```
assets/minecraft/items/paper.json               model.type = range_dispatch(property=custom_model_data)
  10548 → customcrops:item/basics/dry_pot        10579 → customcrops:item/crops/corn/corn_seeds
  10611 → customcrops:item/fertilizers/speed_grow_1   10634 → customcrops:item/sprinklers/sprinkler_1 …
assets/minecraft/items/apple.json               10007 → customcrops:item/crops/corn/corn
assets/minecraft/items/diamond_horse_armor.json 10000 → customcrops:item/wateringcans/watering_can_1
```

贴图经 `ia_overlay_modern_atlas/assets/minecraft/atlases/items.json` 的
`{"type":"single","resource":"customcrops:item/basics/pot","sprite":"ia:50"}` 落到 `ia:` 精灵。
即：**游戏里能正常显示，但整包没有一条 `customcrops:items/*.json`**。

### 2.3 判定链路

- 扫描层 `StardewResourceScanner` 只按命名空间 `customcrops` 收 `items/`、`models/item/`、`models/block/`；
- 计数层 `ResourceExtractionService.profileCounts()` 只统计 `Kind.ITEM_DEF`（`items/*.json`）；
- 于是扫到 148 条 `models/item/**`、0 条物品定义 → `NO_CONTENT`，与日志逐字吻合。

## 四、改动清单（只改必要处，第 192 条）

### 4.1 新增（1 个类）

`platform/resource/ItemModelDispatchIndex.java` —— 派发表读取层（唯一事实来源）：

- 用 `ResourceManager.listPacks()` 倒序读生效资源包（overlays 由原版 `CompositePackResources` 合并，
  读到的就是客户端真正使用的那份），**两种布局都读，灌进同一张表**：
  1. 新式（1.21.4+ 文件式物品定义）：`assets/<ns>/items/<载体>.json` 的 `range_dispatch`
     —— 上面 2.2 的真机样例；
  2. 旧式（旧版 ItemsAdder / 手工包）：`assets/<ns>/models/item/<载体>.json` 的
     `overrides[].predicate.custom_model_data` —— 字段形态已用 4 个真实包核过（见 5.4）。
  同一包内新式先读、同键"先到先占"，因此两种写法并存时以新式为准；跨资源包同样是高优先级先占；
- 只认有据可查的两种写法：`model.type=model`（直接模型）与
  `range_dispatch(property=custom_model_data, index=0)`（阈值派发）；其它类型一律跳过，不猜结构；
  旧式的非 `custom_model_data` 谓词（`damage` / `trim_type` / `blocking` / `pull*` / `firework` …）同样跳过；
- 模型引用不带命名空间时按原版语义补成"文件所在命名空间"（真机取证：`2d2l.cn` 的表里写
  `"model":"gui/icons/invisible_botton"`）；
- 产出三张表：`基础物品 → 直接模型`、`基础物品 → 升序阈值表`、`模型键 → (基础物品, 阈值)`，
  并按命名空间分组供扫描层取用；文件 id（`minecraft:items/paper.json`）一律**归一化成物品 id**
  （`minecraft:paper`）再入表——先前直接用文件 id，导致兜底预览与运行期物品匹配双双落空（见 5.2）；
- 边界：单次最多 20000 个文件、单文件 256 KB（旧式 `overrides` 随载体承载物品数线性增长，
  真机 221 条目 ≈ 30–40 KB，故由 64 KB 上调），超限即跳过；结果缓存，资源重载时由资源生命周期服务
  调用 `invalidate()` 作废；单次构建打一条 INFO 日志（文件数 / 模型数 / 耗时 / 各跳过计数 / 旧式条目数）。

### 4.2 既有文件（9 个，均为最小改动）

| 文件 | 改动 |
| --- | --- |
| `feature/stardew/profile/StardewResourceScanner.java` | 新增 `Kind.DISPATCH` 来源与 `scanDispatch()`（逻辑名取模型键末段，如 `customcrops:item/crops/corn/corn_seeds` → `corn_seeds`）；新增 `dispatch()` / `logicalItem()`；同一模型键与 `models/item/**` 撞车时**用派发条目覆盖**（`LinkedHashMap` 覆盖保留原位置） |
| `feature/stardew/profile/StardewResourceIndex.java` | `feedModel()` 允许派发模型作物品键（**不提前返回**：这类模型路径同时是世界识别模型）；新增公开判据 `logicalCategoryOf()` 与 `hasLegalSerial()`；编号家族的 `_item` 零件模型剥后缀归并到同一对象并**优先作物品键、不再充当世界模型**；新增文档化标准作物名兜底（12 种，含 `redpacket → 摇钱树`，优先级最低） |
| `service/resourcepack/ResourceExtractionService.java` | 计数改用 `StardewResourceIndex.logicalCategoryOf()`（与索引层同源，第 169 条）；`noContentReport()` 统计口径同步；`onReloadApplied()` 作废派发表缓存 |
| `feature/stardew/selector/StardewPreview.java` | `items/` 定义不存在时，用「基础物品 + `custom_model_data`」构造预览栈（与服务端同一条渲染链），取不到才显示缺失提示 |
| `feature/stardew/service/StardewInventoryService.java` | `matchesModel()` 增加第二条判据（派发表反查）；新增 `resolvedModelOf()`；`StardewToolDefinition.matchesByModel()` 改为委托它 |
| `feature/stardew/profile/StardewCropNameStore.java` | `identityOf()` 增加派发表来源（压平为 `customcrops:corn_seeds` 再走既有身份派生规则），使"服务器下发名 → 作物中文名"这条学习链在旧布局服务器上重新生效 |
| `feature/stardew/command/StardewQuerySupport.java` | `诊断` 的扫描统计新增「派发 N 条」计数（验收用，属留档观测） |
| `ui/render/ItemIconCache.java` | 缓存键补上 `custom_model_data` 第 0 个值（原键只有「物品 id + `item_model`」，见 5.2） |

### 4.3 关键口径

- **唯一判据**：计数与建档同走 `logicalCategoryOf()` —— `items/` 物品定义与派发模型都算；
  编号家族（水壶 / 洒水器）必须带合法序号，否则不构成逻辑对象；
  盆豁免（无序号盆本就归一到 `dry_pot_-1`）。
  依据：真机包把 `sprinkler_1` 与 `sprinkler_1_item` **一起派发**，不过滤就会聚合出 `sprinkler_-1` 这种伪条目。
- **匹配三条判据**（顺序固定）：身份键（`.id`）→ `item_model` 组件 → 派发表反查。
- **预览两条路**：`items/` 定义（原有）→ 派发表「基础物品 + 阈值」（新增）。
- **不改** `BlockStateModelResolver.deriveIdentityPath()`：它是世界识别与阶段清单的同源规则，
  派发模型一律先压平成扁平身份再进这条规则。

## 五、实机验证（2026-09-19 夜，jmy.seasonmc.xyz，开发客户端 26.1.2）

### 5.1 第一轮：能力闭环成立

`.\gradlew.bat build --console=plain -q` → **EXIT=0**；`runClient` 进服触发检测后，日志原文：

```
[星露谷农场] 资源档案已建立
作物 12　种植盆 1　肥料 12
药剂 3　水壶 4　洒水器 3
温室玻璃 1
[派发表] 扫描接入 命名空间=customcrops 派发模型=146 已有条目=148 → 新增派发条目 146
```

即静态复算的 36 个逻辑对象与实机完全一致，与 §2.3 的「0 条物品定义」形成闭环。

### 5.2 连带缺陷（就在这一轮暴露出来，均已修）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 派发条目**全被挡掉**（扫到 148 条又退化成 0 条） | 包里 `models/item/**` 与派发模型**是同一批模型键**，扫描按 id 去重"先到先占"，146 条派发全被前面收下的条目占了位 | 同一模型键已被 `models/item/**` 收下（且非 `items/` 物品定义、非方块模型）时，用派发条目覆盖 |
| 选择器**每行图标都一样** | `ItemIconCache` 缓存键只算「物品 id + `item_model`」，漏了 `custom_model_data`；该布局整服共用同一载体（真机：`minecraft:paper` 一张表承载 221 个条目、`minecraft:apple` 承载全部作物产物），于是所有物品挤进一个键，除首个外全画成别人的贴图 | 缓存键纳入 `custom_model_data` 第 0 个值 |
| 洒水器取到 **3D 方块模型** | `sprinkler_1` 是带 `elements` 的方块模型，`sprinkler_1_item` 才是 `item/generated` 背包贴图，索引按"排除 `_item`"反而取了前者 | `<家族>_N_item` 剥后缀归并到同一对象，并**优先作物品键**、不再充当世界模型（3D 那个仍留给世界识别） |
| 预览报"缺失物品模型"、库存里有种子也认不出 | 派发表里存的是**文件 id**（`minecraft:items/paper.json`），而预览/匹配查的是**物品 id**（`minecraft:paper`） | 读取时按 `FileToIdConverter` 同规则归一化；这条同时修好了运行期物品匹配 |

### 5.3 第二轮：用户实机确认

用户实机结论（逐句取证）：图标全部正确（种子 / 产物 / 肥料 / 洒水器 / 水壶各行不同，洒水器为 2D 背包图）；
洒水器、水壶、盆、肥料行显示中文；作物与种子行显示中文名 —— **"可以了"**。

中文名来源说明：该包 `lang/` 为 0 个文件，中文名来自「服务器下发物品名自动学名」这条既有链路
（打开选择器即学一遍），并新增**文档化标准作物名兜底**（12 种，优先级最低，任何学到的真名都会覆盖）；
`redpacket → 摇钱树` 已在该服由用户核对确认。

### 5.4 追加能力：旧式 `overrides` 布局（用户要求"以防万一"）

原实现只读 1.21.4+ 的 `items/*.json`；若遇到**旧版 ItemsAdder / 手工包**把派发写在
`models/item/<载体>.json` 的 `overrides` 里，表现会与 jmy 修之前一样（扫到模型、0 条物品定义）。
已补第二条读取路径，字段形态不是猜的——用本机缓存的 4 个真实包核过：

| 包 | 带 `overrides` 的载体数 | `custom_model_data` 条目数 |
| --- | --- | --- |
| `frp-dad.com` | 1036 | 3743 |
| `jmy.seasonmc.xyz` | 23 | 1147 |
| `tingwanmc.top` | 7 | 2048 |
| `2d2l.cn` | 5 | 6 |

形态与实现假设一致：`overrides[].predicate.custom_model_data` → `overrides[].model`；
同时确认了两处必须处理的细节（非 `custom_model_data` 的原版谓词大量存在、引用可能不带命名空间）。
**未做**：真实旧式服端到端实测（手上没有这种布局的 customcrops 包），验证口子 = 诊断日志里新增的
「旧式 overrides N」字段。

### 复测步骤（其它服务器复用）

1. 进服 → 触发一次资源检测；
2. 提示应为「资源档案已建立」并给出各分类计数；
3. `.stardew 诊断` 预期：`扫描 N 条 (items 0 / 派发 146 / item模型 148 / block模型 0)`；
4. 打开选择器：种子 / 工具条目显示真实图标（基础物品 + 阈值渲染），且**每行不同**；
5. 背包里放入种子后，`countSeed` 应能数出数量（无需 `.id` 手工入库）。

任一步与预期不符，按第 28 章"用户报 bug 流程"重走取样 → 定性。

## 六、已知限制（本轮回合明确不做的部分）

1. **`select` / `composite` 等 item model 类型的派发不解析** —— 无实测样本，宁可少认不猜结构。
2. **编号家族的 `_item` 零件模型不产生独立条目**：它与 3D 方块模型归并成同一个逻辑对象，只作
   物品键（5.2 第三行）。若某服把 `sprinkler_1_item` 当独立可购买物品卖，才会需要独立条目，
   那时再单独拍板。
3. **作物 / 工具中文名**：该包没有 `lang/*`，名字只能来自服务器下发的物品名（学名链）。
   已确认该链路在旧布局下恢复生效（种子名、阶段名去公共词），并新增 12 种标准作物名的文档兜底；
   服务器自建或改名的作物仍只认学到的真名，工具名同理，不伪造。
4. 派发表构建是同步读盘（新式包一次约几十毫秒；旧式读取要顺带扫 `models/item/**`，多几百毫秒），
   只在玩家触发检测 / 重建索引时发生，不在 render/tick 里跑。
5. **旧式 `overrides` 布局未做端到端实测**（见 5.4）：缺样本，逻辑与字段形态已用 4 个真实包核对，
   但"某服靠旧式表建出档案"这一步尚未在真机上跑通。
