## 2. 客户端能拿到什么信号（26.1.2 源码取证）

| 想读的东西 | 能不能读 | 证据 |
| --- | --- | --- |
| 玩家已经尖叫了几次（`WardenSpawnTracker#warningLevel`） | **读不到** | 它是服务端 `ServerPlayer` 私有字段（`ServerPlayer.java:273`）；基类 `Player#getWardenSpawnTracker()` 在客户端恒返回 `Optional.empty()`（`Player.java:1556-1558`）；全源码无任何同步包 |
| 尖啸体自己的 `warningLevel` | **读不到** | `SculkShriekerBlockEntity` 没覆写 `getUpdateTag` / `getUpdatePacket`，区块包的方块实体信息 tag 为空（`ClientboundLevelChunkPacketData.java:154-159`），客户端恒为 0 |
| 尖啸体正在尖叫 | **能读，且最早** | `SculkShriekerBlock.SHRIEKING` / `CAN_SUMMON` 都是进 `createBlockStateDefinition` 的真方块状态属性（`SculkShriekerBlock.java:52-56`），服务端 `shriek()` 用 flag 2 设值（会发包） |

**提前量**：`SculkShriekerBlockEntity#shriek`（`:120-127`）置 `SHRIEKING = true` 后
`scheduleTick(..., 90)`；90 刻（4.5 秒）后 `SculkShriekerBlock#tick`（`:70-76`）才清标记并调
`tryRespond` → `warningLevel >= 4` 才 `trySummonWarden`。即：**看到 SHRIEKING 那一刻，距坚守者
钻出地面还有 90 刻**，正是用户要的「准备复活、还没出来」。

**为什么要同时要求 `CAN_SUMMON`**：`tryShriek`（`:102-112`）在 `canRespond == false` 时照样会尖叫，
而世界生成里存在 `CAN_SUMMON = false` 的尖啸体（`SculkPatchFeature.java:57` 才把世界生成的那批设 true），
它们永远招不出坚守者，不滤掉就是误报。

顺带确认的兜底信号（本轮未使用）：坚守者实体若已生成，`hasPose(Pose.EMERGING)` 在客户端可读
（`Entity#getPose` 是同步数据），钻出动画长 `WardenAi.EMERGE_DURATION = 134` 刻（`WardenAi.java:49`）。

## 3. 设计

**检测**（`WardenWarningGuard`）：盯「身边 32 格内的幽匿尖啸体」，命中条件
`SHRIEKING == true && CAN_SUMMON == true`，且按坐标取**上升沿**（false → true 只报一次；
同一坐标停止尖叫后再次尖叫会再报，那是一次新的警告等级提升）。

- **不逐格扫方块**：一个区块 32768 个坐标，32 格半径跨 5×5 区块，逐格要 80 万次读取。
  改为每刻只处理**一个**区块，遍历 `LevelChunk#getBlockEntities()` 找尖啸体 —— 客户端区块里的
  方块实体对象是齐的（区块包把所有方块实体都发下来：`ClientboundLevelChunkPacketData.java:45-47`；
  客户端在 `LevelChunk.replaceWithPacketData:548-555` 以 IMMEDIATE 建好），一轮 25 刻、25 个区块。
- **已知坐标每刻复查方块状态**：名单里只有身边实际存在的尖啸体（通常个位数），常量级开销，
  因此从「开始尖叫」到报警最多迟 1 刻，远小于 90 刻窗口。
- **未加载区块用不生成的那个入口**：`ClientChunkCache#getChunk(x, z, ChunkStatus.FULL, false)`
  未加载返回 `null`；不用 `Level#getChunk(x, z)`（它 `loadOrGenerate = true`，会拿回空区块，
  看着像加载了实则什么都没有）。

**动作**（`MiningStateMachine`）：命中即播报 + 切 `GO_WILD`，也就是**复用「前往矿区」那条链路本身**
（`tickGoWild` 阶段 1 调 `executeOwnTeleport(module.getWildCommand(), true)`，含 RTP 弹窗自动点选与我方
传送宽限窗），落地后照常进 `MINING` 继续挖。不另造第二套指令发送逻辑（第 169 条：同源逻辑只留一份）。

两个必须显式处理的点：

1. `teleportCooldownTicks = 0` —— 那是「传送没生效、等冷却后重试」的等待窗，逃离不能被它拖住；
2. 先 `baritone.stop()` —— 从 `COMBAT` / 物流态切走时 `onStateExit` 不会停寻路（只有离开 `MINING` 才停），
   不停就会出现「一边打架一边被传送」。

播报走 `module.error(...)` 而不是 `info/warning`：后两者会被「状态播报」开关静默
（`AutoMinerModule#broadcastBlocked` 的三道闸门），这是安全告警，必须让玩家看到。

## 6. 待实机验证项

1. 挖到深暗之域触发尖啸体：聊天栏出现橙色加粗「附近有坚守者准备复活 ▸ 立刻传送逃离」，
   随即执行「前往挖矿指令」，传送落地后自动继续挖矿。
2. 触发时刻人还在原地、坚守者尚未出现（不能等到 `EMERGING` 才动）。
3. 触发时若处于打怪 / 卸货等状态，Baritone 立刻停下（不会一边打架一边被传走）。
4. 尖啸体 `CAN_SUMMON = false` 时（世界生成的非召唤型）**不**误报。
5. 传送成功后 32 格内没有尖啸体，不出现连续重复报警。
