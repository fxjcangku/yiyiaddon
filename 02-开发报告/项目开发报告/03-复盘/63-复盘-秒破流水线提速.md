# 63 - 复盘：秒破流水线提速（去掉每块的网络往返等待）

- 日期：2026-09-17
- 触发：用户「秒破还可以升级加强吗 真正的暴力 还是太慢了」
- 涉及模块：自动挖矿（秒破 / 连锁挖矿）
- 涉及文件：`feature/mining/fastbreak/MiningFastBreakController.java`（核心改动）、
  `feature/mining/config/MiningSettings.java`、`feature/mining/ui/console/MiningBaritonePage.java`
- 口径：用户选定「只做流水线」+「留 1 刻保险」
- 验证：`./gradlew build --console=plain` → **BUILD SUCCESSFUL（EXIT=0）**；**未实机**

---

## 1. 先说清楚上限：真·瞬破不可能

26.1.2 服务端 STOP 分支只认这一条（`ServerPlayerGameMode#handleBlockBreakAction:218-229`）：

```java
int ticksSpentDestroying = this.gameTicks - this.destroyProgressStart;
float destroyProgress = state.getDestroyProgress(this.player, this.player.level(), pos) * (ticksSpentDestroying + 1);
if (destroyProgress >= 0.7F) { ...destroyAndAck...; return; }
```

也就是说：**每块的最短耗时由服务端按「你手上工具对该方块的破坏速度 f」算出来的 0.7 卡点决定**，
客户端改不了这个数。工具越好 f 越大、卡点越早：

| 工具 | f（青金石矿，硬度 3） | 服务端下限刻数 |
| --- | --- | --- |
| 铁镐 | ≈0.067 | 10 刻 |
| 下界合金镐 | ≈0.10 | 6 刻 |
| 下界合金镐 + 效率 V | ≈0.39 | **1 刻** |

所以「真正的暴力」只有两条路：① 把工具/附魔/药水拉满（效率 V 镐、急速 II、潮涌能量）；
② 把**我方自耗**全部砍掉——本轮做的就是 ②。

## 2. 实机基线（用户 chatlog 取证）

```
19:48:10 连锁挖矿 ▸ 识别到 3 块可挖矿脉，已接管挖掘
19:48:11 ✓ 连锁完成 ▸ 本次连锁破坏 3 块          → 约 6 刻/块
19:49:34 识别到 4 块 → 19:49:35 完成 4 块        → 约 5 刻/块
```

而同一批方块在效率镐下服务端下限只要 1 刻 → **4~5 刻全是我方自耗**，其中最大的一项是
「发完 STOP 要等服务端把方块变化包发回来（一个网络往返）才开始下一块」。

## 3. 改法：确认阶段流水线化

| 项 | 旧 | 新 |
| --- | --- | --- |
| STOP 之后的动作 | 进入 `AWAITING_CONFIRM`，等权威方块变化包（一个往返） | **当刻交进待确认集合 `pending` 并回到空闲**，下一块按间隔立刻开 |
| 待确认校验 | 只有当前这一块，超时重发 START | `sweepPending()` 每刻结算：方块变了 → 记入「刚破坏」（ESP 残影 / 连锁矿脉根照常）；超 `STOP_RESEND_AFTER_TICKS` 未变 → 排进重试队列 |
| 重试 | 原地重发 | `dispatchRetry()` 在空闲刻补挖，限速 `RETRY_MIN_GAP_TICKS = 10` 刻、一次一块（避免与 Baritone 抢同一个方块而把进度清零）；重试用尽照旧只拉黑那一个坐标、放行原版 |
| 两块间隔 | `breakInterval`（还要叠加一个往返） | `max(breakInterval, 1)`——用户裁定的「1 刻保险」写死在 `PIPELINE_MIN_GAP_TICKS` |
| 换目标 | `release()`（那时只有单块账） | 新增 `dropTarget()`：只丢当前这一块，**不动别的方块的待确认账** |

### 为什么协议上安全（不是猜的，逐条对过服务端源码）

- 我方 STOP 是按服务端同一公式算准的（`requiredElapsedTicks` 用 float 乘法复核），服务端当刻 `destroyAndAck` 并清空自己的槽位 → 下一块的 START 不会顶掉任何东西。
- 万一 STOP 发早了（工具刚切换、服务端还没同步到新工具，f 被算小）：
  `handleBlockBreakAction:231-236` 会把它放进 **delayed destroy 槽**，同时把 `isDestroyingBlock` 置 false；
  `tick():111-121` 随后每刻继续累加、到 1.0 自己把方块删掉。也就是说**服务端会替我们把这块挖完**，
  我方 `sweepPending` 也校验得出来。
- START/STOP 走 TCP，顺序不会乱：服务端看到的永远是 `START(A) → STOP(A) → START(B)`。
- 待确认集合 `MAX_PENDING = 16` 只是安全阀：按 2~3 刻/块 × 20 刻校验窗口，正常运行最多十来个。

### 顺带修掉的一个坑（流水线引入后才会犯）

`start() / continueBreaking() / mineRequested()` 里的世界切换判定原本是 `level != currentLevel`；
空闲态 `level == null`，于是**每次登记新目标都会误判为「换世界」并清空流水线记账**
（ESP 残影与连锁的矿脉根都会跟着失效）。现改为 `level != null && level != currentLevel`。

## 4. 预期收益

| 场景 | 旧 | 新 |
| --- | --- | --- |
| 间隔 2（你当前配置）+ 效率镐 | 约 5~6 刻/块 | 约 3~4 刻/块（≈1.5 倍） |
| 把「秒破间隔」改成 0 | — | 约 2~3 刻/块（≈2 倍，仅剩 1 刻保险） |
| 服务端硬下限（工具限制） | 1 刻/块 | 1 刻/块（换效率 V 镐 / 急速才有用） |

## 5. 待实机验证项

1. 连锁吞吐是否变快（对比 chatlog 里「识别到 N 块」到「连锁完成」的间隔）。
2. 每块都真的消失（没有「挖了没变化」的漏块）；漏块会在 20 刻后被重试补挖。
3. 挖掘进度 ESP 的完成残影仍正常出现（现在由待确认结算时记账）。
4. 长时间挂机不出现方块被服务端回滚（回滚说明反作弊介入，把「秒破间隔」调回 2~4 即可）。

## 6. 遗留与注意

- 本轮改动未 commit。
- 「秒破间隔」的文案已同步更新（设置说明与游戏内控制台页），因为它现在不含「等服务端确认」那一段。
- 默认值未改（用户裁定只做流水线）：想要最快，去控制台把「秒破间隔」设为 0。
- 若服务器有严格反作弊，最快的档位反而容易被判定：出问题时把间隔调到 2~4 观察。
