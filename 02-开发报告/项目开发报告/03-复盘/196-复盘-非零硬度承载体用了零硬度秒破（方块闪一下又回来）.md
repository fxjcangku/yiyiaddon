# 复盘：非零硬度承载体上用了「零硬度秒破」——方块闪一下又回来，始终挖不掉

- 日期：2026-09-22
- 触发：用户实机 ——「然后巨型菠萝 我故意放在地上 他尝试破坏了 但是 没有挖掉 有挖掉的动画
  不知道用的什么手」
- 前置事实：巨型菠萝的承载体是原版 `minecraft:chorus_plant`（硬度 0.4），
  作物身份挂在展示实体上（`customcrops:item/crops/pineapple/gigantic_pineapple`），
  方块本身是「可被左键破坏的普通方块」——用户在上一轮已经证明「左键能砸掉，空手也行、拿锄头更快」。

## 一、成因：把「零硬度秒破」当成了通用破坏

`BlockPacketSender#breakBlock` 的假设写在注释里：**农作物 / 竹子 / 甘蔗这类方块硬度为 0，
服务端收到 START 即判定破坏完成**，所以它 `START + STOP` 同 tick 连发，并且**本地立刻置空气**
（`level.setBlock(pos, AIR, 11)`，为了让同 tick 的后续逻辑读到新世界）。

清枯苗 / 清错位 / 清杂物（`doBreakPlant`）与批量破坏都直接调这条通道。于是当承载体是
**非零硬度**方块（紫颂植株 0.4）时：

1. 客户端本地立刻把方块抹成空气 → 玩家看到「方块消失了一下」（破坏动作）；
2. 服务端按 `delta × (已挖 tick + 1) ≥ 0.7` 校验（空手时每刻进度只有 0.025，需要约 27 刻），
   同 tick 的 STOP **直接驳回**，随后的方块同步包把方块放回来 → 玩家看到「又回来了、没挖掉」；
3. 本地空气还会骗过验证层（`CropRecognizer.recognize(air)` → `EMPTY`）：这一格**被判成功**，
   模块换下一格，玩家眼里就是「反复尝试、永远挖不掉」。

## 二、处置：按服务端阈值分两条路，别再把零硬度当默认

新增 `StardewFarmExecutor#breakAt(pos)`，删掉原来的 `doSpecialBreakHarvest` 专用实现：

- `requiredDigTicks(delta, 0.7) == 0`（零硬度载体，delta 为 +∞）→ 仍旧走
  `adapter.breakBlock`（同 tick 秒破），行为与改动前逐字一致；
- 否则 → `digBreakProgressively(pos, delta)`：`sendBreakStart` → 等够
  `requiredDigTicks + 2` 刻（+2 抵发包延迟）→ `sendBreakStop` → 再给 20 刻权威同步窗口
  （`BREAK_RESEND_AFTER_TICKS`，与 `MiningFastBreakController#STOP_RESEND_AFTER_TICKS` 同口径）；
  窗口内还没变就重来一轮（新的 START 重新登记服务端槽位），最多 `BREAK_MAX_ATTEMPTS = 3` 轮；
  仍不变则 `sendBreakAbort` + 交回验证层判失败（退避 + 播报），**绝不在这格上无限砸**。

配套改动：

- `doBreakPlant`（清枯苗 / 清错位 / 清杂物）与特殊变种的左键口径都改走 `breakAt`，
  不再直接 `breakBlock`；
- `digInProgress()` 简化为「`breakDigPos != null`」，`verify()` 里那一分支不再限定 `HARVEST`
  ——清理类同样可能砸在非零硬度载体上，挖掘序列没走完就一直留在这一格；
- 批量破坏（`batchActions > 1`）只对零硬度格子连发，非零硬度的格子跳过，
  留给下一轮作为主目标走完整流程（同 tick 连发对它必然是「假成功」）；
- 失败提示：学到的左键口径砸了 3 轮还是原样时，每个作物报一次
  「特殊变种砸不掉（服务端没放行这一格）▸ …｜多半是服务端保护了它，或本服收法其实不是左键：
  手动收一棵给我看，口径会自动更新」。

## 三、顺带修掉的学习盲区（同一句反馈里的「不知道用的什么手」）

`MultiPlayerGameModeSpecialHarvestMixin` 原先**只观测手持金锄头的动作**。用户实测口径是
「空手也能砸、拿锄头更快」，于是空手砸掉一棵反而不被记住，模块继续按默认的右键口径白点。
现在分档：

| 动作 | 是否要求手持金锄头 | 理由 |
| --- | --- | --- |
| 左键破坏（`startDestroyBlock`） | **不要求** | 破坏口径工具不限（本服实测），限制手持物会漏学 |
| 右键交互（`useItemOn`） | 要求 | 右键口径就是「手持原版金锄头右键」，空手 / 随手拿别的物品右键不是收割动作 |

判定与落盘时机仍在协调器（目标必须是特殊阶段作物 + 2.5 秒内那一格确实变了才算数）。

## 四、续：第二次实机复现（同日晚，日志取证）

第一版改完后用户复测仍「站着瞄着不动手」，日志给出了决定性证据：

```
[23:17:20] 破坏 开始挖掘 目标=4795,85,-5604 工具=1 minecraft:golden_hoe 每刻进度=0.083333336 需 10 tick 发包=true
[23:18:00] 破坏 开始挖掘 目标=4799,85,-5603 工具=1 minecraft:golden_hoe 每刻进度=0.083333336 需 10 tick 发包=true
[23:18:22] 破坏 开始挖掘 目标=4799,85,-5603 工具=4 minecraft:apple    每刻进度=1.0E-4      需 7002 tick 发包=true
```

**只有「开始挖掘」，从来没有「结束挖掘」。** 三个缺陷：

1. **序列推进挂在相位机上**（原始设计）：`START` 之后要靠 `verify → INTERACT` 再来一次才会检查
   「够 tick 了吗」，一旦中途重扫农田 / 换任务 / 相位跳转，那次 `START` 就永远悬着 —— 服务端记着一个
   已经累计了进度、却永远等不到 STOP 的破坏会话。
   → 改为**协调器每客户端 tick 独立推进**（`StardewCoordinator#tick` 最前面调
   `StardewFarmExecutor#tickBreakDig`）：与任务相位完全解耦，`START` 之后一定等到 `STOP` 或 `ABORT`。
2. **重规划无条件 ABORT**：`replan()` 里一句 `executor.abortBreakDig()`，而重规划随时会发生
   （重扫、季节代次变化、玩家开背包、区域错位暂停…）。于是「START → ABORT → START」无限循环，
   服务端进度每次都被清零 —— 方块永远挖不掉。这正是 `MiningFastBreakController` 当年踩过的同一个坑
   （见其类注释第 2 条「停挖记账会中止服务端槽位」）。
   → 重规划**不再中止**序列；只有「换目标」（`breakAt` 换格子）与「停机 / 换世界」（`reset()`）才 ABORT。
   挖掘序列本身有界自收尾（最多 3 轮 → ABORT + 播报），不会赖在旧格子上。
3. **开了永远挖不完的会话**：`getDestroyProgress` 读的是**选中快捷栏物品**（不是 `activeHand`）。
   日志里手里是苹果时每刻进度 1.0E-4、需 **7002** tick —— 模块照样发 START，玩家看到的就是
   「站着瞄着、一直不动手」。
   → 两道闸：① 先换手（锄头）**再**算进度，保证速度按工具算；② `required > 200` tick
   （`BREAK_MAX_REQUIRED_TICKS`）时**不开挖掘会话**，直接报「这一格挖不动，已跳过」并交回验证层。
   同时日志补上 `cellSummary`（方块 ID + 该格实体）与「选中物品」，一眼能看出挖的是不是那一格。

顺带修掉一个手部记账副作用：`holdItem` 每次都会 `saveHand()`，同一个工具被重复调用会把「原来的槽位」
覆盖成工具槽，任务结束后不再换回去。挖掘每轮重试都要确认工具在手，因此新增 `holdItemOnce`
（手上已经是它就直接返回）。

## 五、续二：客户端估算整条不可信（按住时长改为下限 + 逐轮翻倍）

加上诊断字段后的日志给出了最终答案：

```
[23:32:32] 破坏 开始挖掘 目标=4799,85,-5601 方块 minecraft:chorus_plant · 实体 minecraft:item
           选中物品=1 minecraft:golden_hoe 硬度=0.4 物品破坏速度=0.0 正确工具=true
           原始每刻进度=0.0 → 实际用 1.0E-4 客户端估算 7000 tick → 按住 40 tick
[23:32:36] 破坏 目标已消失 目标=4799,85,-5601            ← 40 tick 按住后真的挖掉了
[23:33:01] 破坏 开始挖掘（同一格同一把锄头）硬度=0.4 物品破坏速度=1.0 正确工具=true
           原始每刻进度=0.083333336 客户端估算 8 tick → 按住 10 tick
[23:33:02~04] 第 2、3 轮各按住 10 tick → 全部被服务端驳回
```

结论有三条，都不是「口径」问题而是「时长」问题：

1. **客户端的「物品破坏速度」在同一格同一把金锄头上来回跳（一次 0.0、一次 1.0）**，
   估算随之在 8 tick 与 7000 tick 之间跳 —— 这个值不能当判据。
2. **服务端实际要的时长比客户端估算大 4 倍左右**（客户端按「正确工具 i=30」算 8~10 tick，
   服务端按 i=100 算 ≈28 tick），所以「按一下就松」永远被驳回，表现就是「寻路到了、站着不挖」。
3. STOP 被驳回后**同一个 START 槽位不会再自己长进度**，必须重新 START 从头累计，所以只能靠
   一轮比一轮按得久。

处置：单轮按住时长改为「估算当参考，但有下限、且逐轮翻倍」——
`clamp(估算+2, 20, 120)` 起步，之后每轮 ×2（20 → 40 → 80 → 120），最多 4 轮。
40 tick 那一轮实测就能挖掉，于是「寻路过去却一直不挖」消失；真挖不动（服务端保护 / 收法不对）
才会走完 4 轮并报「服务端没放行这一格」。

## 六、验证

| 项 | 结果 |
| --- | --- |
| `.\gradlew.bat compileJava` | **EXIT=0** |
| 零硬度载体（绊线 / 农作物） | 仍走同 tick 秒破，不发多余包 |
| 非零硬度载体（紫颂植株） | START → 等够 → STOP；STOP 后 20 刻未变则重试，3 轮后 ABORT + 播报 |
| 挖不动时 | 不再「本地假成功」，验证层判失败并退避 + 提示，不在同一格死循环 |
