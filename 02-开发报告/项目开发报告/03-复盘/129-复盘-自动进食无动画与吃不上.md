日期：2026-09-19
项目：yiyiaddon（新项目，Fabric 26.1.2 客户端模组）
旧项目对应物：`MiningContainer#autoEat`（按住右键的用食循环）→ 118 号改成发包驱动

## 一、四条成因（逐条取证）

### 1. 动画的真来源：服务端把「我在用食」同步回来了

`LocalPlayer#isUsingItem()` 读的是本地字段（`:545-558`），所以第一反应是「本地不进入用食态就没动画」。
但**服务端也会把自己的用食标志同步回客户端**，而这里会把它接住（`:580-590`）：

```java
public void onSyncedDataUpdated(final EntityDataAccessor<?> accessor) {
    if (DATA_LIVING_ENTITY_FLAGS.equals(accessor)) {
        boolean serverUsingItem = (this.entityData.get(DATA_LIVING_ENTITY_FLAGS) & 1) > 0;
        if (serverUsingItem && !this.startedUsingItem) {
            this.startUsingItem(serverUsingHand);      // ← 本地进入用食态 → 动画（手臂摆动/粒子/移速减慢）
        } else if (!serverUsingItem && this.startedUsingItem) { this.stopUsingItem(); }
```

### 2. 「吃不上」的隐藏成因：同一处还会触发出 RELEASE 包

`Minecraft#handleKeybinds`（`:2026-2029`）：

```java
if (this.player.isUsingItem()) {
    if (!this.options.keyUse.isDown()) {
        this.gameMode.releaseUsingItem(this.player);   // ← 发 RELEASE，服务端立刻 stopUsingItem，这一口作废
    }
```

我们起手不按右键（用完就松开），所以只要本地被上面那条同步点亮成「在用食」，
原版就会替我们发 RELEASE 把这一口取消 —— **越发包越吃不上**，这就是第 2、4 次反馈的成因。

### 3. 「吃半天才生效」：补包策略被我从「每 4 刻」改成「只补一次」

服务端有一条作废规则（`LivingEntity#updatingUsingItem`，`:3348-3355`）：

```java
if (ItemStack.isSameItem(this.getItemInHand(this.getUsedItemHand()), this.useItem)) {
    this.updateUsingItem(this.useItem);
} else {
    this.stopUsingItem();          // ← 手上那格物品变了 → 这一口直接作废
}
```

挖矿侧任何「换手」都会命中它（秒破换工具 / 连锁 / 拾取顶格 / 搭路垫脚）。
旧版起手包**每 4 刻补一发**，被顶掉 4 刻内自动续上；我改成「只补一次」后，
一次作废要干等 `EAT_CONSUME_TIMEOUT_TICKS(60) + EAT_RETRY_COOLDOWN_TICKS(20) ≈ 4 秒` 才重试。
补包本身无副作用、也不会拖慢单件：服务端真在吃时，重复包被
`LivingEntity#startUsingItem` 的 `!isUsingItem()` 卫语句忽略（**计时不会被重置，单件仍 32 刻**）。

### 4. 容器死锁（与 128 号同源）

`isPlayerInventoryClickBlocked()` = `containerMenu.containerId != 0`。128 号中途那层
「玩家开着界面就不关容器」的守卫让容器**永远关不掉** → 进食时「把食物搬进快捷栏」那一步
被永久挡住 → 吃不上（第 4 次反馈）。修法见 128 号：容器要真的关，界面不能动。

## 二、走过的弯路（记录，避免重犯）

为了消动画，我曾把起手包也改成直发 `ServerboundUseItemPacket`（绕开 `gameMode.useItem`）——
实机**吃不上**。原因有二，当时都还没查清：(a) 原版入口里还有 `ensureHasSentCarriedItem()`
（私有，负责把「手持槽位」同步给服务端）与预测登记，自研直发没复刻全；
(b) 更关键的是上面第 1/2 条 —— 只要本地被同步点亮成用食态就会发 RELEASE，起手从哪儿发都一样。
**结论：起手永远走原版 `gameMode.useItem`，要消动画就在本地状态那一层动手。**

## 三、最终改法

| 位置 | 改动 |
| --- | --- |
| `platform/eat/SilentEat`（新增） | 「自动进食期间压制本地用食态」开关，起手打开、这一件结束（吃掉/中断/超时）关闭 |
| `mixin/client/LocalPlayerEatAnimationMixin`（新增） | `LocalPlayer#startUsingItem` 在开关打开时压成空操作 —— **动画没了、RELEASE 也没了**，服务端照常按 `Consumable` 32 刻结算；手动进食期间开关是关的，玩家自己吃东西一切照旧 |
| `MiningContainer#beginEating` | 起手前 `SilentEat.setSuppressed(true)`，随后走**原版入口** `mc.gameMode.useItem(...)`；删掉中途那句 `mc.player.stopUsingItem()`（不再需要，且它治不了同步回来的那一次） |
| `MiningContainer#advanceEating` | 第 3 条恢复**每 `EAT_RESEND_INTERVAL(4)` 刻补一发**（自愈），注释写明「服务端真在吃时重复包被忽略、不重置计时」 |
| `MiningContainer#clearEating` / `stopPacketEat` | 一并关闭 `SilentEat`（`stopPacketEat` 本就调 `clearEating`） |
| 诊断日志（新增） | `EAT_LOG = LoggerFactory.getLogger("yiyiaddon/eat")`，**只写 latest.log、不进聊天** |

## 四、诊断日志：五条线

排查「吃不上」时读 `run/logs/latest.log` 里 tag 为 `yiyiaddon/eat` 的行（同状态每秒最多一条）：

| 日志 | 含义 / 下一步 |
| --- | --- |
| `起手 ▸ 槽位X 选中槽X 物品 x数量 · 容器idN · 界面X` | 这一包从哪儿发出、当时容器/界面状态 |
| `吃掉一件 ▸ A x50 → x49` | 正常结算 |
| `中断 ▸ 手里已不是A（实际 B · 选中槽X）` | 有东西在 1.6 秒里抢了手 → 查是谁换的手持格 |
| `等待服务端结算 ▸ 已N刻 · 数量Z`（每秒一条） | 包发了但服务端不结算 → 数量一直不动就是这条 |
| `搬食物被容器挡住 ▸ containerId=N` | 容器没收掉导致搬不进快捷栏（128 号那条死锁的观测点） |
| `超时放弃 ▸ 已等N刻` | 这一件彻底判失败、进冷却 |

## 五、边界（说清，避免预期错位）

1. **吃完那一下的咀嚼音与粒子去不掉**：那是服务端 `Consumable#onConsume → emitParticlesAndSounds`
   广播的，别的玩家看到的就是你在吃；客户端侧能藏的都藏了（用食姿态 / 粒子 / 移速减慢）。
2. **单件耗时仍是服务端口径的 32 刻**（1.6 秒）——发包不能加速服务端结算；
   「秒吃」的收益来自「不等按键 + 两件之间零间隔 + 饱食度顶满后自然再生立刻生效」，
   以及「服务端把用食时长设为 0（按包结算）时逐包续发」那条分支。
3. **饱食度已满 20 而血不满时不吃金苹果**（现状）：金苹果类 `canAlwaysEat` 本可随时吃，
   但进食触发条件是 `饱食度 < 20`，此时只靠原版自然再生（没饱和度时 4 秒 1 点血）。
   ——**该项用户尚未裁定**，如需要让「满饱食度 + 残血」也啃金苹果救急，改一处判据即可。
4. 进食期间仍会**停 Baritone**（`tickMining` 优先级 2.6），这是既有设计（进食中换槽会让服务端停掉用食）。

## 六、验收

`.\gradlew.bat build --console=plain` → BUILD SUCCESSFUL。

实机（用户确认「吃东西好像修好了…牛逼啊 可以了」）：
- 进食**无动画**、不再卡在「进食中」、不再一吃吃半天；
- 沾到换手打断时 4 刻内自动续上，单件仍 1.6 秒吃完；
- 白名单外食物不吃（124 号口径不变）。
