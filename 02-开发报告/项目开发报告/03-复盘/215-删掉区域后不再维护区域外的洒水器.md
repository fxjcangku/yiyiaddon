# 215 · 删掉区域后不再维护区域外的洒水器

> **后续（同日）：本文第二节那个「只剔除维护、保留点位」的取舍已被 [218](218-删区域时一并删掉区域内的洒水器点位（推翻第30条的保守取舍）.md) 推翻** ——
> 保留点位会在世界里留下 ESP 框、点位列表里也还列着，玩家看到的是「这块地还在被管」。
> 现在改为删区域时把区域内的洒水器点位一并删除，那道「维护对象必须在区域内」的闸也已撤掉
> （它会误伤「先绑洒水器、后圈地」）。本文留档说明演进过程。

- 日期：2026-09-22
- 触发（用户原话）：「假设我设置了 4 个区域，删掉了其中两个，然后洒水器不是还在吗？
  区域都删掉了洒水器没跟着一起删掉 导致我来回跑动」
- 相关：[36-规范-分区种植.md](../01-规范与UI规格/36-规范-分区种植.md)（「圈地是唯一的范围来源」）、
  [214](214-复盘-自检错位改用世界红框（未启动也要看得见）.md)（同一天，同属"区域决定范围"这条线）

## 一、现象与成因

`StardewTaskPlanner#sprinklerPointsInDimension()` 取维护对象的口径是：

```java
for (StardewPointManager.StardewPoint p : owner.points.getAll(StardewPointType.SPRINKLER)) {
    if (!p.inCurrentDimension()) continue;
    ... // 只判"这台还在不在"
}
```

**只要点位绑过、且在当前维度，就会被维护** —— 完全不看它浇不浇得到地。
于是删掉 2 块地之后，那两块地里的洒水器仍在对象列表里，模块照旧挨个走过去点一遍，
玩家看到的就是"删了地还在来回跑"（而且会按 `sprinklerInterval` 周期性重复）。

口径上的不一致才是根子：**所有其它任务都以「种植区域」为唯一范围来源**
（未分区格子一律不管，见 `resolveTask` 的第一道闸），唯独洒水器维护漏了这把尺。

## 二、改动

维护对象加一条判据 —— 洒水器必须落在某个种植区域内：

```java
// 不在任何种植区域里的洒水器**不维护**：洒水器的意义是浇地，区域被删掉（或从来没圈进去）
// 之后那台已经没有要浇的盆，继续为它跑腿就是纯白跑。
// **只从维护对象里剔除，绝不删点位**：玩家重新圈地后这台自动恢复被维护，不必重新绑一遍。
if (owner.regionAt(p.pos()) == null) continue;
```

放在「维度」判据之后、「洒水器是否还在」判据之前 —— 区域外的点位连"不见了"都不必报，免得刷噪声。

### 为什么是"不维护"而不是"跟着删点位"

- **删点位不可逆**：删区域常见的用法是"重划"（圈错了一格、想改范围），跟着删点位会让玩家重绑一遍；
- **点位是玩家的数据**：区域是"这块地在种什么"，洒水器点位是"这台设备在哪"，两件事的生命周期不同；
- **行为可自证**：不维护的效果玩家立刻能看到（不再跑过去），而误删数据没法撤销。
  这与第 214 条"自检那份高亮不删、只影响显示"是同一种取舍：**宁可少做动作，不要动玩家的数据**。

## 三、验证

- `GetDiagnostics`：`StardewTaskPlanner.java` 0 诊断。
- 待实机：圈 4 块地、各放洒水器 → 删掉其中 2 块 → 模块应只维护剩下 2 块地里的洒水器，
  不再往删掉的那两块跑；重新圈回那两块 → 那两台洒水器自动恢复被维护。

## 四、教训

1. **"范围来源"必须是全模块统一的**：只要有一条链路（这里是洒水器维护）绕开"以种植区域为范围"，
   删区域时就会出现"这块地不管了、但为这块地服务的东西还在跑"的割裂。
   新增任何"按点位跑腿"的链路时，都要先问一句：**它的范围是不是也该由区域裁剪？**
2. **剔除 ≠ 删除**：玩家删了 A（区域），不代表他想删 B（设备点位）。把 A 删除时的副作用限制在
   "不再使用 B"，而不是"连带删除 B" —— 这样即使判断错了，代价也只是"少做一件事"，可以一句话改回来。
