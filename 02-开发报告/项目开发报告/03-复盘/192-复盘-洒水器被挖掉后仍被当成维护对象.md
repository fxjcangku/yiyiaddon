# 复盘：洒水器被挖掉后仍被当成维护对象（ESP 还在、还报「本轮 1 台」）

- 日期：2026-09-22
- 触发：用户实机反馈「要是洒水器被挖掉了，没有识别，还能运行，然后洒水器的 ESP 还在，
  然后还去维护洒水器，但是其实洒水器早就被挖掉了，还提示 [星露谷农场] 洒水器维护完成 ▸ 本轮 1 台」
- 结论：两级漏判叠加 ——
  ① **绑定校验**只比 BlockState，而贴图形态洒水器的载体格永远是空气，被挖掉之后「空气还是空气」，
  校验一直判定有效；
  ② **维护链路与 ESP** 取对象时只按「本维度有哪些点位」，从不做点位校验，
  于是照常走过去灌水、把方框画在原处、并报出「本轮 1 台」这种假结论。

## 一、取证

`StardewFarm/points/jmy.seasonmc.xyz_25565.json` 里那台：

```json
"sprinkler": [{ "x": 4803, "y": 85, "z": -5597, "验证": "人工确认世界载体",
  "身份": "customcrops:sprinkler_2",
  "世界绑定": { "世界载体方块": "minecraft:air",
               "资源语义身份": "minecraft:air", "资源模型": "minecraft:block/air" } }]
```

载体是 **air** = 这台洒水器是 `item_display` 贴图形态（本模组 `SprinklerWorldBinding` 的注释里
写明了这种形态的载体格本来就是空气）。而 `matches(pos)` 当时只比
`carrierBlockId` / `carrierState` 两项 → 被挖掉后两项都没变 → **永远判「绑定仍然有效」**。

维护链路侧：

- `StardewTaskPlanner#sprinklerPointsInDimension()` 只过滤 `p.inCurrentDimension()`，**不校验点位**；
- `StardewTaskVerifier#SPRINKLER_CHECK` 收尾时 `announceSprinklerRoundDone(list.size())`
  ——「本轮 N 台」就是「本维度有几个点位」，与「实际灌了几台」无关，所以必然会报「本轮 1 台」；
- `StardewRenderState#boundSprinklers()` 同样只过滤维度 → ESP 方框照画。

## 二、改动

### ① `SprinklerWorldBinding`：贴图形态必须验证展示实体仍在（根因）

`capture()` 当初正是用 `displayCarrierAt(pos)` 才认出「载体格是空气但挂着贴图实体」这种形态的；
`matches()` 补上同一份判据，两侧口径一致：

```java
return !state.isAir() || displayCarrierAt(pos);
```

新增 `displayCarried()`（`carrierBlockId` 是 `minecraft:air`）供上层区分「挖掉了」与「载体换了」。
挖掉之后 `matches()` 返回 false → 点位校验给出确定结论。

### ② `StardewPointManager`：新增「确定不可用」这一档

- 新常量 `MISSING_SPRINKLER`＝「洒水器已不存在（那一格的洒水器实体消失了，可能已被挖掉）」；
  贴图形态挖掉时返回它，而不是含糊的「载体状态不一致」。
- 新方法 `sprinklerUnusableReason(point, index)`：`null` = 仍可维护（含「区块还没加载」这类**暂时
  未知**）；非 null = **确定不可用**。与 `isWorldPending` 的分工写进注释：
  后者是「还不知道、要复核、要照常跑过去把区块加载出来」，前者是「已经知道它不在 / 绑定失效」。
  「当前服务器资源未就绪」也归入「不判死」，提为常量 `RESOURCE_NOT_READY`。

### ③ 维护链路与 ESP 都剔除确定不可用的点位

- `StardewTaskPlanner#sprinklerPointsInDimension()`：剔除 + 每个点位**只提示一次**
  （去重记账在协调器：`missingSprinklersReported`，会话复位时清空；点位重新出现后标记解除）；
- `StardewRenderState#boundSprinklers()`：不画。**「区块还没加载」两种场景都不剔除**——
  玩家走过去的路上本来就要看到它、要靠走过去把区块加载出来才能判。

### ④ 播报：把「假结论」换成实情 + 出路

新增 `StardewFarmReporter#announceSprinklerMissing`：

> 洒水器不在了，已跳过维护 ▸ 优质洒水器 · 4803, 85, -5597 ▸ 洒水器已不存在（那一格的洒水器实体消失了，
> 可能已被挖掉）｜在控制台「点位」页的洒水器卡片点「管理」，删掉这一个点位

走 `critical`（异常类，红色）而不是普通状态提示；同一台只报一次。

## 三、验证

| 项 | 结果 |
| --- | --- |
| `.\gradlew.bat compileJava` | **EXIT=0** |
| 实机验证 | **已通过**（用户 2026-09-22「刚刚的 bug 已经修好了，被挖就不启动了」；客户端日志 22:36:35 / 22:37:50 两条自检播报：「启动自检未通过 ▸ 配置问题 ▸ 洒水器 4797, 85, -5603：洒水器已不存在（那一格的洒水器实体消失了，可能已被挖掉）▸ 禁止启动」） |

补充事实（用户 2026-09-22 补充「洒水器其实是滴水石锥」）：这台服的洒水器是**用滴水石锥外观的物品
渲染成 `item_display` 贴图实体**的（所以那一格永远是空气、点位列表里的图标也是滴水石锥），
这正好印证了根因——只比 BlockState 的校验在这种形态下永远判有效。

复测要点：
1. 站在已绑定的洒水器旁 → 把它挖掉 → 等下一轮洒水器检查：
   - 不再有「洒水器维护完成 ▸ 本轮 N 台」把它算进去；
   - ESP 方框消失；
   - 聊天出现一次「洒水器不在了，已跳过维护 ▸ 类型 · 坐标…」；
2. 把它重新摆回去（同一格）→ 方框恢复、维护恢复正常（标记已解除，再挖会再提示一次）；
3. 走到未加载的远端洒水器（区块没加载）→ **不**报「不在了」，照常过去维护。
