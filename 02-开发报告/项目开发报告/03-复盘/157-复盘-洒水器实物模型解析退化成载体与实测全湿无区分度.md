## 二、根因：模型键解析退化成「载体」，世界识别三条判据全空

### 1. 155 关于「本服没有 item_model 组件」的判断是错的

155 复原因为「整服自定义物品挂在 `minecraft:paper` 上，数据组件里**没有** `item_model`，
于是 `model == null` 恒定成立、实物被整个跳过」——但**修正后的日志把这条推翻了**：
展示物的 `item_model` 组件**是存在的**，值就是 `minecraft:paper`（载体本身）。

### 2. 新写法仍然「看起来对、其实是空」：组件非空即返回

155 之后的 `resolvedModelOf` 长这样：

```java
public static String resolvedModelOf(ItemStack stack) {
    String model = itemModelOf(stack);
    if (model != null) return model;                      // ← 组件非空即返回
    return ItemModelDispatchIndex.get().modelKeyOf(stack); // ← 派发表永远轮不到
}
```

ItemsAdder / Nexo 这类布局里，`item_model` 组件写的是**载体**（`minecraft:paper`），
真实身份在 `custom_model_data` 里、由资源包 `assets/minecraft/items/paper.json` 的
`range_dispatch` 按阈值派发。组件非空即返回 ⇒ 派发表永远没用上 ⇒ 解析结果恒为
`minecraft:paper`。

后果是**判据的输入又变成空**（155 修好的是「看起来空」，这次是「看起来有值，其实是载体」）：

- 判据 ① `sprinklerByItemModel("minecraft:paper")` → 末段不是 `sprinkler_*` → `null`；
- 判据 ② `flatIdentityOf("minecraft:paper")` → `minecraft:paper`，与 `customcrops:sprinkler_N` 不等 → `null`；
- 判据 ③ 名称：服务器没下发自定义名（日志里 `名=` 为空）→ `null`。

三条全空 ⇒ `matchSprinklerDisplay` 恒返回 `null` ⇒ `displayMismatch` 走「认不出 → 放行」
⇒ **写明任意品质都能绑上**；绑定播报里的「验证」也如实写着 `人工确认世界载体`。

同一条断链还波及作物：`StardewCropDisplayProbe.modelOf` 要求命名空间是 `customcrops`，
解析结果恒为 `minecraft:paper` ⇒ 展示实体整批被忽略（诊断里「盆上作物：附近 8 格内没有展示实体」）。

## 三、改动（三处，均为最小改动）

### 1. `ItemModelDispatchIndex.Snapshot`：拆出「只认阈值命中」的入口

```java
public String modelKeyOf(ItemStack stack) {        // 语义不变：阈值命中 → 直接模型兜底
    String matched = dispatchedModelOf(stack);
    if (matched != null) return matched;
    String modelId = modelIdOf(stack);
    return modelId == null ? null : directByItem.get(modelId);
}

public String dispatchedModelOf(ItemStack stack) { // 新增：只返回阈值命中的自定义模型
    ...
}
```

为什么必须拆开：原版物品的 `assets/minecraft/items/<id>.json` 会被登记成
`minecraft:item/<id>`（客户端内部写法，不是自定义身份）。把它当反查结果去覆盖
`item_model` 组件，只会把自定义物品认成原版——**要的只是「阈值真的命中」那一支**。

新增 `modelIdOf(stack)`：查找键改为「`item_model` 组件优先、缺失退回注册表 id」，
与客户端解析模型的口径一致（组件值就是 `assets/<ns>/items/<id>.json` 的查找键）。
本服两者同为 `minecraft:paper`，行为一致；「组件指向自定义 id」的布局也能命中自己的派发表。

### 2. `StardewInventoryService.resolvedModelOf`：派发阈值命中优先

```java
String dispatched = ItemModelDispatchIndex.get().dispatchedModelOf(stack);
if (dispatched != null) return dispatched;             // 载体 + custom_model_data 派发命中
String model = itemModelOf(stack);
return model != null ? model : ItemModelDispatchIndex.get().modelKeyOf(stack);
```

- 派发表**没命中阈值**时一律沿用旧口径 ⇒ 原版物品、把真实模型写进组件的布局，行为一字不变；
- 只有「载体 + `custom_model_data`」这一支翻上来，正是本服（以及所有 ItemsAdder / Nexo 布局）。

### 3. `StardewPointActions`：取证日志从「每秒扫描」挪到「玩家亲手绑定」

155 把未命中日志写在了 `matchSprinklerDisplay` 里，而它在附近预览扫描里每秒跑一遍
（相邻 8 个展示物 → 每秒 8 条，含根本不是洒水器的「稻草人」）。改为：

- `matchSprinklerDisplay` 不再打日志（只保留「同格多种洒水器」的歧义日志，那条是偶发）；
- 新增 `displayCarriersAt(BlockPos)`；`addSprinklerFromCrosshair` 在两次识别都失败、
  决定是否放行之前打印一次 `[星露谷] 洒水器实物识别未命中：格=… 展示物=…`。

## 五、附：四台实测全是 `5×5 · 24 格` 怎么看

数据本身是真实的（点位文件 `StardewFarm/points/jmy.seasonmc.xyz_25565.json` 里
四台的「范围」都是 `[-2..2]²` 去掉中心 24 格、「矩形内干盆」都是 0、`truncated()` 未命中），
但它**不能证明四台覆盖范围相同**：

- 盆的干湿由**方块的语义身份**判定（`wet_pot_*` → WET）。这片地当时**整块都是湿盆**，
  于是「最近归属」过滤后每个洒水器拿到的都是自己那块 5×5 里的全部盆；
- 湿盆不含「是谁浇的」这个信息：初级台若只盖 3×3，外圈那一圈仍会因为别的原因（先前浇水 /
  雨水 / 服务器机制）继续是湿盆，于是被算成它的覆盖 —— 这就是
  **实测只是上限，不是精确范围**；
- 想拿到有区分度的结论：**等盆变干（收完一茬 / 换新盆）后再 `.stardew 实测范围`**，
  此刻只有真正被浇到的盆是湿的。第一次实测若「矩形内干盆 = 0」，就应当按上限看待。

本次不动判定逻辑（第 163~165 条：非必要不擅改）——这个「全湿无区分度」的观察先落在此处备查，
要加「全湿可疑」提示再议。
