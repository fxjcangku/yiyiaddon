# 208 · 更新提示按渠道筛：正式版玩家不再被推测试版

- 日期：2026-09-22
- 触发（用户原话）：「仓库发布页能不能弄一个测试发布页跟正式版发布页 能智能排序的」
  「一个发布页有两种页面 测试版跟正式版」→ 讨论中发现客户端侧的真 bug
- 相关：[206](206-复盘-简化后勤默认改为关闭（走逐作物四个阈值）.md)（同一天，无关）
- 发布侧铁律同步：`开发习惯.md` 第 245 条（每个 beta 先有台账再发布）

## 一、仓库侧先说清（这一半不用改代码）

GitHub 的 Releases 页**只有一条时间线**，不能真的分出「测试版 / 正式版」两个标签页。原生能给的是：

- 测试版勾 **pre-release**、正式版不勾 → 列表里每条自带 `Pre-release` / `Latest` 徽章，Latest 永远指向正式版；
- 标签命名分家：`v1.0-beta1`（测试）/ `v1.0`（正式）。

排序仍按发布时间，改不了。要「按版本号智能排序的目录」，那是仓库首页之外的产物（脚本 + API 生成），
本轮没做，先记着（用户本轮只要求修 bug）。

## 二、客户端侧的真 bug

`ReleaseCatalog.newest()` 只挑「版本值最大」的发布，**不看渠道**。而版本比较是先比数字、再比后缀
（`ReleaseVersion.compareTo`：`1.1-beta1 > 1.0`），于是出现：

| 玩家装的 | 线上有 | 修复前 | 修复后 |
| --- | --- | --- | --- |
| beta2 | v1.0 | 提示升到 v1.0 ✓ | 一样 ✓ |
| **正式版 1.0** | 1.1-beta1 | **提示去装测试版** ✗ | 不提示 ✓ |
| 正式版 1.0 | v1.1 | 提示升到 v1.1 ✓ | 一样 ✓ |

正式版玩家被推测试包是逆向的：他选正式版就是要稳。反过来测试版玩家必须能收到「正式版发布了」的提示
（`1.0 > 1.0-beta1` 天然成立），这条不能挡。

## 三、改动

- `ReleaseCatalog.newest(json, minecraftVersion, stableChannel)` 加一个渠道参数：`stableChannel = true`
  时跳过所有「版本号带后缀」的发布（`!version.qualifier().isEmpty()`）。
- `UpdateService.stableChannel()`：本机版本号解析出来、且**没有后缀**才算正式版；版本号认不出（开发态）时不筛。
- 状态文案：正式版客户端在线上只有测试版时显示「**暂无正式版本**」（原来是「暂无发布版本」，会让玩家以为没发过）。
- **判据只看版本号，不看 GitHub 的预发布勾选**：勾选是页面装饰、容易漏勾；标签命名是硬规范
  （发布包名 `yiyiaddon-<版本>-<MC 版本>.zip` 也按它匹配）。勾错勾不会导致误推，也不会导致漏推。

## 四、验证

- `.\gradlew build --console=plain -q` → **EXIT=0**。
- 逻辑自检（按上表三行推演）：正式版 + 线上只有测试版 → `latest = null` → 状态「暂无正式版本」、不弹窗；
  测试版 + 线上有正式版 → 照常提示升正式版；正式版 + 更高正式版 → 照常提示。
- **未实机**：复测办法 —— 把 `gradle.properties` 的 `mod_version` 改成 `1.0`（正式版），启动开发客户端，
  首页右上角应显示「已是最新版本 / 暂无正式版本」而**不是**「发现新版本」（线上最新是 `v1.0-beta1`）。

## 五、教训

1. 「挑最新版本」不能只看版本值大小 —— **渠道是产品语义**，正式版玩家不该收到预发布提示；
   这类规则要在解析层一次写清（放在 `ReleaseCatalog` 而不是调用方），否则每个调用点都要记得筛一遍。
2. 判断依据要选**可自检的那个**：预发布勾选在网页上、客户端看不见也无法验证有没有勾对；
   版本号后缀在包名和标签里都能自证，用它的判据不会因操作失误而失效。
3. 顺带把流程固化：`开发习惯.md` 第 245 条 —— **每个 beta 版本先有台账文件再发布，没有台账不许发**
   （发布页正文只能来自台账，靠记忆写必然漏）。
