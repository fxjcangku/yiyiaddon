# 164 复盘：杀戮光环目标选择器「模型变蛋 / 没汉化」（26.2 的两处 API 语义变更 + 随包中文实体名表）

## 一、现象与取证

用户 2026-09-21：「26.2 的杀截光环选择器里面模型都变成蛋了，然后都还是英文；26.1.2 的混淆版
选择器模型没变成蛋，但是也没汉化。」

两个症状、两条线不同组合，说明是**两件互不相干的事**：

| 线 | 模型 | 名字 |
| --- | --- | --- |
| 26.2 | 全变成刷怪蛋 | 英文 |
| 26.1.2 | 正常 | 英文 |

先问清环境（本机有那个客户端的实例目录）：客户端语言 `lang:zh_cn`、单人世界、英文名是
`Zombie / Creeper` 这种**英文原名**（不是 `entity.minecraft.zombie` 键名）。

## 二、名字：客户端根本没有中文实体译名，不是本模组的错

`EntityType#getDescription()` 取的是**客户端当前语言**的译名，本模组没做任何加工。逐项查了那个客户端：

```
C:\...\.minecraft\versions\LunarFox\LunarFox.jar       → lang 下只有 en_us.json 与 deprecated.json
C:\...\versions\26.2\26.2.jar                          → 同样只有两份
mods/*.jar（103 个）                                    → 没有任何一个自带 assets/minecraft/lang/zh_cn.json
资源包（服务端下发的 3.7MB 那份）                          → 有 zh_cn.json，但只有 1337 字节（几十条）
```

即：**这个客户端里根本没有原版中文实体译名**，`getDescription()` 只能回落到 `en_us`（于是显示
`Zombie`）。本模组界面本身全是中文硬编码，实体名混着英文确实难看 —— 所以修法不是「去修客户端」，
而是**本模组自备一份官方中文实体名**。

### 定版口径（`platform/identity/EntityDisplayNames`）

```
客户端给了中文 → 用客户端的
否则          → 用随包中文表
都没有        → 原样返回客户端给的名字
```

「客户端这条确实没译」只有两条**可直接验证**的判据，不靠猜：

1. 客户端给的就是翻译键本身（`entity.minecraft.zombie`）；
2. 客户端给的与**官方英文原名**逐字相同。

其余一律用客户端的名字 —— 资源包改名（服务器把某个生物改成别的叫法）、其它语言的译名、
模组自定义实体，都不会被随包表覆盖。

随包两份表（`src/main/resources/assets/yiyiaddon/lang/`，各约 11 KB）：

- `zh_cn.json` —— 官方 zh_cn 的 `entity.minecraft.*` 共 218 条（26.1.2 的 215 条 + 26.2 的 218 条合并）；
- `en_us.json` —— 用来做上面第 2 条判据的官方英文原名。

两份**同时是合法的语言文件**：客户端语言是中文时，原版界面（物品栏、聊天里的实体名）也跟着中文化。

改的是**显示层**：`KillAuraTargetingPage#title()` 与 `entityDisplayName()`（透视的实体候选复用同一份，
一并生效）。**没动** `EntityIdentifier`（`.id` 识别与 ESP 走它，`EntityIdentity` 会落盘，
改名会让已存的身份数据跟着变）——用户这次只点名选择器。

## 三、模型变蛋：26.2 两处 API 语义变更，都在合成实体这条路上

用项目自带的临时埋点（`// #region debug-point 图标自检`）在独立生产实例里跑，把
`ItemIconCache#renderModel` 整条链路的每一步都落进日志，一次跑出两个根因：

### 3.1 `Entity#getId()` 在 26.2 会抛

```
Caused by: java.lang.IllegalStateException: Tried to access entity ID before ID assignment
	at net.minecraft.world.entity.Entity.getId(Entity.java:438)
	at net.minecraft.client.renderer.item.ItemModelResolver.updateForLiving(ItemModelResolver.java:32)
	at net.minecraft.client.renderer.entity.LivingEntityRenderer.extractRenderState(LivingEntityRenderer.java:309)
```

26.1.2：`private int id = ENTITY_COUNTER.incrementAndGet();` —— **构造即分配**；
26.2：`private int id = 0;`，`getId()` 见 0 就抛。而生物渲染状态抽取会经
`ItemModelResolver#updateForLiving` 读 id（手持物的动画种子），于是**每个生物**的
`extractEntity` 都被包成 `ReportedException` → `renderModel` 返回 false → 记入不可用 → 整列退化到
第 ② 级刷怪蛋。合成实体不进世界、永远拿不到世界分配的 id，所以显式给一个正的固定值
（`SYNTHETIC_ENTITY_ID = 1`；**不能给 0，0 就是「未分配」的哨兵**）。

### 3.2 `create(level, reason)` 在 26.2 会过 `canSpawn`

```
26.1.2: return !isEnabled(level.enabledFeatures()) ? null : factory.create(this, level);
26.2  : return create(level, new EntitySpawnRequest(reason, false));
        → !request.ignoreChecks() && !canSpawn(level) ? null : factory.create(this, level);
```

`canSpawn` 含难度判定：**和平难度下敌意生物直接返回 null**（僵尸、苦力怕…），同样退化成刷怪蛋。
我们只是合成一个「用来拍照」的实体、不进世界，所以改成显式忽略检查：

```java
request.type.create(client.level, new EntitySpawnRequest(EntitySpawnReason.COMMAND, true));
```

### 3.3 验证（独立生产实例，26.2，语言设成 en_us）

```
[probe] 语言选择=en_us zh_cn登记=true 僵尸显示名=Zombie 直查键=Zombie 本模组口径=僵尸
[probe] 截取结果 type=entity.minecraft.zombie    槽位=0 可见=true
[probe] 截取结果 type=entity.minecraft.creeper   槽位=0 可见=true
[probe] 截取结果 type=entity.minecraft.illusioner 槽位=0 可见=true   ← 修前是 ReportedException
[probe] 截取结果 type=entity.minecraft.giant      槽位=0 可见=true   ← 修前是 ReportedException
[probe] 截取结果 type=entity.minecraft.skeleton   槽位=0 可见=true
[probe] 合成实体为 null type=entity.minecraft.player               ← 预期：玩家没有通用渲染器，走玩家头颅
```

- **名字**：客户端英文（`Zombie`）时本模组口径给出 `僵尸`，随包表生效；
- **模型**：先前抛异常的巨人 / 幻术师现在都能截到不透明模型（`可见=true`）；
- 埋点验完即删（`#region debug-point` 全部清除），发布产物里没有探针。

## 四、没动的东西

- 26.1.2 线一行代码没改（它的 `create`/`getId` 语义本来就是我们要的），只跟着加了随包中文表与显示层改动；
- 实体图标的四级回退、刷怪蛋兜底、静态图标表、玩家头颅这些**都没改**；
- `EntityIdentifier` 与 `EntityIdentity` 落盘数据没改（见第二节末尾）；
- 客户端语言设置、资源包策略、`ResourcePackGate` 没碰。

## 五、可复用的两条经验

1. **发现症状在「两条线表现不同」时，先分诊再动手**：这次是「名字」跨线相同（环境问题）、
   「模型」只挂 26.2（API 语义问题），一开始按一个 bug 查会白费功夫；
2. **26.x 里「构造出来的实体」不再是 26.1.2 的那个实体**：id 不再自动分配、`create` 开始过
   `canSpawn`（含难度）。凡是要**合成实体**的代码（图标、预览、试穿）都必须在 26.2 上重新过一遍这两点。
