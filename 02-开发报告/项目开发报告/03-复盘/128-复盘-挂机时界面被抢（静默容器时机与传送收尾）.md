# 128-复盘-挂机时界面被抢（静默容器拦截时机 + 传送收尾不许动玩家界面）

日期：2026-09-19
项目：yiyiaddon（新项目，Fabric 26.1.2 客户端模组）
旧项目对应物：`AutoMinerModule#onOpenScreen :1172-1182`（静默容器，事件挂在 `OpenScreenEvent` 上）
用户原话（三连）：
1. 「开潜影盒子 会抢我鼠标 之前我记得不会的呀 卸货的时候 我挂机都没事」
2. 「好像不是 开容器抢鼠标 是输入指令抢鼠标 回到了游戏界面 我本来是这个界面的 然后卸货触发就把我这个界面关掉了」
3. 「没用 只要传送成功 就会把我的这个页面关闭」
落点：`core/event/EventDispatcher`、`mixin/client/MinecraftSetScreenMixin`、
`mixin/client/LocalPlayerScreenGuardMixin`、`feature/mining/AutoMinerModule`、`MiningContainer#closeContainer`

一句话结论：**一共三把刀在砍玩家的界面** —— 一把是我方静默容器的拦截时机太晚（界面已建、鼠标已交还），
一把是我方容器收尾里的 `player.closeContainer()`，一把是原版传送/过门路径里的两处无条件 `setScreen(null)`。
三把都堵掉了，且都不碰「玩家按 ESC 关菜单」那条路。

---

## 一、第一把刀：静默容器的取消时机太晚（我方）

旧项目 `OpenScreenEvent` 在**界面被设置之前**触发，取消即「界面根本不建」。

本项目迁移时挂在了 Fabric 的 `ScreenEvents.AFTER_INIT` 上，取消方式变成 `client.setScreen(null)`：

```java
// 改前：EventDispatcher
ScreenEvents.AFTER_INIT.register(EventDispatcher::onScreenInit);
...
ClientEvent event = ClientEvent.cancellable(SCREEN_OPEN, screen.getClass().getName());
ClientEventBus.publish(event);
if (event.isCancelled()) { client.setScreen(null); return; }   // ← 太晚了
```

而原版 `Minecraft#setScreen` 的顺序是（`:1168-1185`）：

```java
this.screen = screen;
...
this.mouseHandler.releaseMouse();            // ← 鼠标在这一刻已经交还系统
screen.init(this.window.getGuiScaledWidth(), ...);   // ← 我们的判定挂在 init 之后
```

所以到我们取消时：**界面已经建好、鼠标已经交还**，只能再调一次 `setScreen(null)` 收场 ——
实机感受就是「开箱子时鼠标被抢一下」；更糟的是那次嵌套调用在 `level != null` 时会把
**聊天界面**恢复出来（`setScreen(null)` 内部 `screen = this.gui.getChat().restoreChatScreen()`）。

## 二、第二把刀：我方容器收尾的 `player.closeContainer()`（我方）

`MiningContainer#closeContainer()` 的 javadoc 早就写明「`player.closeContainer()` 会无条件关掉当前
打开的任意 Screen」，但代码里只有 `containerMenu != inventoryMenu` 一层判断。而
`LocalPlayer#closeContainer` 的真身（`:334-341`）：

```java
public void closeContainer() {
    this.connection.send(new ServerboundContainerClosePacket(this.containerMenu.containerId));
    this.clientSideCloseContainer();
}
public void clientSideCloseContainer() {
    super.closeContainer();
    this.minecraft.setScreen(null);            // ← 顺手拍掉玩家任意界面
}
```

卸货阶段「屏幕被占用就定期收容器」那段每 20 刻调一次 → 玩家开着游戏菜单挂机时菜单被拍掉。

**中途我走过一次弯路（记录下来避免重犯）**：先给它加「玩家开着界面就不关」的守卫 ——
结果容器根本没被收掉，留下 `containerMenu.containerId != 0`，使
`isPlayerInventoryClickBlocked()`（`= containerId != 0`）恒为真，
进食时「把食物搬进快捷栏」那一步被永久挡住 → **吃不上**（见 129 号复盘）。
正确做法不是「不关」，而是「**关容器但别动界面**」。

## 三、第三把刀：原版传送路径（两处，跟模块无关）

用户第 3 句「只要传送成功就会关」锁定在这条链上（本服走「重生式传送」）：

```java
// ClientPacketListener#handleRespawn
if (oldPlayer.hasContainerOpen()) {
    oldPlayer.closeContainer();          // ← 第一刀：只要那一刻有容器开着（含我方静默容器）→ setScreen(null)
}
...
this.startWaitingForNewLevel(newPlayer, this.level, levelLoadingReason);
//   → ClientPacketListener#startWaitingForNewLevel（`:1633-1643`）
//   → this.minecraft.setScreenAndShow(new LevelLoadingScreen(...));   // ← 第二刀：无条件替换玩家界面
```

`setScreenAndShow` = `setScreen(screen)` + 立即 `renderFrame(false)`，与玩家界面对冲。

**为什么敢拦掉「加载地形中」**：它只负责画进度条 —— 真实加载推进与「客户端已加载」上报
（`ServerboundPlayerLoadedPacket`）都在 `ClientPacketListener#tick` 里由 `levelLoadTracker` 完成
（`:2777-2780 notifyPlayerLoaded`），与该界面无关。所以「玩家开着界面时」不显示它，不影响传送与落地后发包。

## 四、最终改法

| 位置 | 改动 |
| --- | --- |
| `mixin/client/MinecraftSetScreenMixin`（新增） | 在 `Minecraft#setScreen` **HEAD** 注入：`screen != null` 时发布 `SCREEN_OPEN`，被取消则 `ci.cancel()` —— **整个 `setScreen` 不执行**（界面不建、鼠标不动），回到旧项目 `OpenScreenEvent` 的时机 |
| `EventDispatcher#onScreenOpen`（新增） | 打开前的判定入口；`AFTER_INIT` 只保留「关闭追踪（`SCREEN_CLOSE`）」，不再做取消 |
| `mixin/client/LocalPlayerScreenGuardMixin`（新增） | 两个 `@Redirect` 精确拦原版内部关界面的调用：`clientSideCloseContainer`（容器收尾）与 `handlePortalTransitionEffect`（过门），改走下面的判定 |
| `EventDispatcher#closeScreenUnlessPlayerOwned`（新增） | 目标是 `setScreen(null)` 时：当前是**玩家自己开的非容器界面**（游戏菜单 / 聊天 / 我们自己的控制台）→ **保留**；容器界面、死亡界面 → 照旧关 |
| `AutoMinerModule#onOpenScreen` | 挖矿运行中且 `mc.screen != null` 时，取消 `LevelLoadingScreen`（即上面第三把刀的第二刀）；其余判定（放行背包、取消容器界面）不变 |
| `MiningStateMachine` 卸货 / 补给两处 | 「非容器界面就卡住 + 每 20 刻收容器」的判据放过 `PauseScreen`：不必关它，也不该因为它卡住流程 |
| `MiningContainer#closeContainer` | 撤掉中途那层「玩家开着界面就不关」的守卫，恢复直接调用（保护职责全部上移到 `LocalPlayerScreenGuardMixin`），javadoc 记明原因 |

`SilentContainerClose`（中途为「关容器但不动界面」加的作用域标记）**已删除** —— 被更精确的 `@Redirect` 取代。

## 五、边界（明确写清，避免预期错位）

1. **玩家按 ESC 关菜单不受影响**：走 `Screen#onClose` → `setScreen(null)`，不经过上面两个 `@Redirect`，
   也不经过 `SCREEN_OPEN`（那是「开」），所以不会被吞。
2. **死亡界面照旧关**（显式排除），否则重生后死亡界面会赖着不走。
3. **容器界面照旧关**（`closeContainer()` 的原有语义不变）。
4. **没开界面时一切照旧**：`LevelLoadingScreen` 正常显示（原生进度条），
   静默容器仍由 `SCREEN_OPEN` 在 `setScreen` 头部取消，容器数据照旧走 `mc.player.containerMenu`。
5. 原版其它关界面路径（如死亡重生时的 `ClientPacketListener:1340`）**未改动**。

## 六、验收

`.\gradlew.bat build --console=plain` → BUILD SUCCESSFUL；客户端日志无 Mixin 注入报错。

实机（用户确认「牛逼啊 可以了」）：
- 开着游戏菜单挂机 → 卸货 / 补给 / 前往野外**不再抢鼠标、菜单不被关**；
- 自己按 ESC 开关菜单正常；
- 卸货 / 补给照常静默跑完。
