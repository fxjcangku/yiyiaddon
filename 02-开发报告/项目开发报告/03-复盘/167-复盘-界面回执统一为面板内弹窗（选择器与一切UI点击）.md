# 167-复盘-界面回执统一为面板内弹窗（选择器与一切 UI 点击）

## 一、用户原话与诉求

> 「然后我发现很多选择器 点加减都会聊天框都会发送提示  我就是想改成能不能所有选择器都发送在聊天框同步 添加或者减去」
> → 「我在想要不要全部做成弹窗的 跟状态栏一样提示过一会就消失的」
> → 「A 选择器全部都一样」
> → 「凡是 ui 点击都在 ui 里面弹窗 比如收藏模块 就弹已收藏 xxx 模块名字」

前两句追问把方案从「聊天框同步」推到了「面板内弹窗」，最后一句**把范围从选择器扩到一切界面内点击**：

1. 所有选择器的**加 / 减都必有回执**，且口径一致；
2. 回执形态**不再走聊天框**，改成**面板内顶部弹窗**（跟状态栏一个观感，过一会儿自己消失）；
3. **全部选择器统一**，不留个别走老路的；
4. 再扩一层：**凡是 UI 点击都在 UI 里弹窗**，且弹窗要**报出被操作对象的名字**（收藏就报模块名）。

## 二、取证（先查清「为什么聊天框回执等于没反馈」再动手）

| 现状 | 取证位置 | 结论 |
| --- | --- | --- |
| 加减只发聊天框 | 原 `SelectorScreen#notifyAction` → `ClientChat.send` | `ClientChat` 走的是原版聊天栏 |
| 面板开着时看不到 | 原版行为：`Screen` 激活期间整个 HUD 被隐藏 | 聊天栏与行动栏**都不可见**，回执实际是「关掉窗口之后才看到」 |
| 连点几下刷一屏 | 两栏选择器一次会连点十几下 | 关窗瞬间一次性涌出，既吵又对不上是点哪一下 |
| 已有现成的面板内通道 | `ui/render/TooltipLayer#notify` | `NOTICE_HOLD_MS = 1900L` 毫秒自动消失、重复调用**只刷新同一条不堆叠**、跨帧存活、支持 `§` 颜色码 |
| 所有面板都能画它 | `PanelScreen` / `ClickGuiScreen` / `ModuleScreen` 的 `beginFrame()` + `draw()` | 命中即可见，不需要每个窗口各接一次 |
| 还有第三条隐藏通道 | `CommandMessageFormatter.of/sendLine` 最终也走 `ClientChat.rawComponent` | 星露谷、自动农场、自动矿挖的点位 / 区域类回执走的也是聊天框 |

结论：不是「换个文案」，而是**换通道**——从「世界内才可见的聊天栏」换到「面板内必然可见的顶部弹窗」。

## 三、方案定案（A 方案）

用户在同一条需求上抛了三个选项（① 全部同步进聊天框 ② 全部改面板内弹窗 ③ 各模块自便），最后拍板 **A：全部改面板内弹窗，聊天框不再发，批量操作只发一条汇总**。

理由记录（供后续判断同类问题复用）：

- 选择器是**面板内**的连续动作，反馈必须落在**同一个视野里**才有意义，聊天框在面板开着时等于不存在；
- 加减一次只改一条，**不需要留痕**，1.9 秒的弹窗刚好；真正的「记录」是右侧已选栏本身；
- 批量（组头全选 / 清空）**逐条发会把弹窗刷成走马灯**，只发一条 `N 项` 汇总。

## 四、改动清单

### 1. 新建 `ui/SelectionReceipt.java` —— 唯一出口 + 唯一文案

所有选择器回执都调它，不允许再各自拼字符串（开发习惯第 169 条「同源口径：同一句话只有一处」）。八个公开静态方法覆盖目前全部语义：

| 方法 | 文案 | 用在哪 |
| --- | --- | --- |
| `added(name)` | `§7已添加 §a<名>` | 两栏选择器加入一条、文本名单添加 |
| `removed(name)` | `§7已移除 §c<名>` | 两栏选择器移除一条、名单逐项移除 |
| `addedMany(count)` | `§7已添加 §aN 项` / `§e没有可添加的条目` | 组头「全选」 |
| `removedMany(count)` | `§7已移除 §cN 项` / `§e没有可移除的条目` | 组头「清空」 |
| `cleared(count)` | `§7已清空 §cN 项` / `§e本来就是空的` | 行尾 ↻ 清空本行 / 本组已选 |
| `toggled(on, name)` | `§7已启用 §a<名>` / `§7已停用 §c<名>` | 一行一个 ✓ / ✗（容器类型、装备附魔目标） |
| `selected(name)` | `§7已选择 §a<名>` | 单选窗（挑装备 / 换作物 / 挑菜单物品） |
| `reset()` / `reset(count)` | `§7已恢复默认` / `§7已恢复默认 §aN 项` | 行尾 ↺ 复位 |
| `favorited(added, name)` | `§7已收藏 §a<名>` / `§7已取消收藏 §8<名>` | 模块行右侧星标 |

两个内部约定：

- `clean(name)`：**先剥掉 `§` 颜色码再回显**。条目标题常自带配色（如 `§7名称 §8- §7描述`），直接回显会把弹窗染花。
- `notify(text)`：**单一出口**，将来换提示方式（加图标 / 加音效 / 挪位置）只改这一行。

### 2. `ui/screen/SelectorScreen.java` —— 所有两栏选择器的共同父件

23 处调用方（18 处 `new SelectorScreen(...)` 多选 + 5 处 `SelectorScreen.pick(...)` 单选）全部经由这一个类，改一处即全覆盖：

- 删除 `notifyAction(...)` 私有方法，`ClientChat` import 换成 `SelectionReceipt`；
- [`toggle(Entry, boolean)`](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/screen/SelectorScreen.java#L727-L743)：加入走 `added`、移除走 `removed`；被准入判定（`addGuard`）拒绝时**不改名单、只弹拒绝原因**，仍是弹窗；
- [`toggleAll()`](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/screen/SelectorScreen.java#L600-L627)：新增 `int changed` 计数，**整组只发一条汇总**；拒绝原因若有则先弹一条，再弹汇总（0 项时由回执自己说明原因，例如「没有可添加的条目」）；
- 类注释里「交互与文字照旧项目」一段同步改写，说明回执通道已换、唯一出口在哪。

单选模式 [`pickRow`](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/screen/SelectorScreen.java#L704-L713) **仍在调用方发回执**：单选窗点行即关窗，只有调用方知道这次选择的业务含义（是「换装备」还是「换作物」），统一在父窗口的 `onPick` 回调里发 `selected(...)`，不重复。

### 6. 空名单不再「静默 return」

`VisionSelectors` / `KillAura*` 的行尾 ↻ 原本写成 `if (isEmpty()) return;`，好处是不写盘，坏处是**点了完全没反应**（正是用户抱怨的那种手感）。改法：

```java
int count = size();
if (count > 0) {
    清空();
    落盘();
}
SelectionReceipt.cleared(count);   // count == 0 时由回执自己说「§e本来就是空的」
```

**空名单时状态不动、不写盘，但必有一句回音。**

## 七、补记（同日追加）：凡是 UI 点击都在 UI 里面弹窗

### 1. 用户口径

> 「凡是 ui 点击都在 ui 里面弹窗 比如收藏模块 就弹已收藏 xxx 模块名字」

这句话把第四节的范围**从「选择器」扩到「一切界面内点击」**，并要求弹窗里**带上被操作对象的名字**（收藏就报模块名，添加就报条目名）。

### 2. 判据：怎么知道「这一句是玩家点出来的」

不去逐个标注调用点，而是问一句客观事实 —— **此刻是否停在扩展自己的界面里**：

新增 [`SkiaScreen#isOpen()`](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/render/SkiaScreen.java#L43-L56)：

```java
public static boolean isOpen() {
    return Minecraft.getInstance().screen instanceof SkiaScreen;
}
```

`SkiaScreen` 是所有自绘界面的基类（`PanelScreen` 一族 + `ClickGuiScreen` + `ModuleScreen`），**它们全都会在帧末调 `TooltipLayer.beginFrame()` / `draw(...)`**，因此这个判据为真时弹窗必然画得出来。这一个判据同时把两种来源分得干干净净：

| 来源 | 界面开着？ | 走哪条 |
| --- | --- | --- |
| 面板里点按钮 / 点加减 / 点星标 | 是 | 面板内弹窗 |
| 指令、快捷键、进世界后台补开模块 | 否 | 聊天栏（原样） |

### 3. 新出口：`ClientChat#ui`

[`ClientChat`](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/core/ClientChat.java) 从「一条聊天出口」变成**两条**，分派判据唯一：

- `send(moduleName, text)` —— 恒定进聊天栏。给**世界情报**（管理员检测结果、资源包提取进度）、**后台播报**（进世界补开模块）、**多行卡片**（`CommandMessageFormatter`）用。
- `ui(moduleName, text)` —— 「玩家点出来的」一句回执。界面开着 → 面板内弹窗；否则退回聊天栏。判断与发送都在 `mc.execute` 里做，与 `send` 同样线程安全。

**为什么不能直接在 `send` 里一刀切**：面板内弹窗是一行居中提示（约两秒淡出、**不堆叠**、**不进聊天历史**）。把 `send` 全部改道会出两个真问题 ——
1. `CommandMessageFormatter` 的**多行卡片**（标题 + 字段 + 状态）画不进单行弹窗；
2. 「管理员检测到隐藏管理员」「还差 3 项没配好」这类**需要留在聊天记录里翻看**的内容，两秒后消失就找不回来了。

所以「改道」只给单行回执，且**只给玩家点出来的那些**。

### 7. 补记（同日追加）：长文案不撑爆面板 + 会不会刷屏

用户追问：「那么多文字 会不会刷屏啊 检测资源包按钮 ui 会不会被撑爆」。两个问题分开答，一个答「不会」，一个查出真漏洞。

**刷屏：不会。** 「检测 / 更新资源」一次完整跑下来，`announce(stage, ...)` 一共 11 个阶段
（check / autoSession / automaticRefresh / retry / cache / download / reuse / loading / fallback /
parsing / parsed / fail），每个阶段由 `ANNOUNCED` 按 `模块名/阶段` 去重，**一次运行最多各出一条**；
开头那张多行卡片也是合并成一条消息发的（`CommandMessageFormatter` 的既有口径）。
面板内弹窗那侧更是天然不刷屏：`TooltipLayer#notify` 重复调用只替换同一条、1.9 秒自动淡出，**不堆叠**。

**撑爆：原先真的有这个漏洞，已修。** `drawNotice` 对宽度**没有任何上限** ——
`boxWidth = measure(text) + 2 × pad`，而 `boxX = max(pad, (viewport - boxWidth) / 2)`，
一旦文案宽过视口，框就从左侧贴边、向右侧**直接溢出屏幕**。上一节把字号从 10 提到 12 又把这个余量收窄了两成，
而本轮恰好把一批长文案（ID 识别的「已添加物品 ▸ 名称 ▸ 文件名」、`恢复默认失败：` + 异常描述等）接进了这条通道。

修法（`TooltipLayer#noticeSizeFor`）：**从 12 起量，放不下就逐档缩字号（步长 0.5，下限 9），不截断**。

```java
private static float noticeSizeFor(String text, float viewportWidth) {
    float limit = Math.max(NOTICE_PAD_X * 2f, viewportWidth - NOTICE_PAD_X * 2f);
    float size = NOTICE_SIZE;
    while (size > NOTICE_MIN_SIZE
        && MinecraftText.measure(text, size, false) + NOTICE_PAD_X * 2f > limit) {
        size = Math.max(NOTICE_MIN_SIZE, size - 0.5f);
    }
    return size;
}
```

- **缩字号而不是省略号**：回执本身就是一句话，截一半等于没说清楚（见 166 号复盘「宁愿简洁一点也不出现 ...」）；
  框会跟着变矮变小，但话是完整的。
- **下限 9**：与 `HomePage` 自适应字号同一收底值；视口是**整屏设计宽**而非面板宽，正常单行文案远远够用，
  实测这条分支几乎不会被走到，纯粹是兜底。
- 框的绘制尺寸全部改为按 `size` 算（宽 / 高 / 文字基线），因此不存在「缩了字还按原框画」的错位。

两侧 `compileJava` EXIT=0。

### 8. 补记（同日追加）：ID 识别「自动保存模式」原本一条提示都没有

用户追问：「自动保存模式不弹窗提示吗」。查下去是真的漏了，而且是**最该有的那种漏**。

**漏在哪。** `IdIdentifyModule.report()` 走的是 `ClientChat.send`，而识别的两个触发口里有一个是
**模块页上那颗开关**（`applyEnabled(true)` → `identifyByMode()`）。点开关时面板正开着：

- 识别结果发聊天栏 → 看不见；
- 而「开启即识别、识别完自关」这条链路会让 `tryEnable` 走 `module::onEnable` 自关的分支，
  连 `已开启` 都不播报（`suppressEnableAnnounce` + 自关早退）。

两件事叠起来 = **在自动保存模式下点 ID 识别的开关，一个字都看不到**。失败分支
（`主手和副手都是空的` / `识别失败` / `准星没有指向有效方块`）也是同样命运。

**怎么改。** 不能简单地把 `send` 换成 `ui`：`report()` 会发 2~3 行（主行 + 保存文件 + 状态快照），
逐行转弹窗会被后一条盖掉，玩家只看得到最后一行 —— 那等于把「保存到哪个文件」这个关键信息丢了。
所以按判据分叉：

```java
if (SkiaScreen.isOpen()) {           // 模块页点开关：压成一条
    ClientChat.ui(MESSAGE_MODULE, headline + " §8▸ " + outcome + 快照段);
    return;
}
// 指令 .id：玩家在世界里，照旧发多行卡片（要留在聊天记录里）
ClientChat.send(headline); ...
```

弹窗形态：`✓ 已识别物品 ▸ 金锭 ▸ 已保存 xxx.json`（方块再加 `▸ 状态快照 yyy.json`）。

**同一批还修了 `IdConfigModule`** —— 「ID 配置」面板上那 23 处按钮回执（刷新、识别物品、
识别准星方块、逐条删除、打开数据目录失败、六种清空、清理失效目标）全部由
`ClientChat.send` 改走 `ClientChat.ui`。它们 100% 是面板按钮触发的，属于本报告第七节判据里
最典型的一类，之前同样是一条都看不见。其中「识别准星方块」也是两条（稳定记录 + 状态快照），
按同一套办法在界面开着时压成一条。

**顺带修的注释/文案**：`IdResultScreen` 两处「反馈走聊天栏」的注释、
`IdentityModulePage` 使用说明里「自动保存…聊天栏播报保存结果」一句，都同步改成实际行为。

**没动**：`IdIdentifyModule.pruneSilently()`（进服后台清理失效目标）—— 不是玩家点出来的，
留在聊天栏。

两侧 `compileJava` EXIT=0。
