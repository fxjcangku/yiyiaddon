# 复盘：广播只投给「发送那一刻在线」的玩家（消息不再有缓存假象）

- 日期：2026-09-21
- 触发：用户问「是不是有消息缓存，别的玩家进去能看见旧消息」
- 结论：**没有缓存**，是管理员广播的投递口径问题，已按用户选定口径（严格只发当时在线）改掉并线上验收

## 一、现象与排查

用户发了一条广播（`hihi`）后，另一个玩家进服也看到了它，怀疑「消息有缓存」。

| 检查项 | 结果 |
| --- | --- |
| 接口缓存 | 无。所有 JSON 响应带 `Cache-Control: no-store`（`worker.js` 的 `jsonResponse`），客户端也不落地消息，只按 3 秒轮询即画 |
| 库里的 `hihi` | 两条都是**广播行**（`target_uuid IS NULL`、`target_name = 所有人`，18:55:11 / 19:43:33） |
| 投递规则 | `/api/messages/poll` 的广播分支：`m.target_uuid IS NULL` 且「消息时间 ≥ 该玩家 `first_seen`」且「该玩家没有已读记录」→ **注册早于这条消息、但当时不在线的老玩家，下次进服第一次轮询就会补收到** |

所以「别的玩家看见旧消息」不是缓存，是**广播对离线玩家的补投**。

## 二、口径定稿（用户 2026-09-21 选定）

> 广播 = 只发给**发送那一刻在线**的玩家；离线玩家永远不补收。私信仍保留「等对方上线投递」。

在线判定沿用全站唯一口径：`users.last_heartbeat >= now - HEARTBEAT_TIMEOUT`（90 秒；心跳写库有 30 秒节流，窗口必须大于节流周期 + 心跳间隔）。

## 三、改动

1. **新列 `messages.target_uuids`**：广播行在发送时固化接收名单，逗号分隔并带头尾逗号（`,u1,u2,`），
   用 `INSTR(target_uuids, ',' || uuid || ',') > 0` 精确匹配，避免 uuid 前缀误撞。
   `NULL` 表示「不限定接收人」，只留给玩家的跨服频道消息（聊天记录补收，维持原样）。
2. **`/api/messages/send`**：
   - 传 `target_uuid` → 私信单行、`delivered = 0`，等收件人上线；
   - 不传 → 广播：先查在线名单写进 `target_uuids`，再插一行；返回 `delivered` 人数，
     无人在线时返回「当前无人在线，消息未投递」（名单为空串，这条谁都不投）。
3. **`/api/messages/poll`** 广播分支加一道条件：`target_uuids IS NULL OR INSTR(...) > 0`。
   `first_seen` 闸门保留（对 `NULL` 那批玩家的跨服频道消息仍然必要）。
4. **面板**：广播发送后若 `delivered === 0` 弹「当前无人在线，消息未投递」，不再让人误以为已送达。
5. **迁移**：`sql/migrations/migration-2026-09-21-message-target-uuids.sql`；`sql/schema.sql` 同步补列；
   `ensureMessagesTargets()` 在消息接口首次被调用时自动补列（沿用 `ensureCommandActivityTable` 的自愈写法）。
6. **Service Worker** 缓存名 v6 → v7（面板 JS 改了，两处副本同步：`sw.js` + `worker.js` 内联副本）。

## 四、线上执行与验收（2026-09-21）

| 步骤 | 结果 |
| --- | --- |
| `ALTER TABLE messages ADD COLUMN target_uuids TEXT`（远程 D1） | 成功，`PRAGMA table_info` 已看到该列 |
| `wrangler deploy` | 成功，Worker 版本 `9b216d4e-e15d-4d54-adc5-cb7d7d35d9e7` |
| 造一条只投给 Phoera1n 的广播（`target_uuids = ',3a943890-…,'`） | — |
| 名单内玩家 poll（Phoera1n） | `count = 1`，**命中**该消息 |
| 名单外玩家 poll（Estrela03，`first_seen` 早于该消息） | `count = 0`，**未命中** |

名单外那位是老玩家（`first_seen` 早于消息），他能被排除**只能**是因为名单条件——`first_seen` 闸门在这条上不成立，
所以这是一次真正打到新逻辑的验收，不是被别的闸门挡住而「看起来对」。
