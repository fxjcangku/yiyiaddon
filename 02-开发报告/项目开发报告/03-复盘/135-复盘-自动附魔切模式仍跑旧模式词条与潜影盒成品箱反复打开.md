## 2. 缺陷一：切到「自定义附魔」后仍按「原版附魔书」的词条干活

### 2.1 根因（第 167 条取证）

词条列表由 `rebuildActiveTasks()` 构建，旧实现把**13 个多选组一次性全并进来**（旧项目 `AutoEnchantBook:1722-1726` 的同源写法）：

```java
List<List<String>> enchantmentGroups = List.of(
    SWORD_ENCHANTS, AXE_ENCHANTS, BOW_ENCHANTS, ARMOR_ENCHANTS, OTHER_ENCHANTS,   // CUSTOM 模式可见的 5 组
    VANILLA_ARMOR_ENCHANTS, … VANILLA_COMMON_ENCHANTS);                            // BOOK 模式可见的 8 组
```

而目标模式只决定**界面显示哪一页**（`EnchantConsoleScreen#tabsFor`）：BOOK 模式只有「原版附魔分类」页，CUSTOM 模式只有「自动附魔分类 / 自定义附魔」页。于是两模式的勾选**互不覆盖、共用同一份 `enchantSelection`**，`rebuildActiveTasks` 又全并进去，结果：

- 在 BOOK 模式勾的「保护 IV / 锋利 IV…」一直留在 `enchantSelection` 里；
- 切到 CUSTOM 后 `activeTasks` = 原版勾选 + 自定义勾选；用户「自定义那边一个都没勾」时，任务列表**非空**（全是原版词条），模块照常启动，继续刷原版词条 → 用户看到的「切了模式还在附魔原版附魔书的附魔书」。

第二个叠加点：旧项目 `目标模式.onChanged` 只做 `同步模式分组(); 刷新模式界面();`（**只重排界面，不动运行态**），所以「模块还开着就切模式」时，`activeTasks` 连重建都没有，仍是上一次激活时建的那份。

### 2.2 修复

| 位置 | 改动 |
| --- | --- |
| [rebuildActiveTasks](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/enchant/fsm/EnchantStateMachine.java#L2198-L2233) | 按当前模式取组：`BOOK` → `EnchantSettings.BOOK_GROUPS`（8 个原版组）；`CUSTOM` → `EnchantSettings.CUSTOM_GROUPS`（5 个扩展组）；`GEAR` → 空（它只认「装备附魔配置」）。`自定义附魔目标` 文本项只在 CUSTOM 并入（该页只在 CUSTOM 可见） |
| [tick 入口](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/enchant/fsm/EnchantStateMachine.java#L428-L441) | 运行中检测到 `目标模式` 变化 → [`restartForModeSwitch`](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/enchant/fsm/EnchantStateMachine.java#L319-L343)：停杀戮光环 / 停寻路 / 收掉可能还开着的静默容器 / `active=false`，下一帧经 `ModuleManager` 静默关 + 带播报开，走一遍既有的「自检 → 启动链」 |
| 激活链收尾 | `activateGear` / `activateBook` 记下 `lastTargetMode`，因此只有「激活之后又切模式」才触发重启，不会重复重启 |

**为什么是重启而不是就地改状态**：三模式互斥，词条列表、GEAR 的装备队列 / 铁砧计划、容器相位都是模式私有运行态；重启直接复用已有的自检与激活链（第 169 条：同一份逻辑不写两遍），新模式点位没配好时照旧给出「还差 N 项没配好」。

## 3. 「原版装备附魔」是否同源问题（用户要求顺带检查）

- **词条串模式：不成立。** GEAR 全流程只读 `gearProfile`（`gearEnchantConfig`）与 `gearTargetItem`，不碰 `activeTasks`（`activeTasks` 的使用点只有 `rebuildActiveTasks` / `tickChecking` / `tickStoring` / 启动播报，全在 BOOK·CUSTOM 流程）。所以 GEAR 不会继承另两个模式的勾选。
- **切模式不生效：成立，与缺陷一同源。** 旧实现下「模块开着 → 从 GEAR 切到 BOOK/CUSTOM」或反向切换时，`tick` 仍按 `state` 继续跑旧模式的处理器（例如 BOOK 激活态切到 GEAR 后，`tickIdle` 照旧把流程推去附魔书循环；此时 `gearTargetItem == null`，顶部那条 GEAR 断点恢复校验被跳过，**不会空指针**，但模式确实没生效）。本次的 `restartForModeSwitch` 一并覆盖这三种切换方向。

## 4. 缺陷二：成品箱是潜影盒时反复发包打开

### 4.1 根因（第 167 条取证）

[EnchantContainer#chestMenuOpen](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/enchant/service/EnchantContainer.java#L236-L250) 旧实现只认 `ChestMenu`：

```java
return mc.player != null && mc.player.containerMenu instanceof ChestMenu;
```

而 26.1.2 里潜影盒的菜单是**独立的** `net.minecraft.world.inventory.ShulkerBoxMenu`（`extends AbstractContainerMenu`，**不是** `ChestMenu` 的子类；已用 `01-开发参考库/Minecraft原始源码/net/minecraft/world/inventory/ShulkerBoxMenu.java` 与官方 `MenuType.SHULKER_BOX` 注册行验真）。于是：

1. 箱子 / 陷阱箱 / 木桶开出 `ChestMenu` → `chestMenuOpen()==true` → 正常；
2. 潜影盒做出品箱 → 界面其实已开，`chestMenuOpen()` **永远 false** → 各 `tickXxx` 停在 `guiPhase==0` 的「发包开箱」分支 → **每 tick 重发一次开箱包**（实机表现就是「反复发包打开」）。

同样的写法还有 6 处 `(ChestMenu) mc.player.containerMenu` 强转 + `handler.getRowCount() * 9` 数容器槽位（`getRowCount` 只有 `ChestMenu` 有），潜影盒下不只是判不出，强转本身就会抛 `ClassCastException`。

### 4.2 修复

| 位置 | 改动 |
| --- | --- |
| [chestMenuOpen](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/enchant/service/EnchantContainer.java#L236-L250) | 新增 `isBlockContainerMenu(menu)` = `ChestMenu \|\| ShulkerBoxMenu`，箱子 / 陷阱箱 / 木桶 / 潜影盒统一认 |
| [containerSlotCount](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/feature/enchant/service/EnchantContainer.java#L111-L121) | 新增「容器本体槽位数 = `slots.size() - 36`」，取代只能对箱子用的 `getRowCount() * 9`；`containerSlotOf` 改为复用它（同一来源，第 169 条） |
| 状态机 6 处 | `ChestMenu handler = (ChestMenu) mc.player.containerMenu;` → `AbstractContainerMenu handler = mc.player.containerMenu;`；`handler.getRowCount() * 9` → `container.containerSlotCount(handler)`。涉及 `tickStoring` / `tickRestocking` / `tickGearTakeGear` / `tickGearRestockLapis` / `tickGearTakeAnvil` / `tickGearStoreOutput`；`ChestMenu` 导入随之删除 |

覆盖范围：**五个箱类点位全适用**（书本箱 / 青金石箱 / 成品箱 / 装备箱 / 铁砧箱），不只成品箱；大箱子（54 槽）与木桶（27 槽）数值与改前一致。

自动箱子模块不受影响：它走 `ContainerAccess.openMenu()`（判 `containerId != 0`）+ `slot.container != 玩家背包`，本来就与菜单具体类型无关。
