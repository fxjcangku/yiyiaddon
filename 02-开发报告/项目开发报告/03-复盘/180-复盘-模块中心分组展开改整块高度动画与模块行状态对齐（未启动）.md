# 复盘：模块中心分组展开改成「整块高度动画」 + 模块行状态标记对齐与文案统一（未启动）

日期：2026-09-21

## 一、用户需求

1. 「ui分组展开 不流畅有卡顿 模块页面」——模块中心点开分类头时的手感要顺；
2. 「星露谷钓鱼 跟星露谷农场这里没对齐 统改成未启动」——同一分组下两行的右侧状态没对齐
   （截图里「星露谷钓鱼」那行的蓝色星标与红色圆点叠在一起），两行文案也统一成「未启动」。

## 二、取证（改之前先定位到行）

| 现象 | 取证位置 | 结论 |
|---|---|---|
| 展开「先占位、再滑动」 | `ModuleCenterPage#rebuildRows`（旧版：`if (!EXPANDED.contains(id)) continue;` 把成员行**插进**清单）+ `#seedRowShift`（新行抬 `ROW_INSERT_LIFT = 14`） | 块的高度**立刻**占满，块下面的行再滑过去让位 —— 同一件事被拆成两段动作 |
| 动画途中几行闪悬停 / 缩一下 | `CardPage#setCardCount`（`keep = min(旧长度, 新长度)`，**按下标**原地保留 `hoverSpring` / `PressState`） | 插入行后，被插入位置**之后**的每一行都拿到了别人的动画状态 |
| 两行状态没对齐 | `ModuleRow#drawRow` 旧算式 `badgeX = arrowX − ARROW_GLYPH − BADGE_GAP − 文字宽` | 位置跟着**文字宽**走：「未启用」（3 字）与「无法使用」（4 字）左缘差一个字宽 |
| 星标与圆点叠在一起 | 同文件 `STAR_RIGHT_INSET = 96`：星标右缘 = 右 − 88.5，而 4 字文案的徽章左缘 = 右 − 93 | 宽文案直接**顶进星标**（截图证据：两个图形重叠） |

文案来源：`ModuleRow#drawRow` 旧默认值「未启用 / 已启用」；星露谷钓鱼的覆写见
`StardewFishingModule#statusBadgeText()`（166 号复盘补记那一条）。

## 三、改法一：分组展开 = 折叠块的整块高度动画

**模型**：一个分类 = 一个「折叠块」（块头 = 分类头，块内容 = 页面入口行 + 模块行）。
成员行**始终留在清单里**，占的高度 = 展开度 × 内容高；展开度是每块一根弹簧
（`groupReveal`，`Spring.critical(0.28)`）。

| 位置 | 处置 |
|---|---|
| `ModuleCenterPage#rebuildRows` | 收起的分类不再 `continue` 跳过成员行；登记 `blockSizes`（块行数）与每行的块 id |
| 新增 `#layoutSlots` | 一次排出「行顶边 + 块窗口底边 + 行的展开度」三份数组（下标同 `rows`）：绘制、命中、滚动上限都只读这一份（第 169 条同源口径） |
| 新增 `#groupReveal` / `#ensureReveals` | 每块一根展开度弹簧；**首次出现直接落定**目标值（进页面就是展开态，不补播入场动画，与 `CollapsibleSection#expanded` 同口径） |
| `#drawCard` | 展开度 0 → 不画；展开度 < 1 → `clipRect` 压到块窗口内 + `alpha × 展开度` 淡化（与折叠区同一口径）；半展开的行不参与悬停（指针坐标传行外值，浮层不会在路上闪出来） |
| `#indexAt` / 新增 `#hittable` | 展开度 < 1 的行不参与命中（只能点到看得见的部分，与 `CollapsibleSection` 一致） |
| `#update` | 先推进展开度与行位移弹簧 → `layoutSlots()` → 再让基类做悬停命中：同一帧画面与命中读同一份几何 |
| `#seedRowShift` / 新增 `#rememberTops` | 位移量改成「上一次的静态顶边 − 这一次的静态顶边」**逐行比较**（旧版按「下标 × 节距」推，折叠动画进行到一半时装配清单会算错）；新出现的行不再铺位移（由展开动画带出来） |
| `#rowKeys`（块 id + 内容标识） | 修掉旧版按模块 id 取标识的隐患：同一模块同时在「常用」块与自己的分类里时是两行，旧写法两行共用一根位移弹簧 |

**顺带修掉的**：展开 / 收起不再改变行数 → `CardPage` 的悬停 / 按下状态不再串行（第二节第 2 行那条）；
收起也有出场动画了（旧版是「被收起的行直接消失」，见 166 号复盘第十节自述）。

## 四、改法二：状态标记对齐 + 文案统一「未启动」

| 位置 | 处置 |
|---|---|
| `ModuleRow#stateX`（新增） | 状态标记左缘 = 星标右缘 + 10，**只由行宽决定**；同页所有行的圆点与文字落在同一条竖线上 |
| `ModuleRow#stateRightLimit`（新增） | 状态文字的最右边界（箭头左边再留一格）；文案比预算还长时**整段不画**，绝不压到箭头 |
| `ModuleRow#STAR_RIGHT_INSET` | 96 → **112**：给最宽的一档文案让位。算式：星标右缘（右 − 104.5）+ 10 = 状态左缘（右 − 94.5），最宽的「点击进入」（4 字，实测 56）右缘停在右 − 38.5，箭头占右 − 20.5 ~ 右 − 7.5，仍有 18 像素余量 |
| `ModuleRow#drawRow` 默认文案 | 「未启用」→「**未启动**」（关着的行统一读这个；开着的仍是「已启用」） |
| `StardewFishingModule` | 撤掉 `statusBadgeText()` 覆写（连带删掉 `STATUS_BADGE` 常量与相关注释），改走默认口径；「这个模块还不能用」仍由行注释「开发中，暂时无法使用」与点击后的拒因说明表达 |
| `Module#statusBadgeText` / `ModuleEntry#statusText` | 覆写点保留（虚拟方法，现在没有子类覆写），javadoc 改成不再引用已撤掉的用法 |

## 五、影响面与「没动」的部分

## 八、踩坑与修复（用户实机截图暴露）：模块中心的**行全部不画**

**现象**：用户截图「怎么都消失了？」—— 模块中心内容区整片空白，连空状态文案都没有
（说明行数是有的，只是每一行都被跳过）。

**根因（坐标基准混用）**：`ModuleCenterPage#drawCard` 里写成

```java
float clipBottom = slotClipBottom[index];   // 相对内容原点：块头是 24、第一行是 0
if (clipBottom <= y) return;                // y 是画布绝对坐标（内容区顶 ≈ 100 以上）
```

`slotTop / slotClipBottom` 都是「相对内容原点」的量，而 `y` 来自 `cardY`（已含 `originY`）。
两者直接比大小 → 恒为「在窗口外」→ 全页行 return，什么都不画。

**修复**：只比同一套坐标里的**可见高度** —— `visible = slotClipBottom − slotTop`（相对量之差），
`visible <= 0` 判「还没露出来」、`visible < 行高` 判「半露需要裁剪」，`clipRect` 也用这个高度，
再也不与画布坐标相减。同一 bug 类别在本页只此一处：`indexAt` / `stickyIndex` / `onClick` 里的
绝对坐标都是先 `originY + slotTop` 再比较，口径一致。

**回归**：`.\gradlew build --console=plain -q` → **EXIT=0**，产物
`build/libs/yiyiaddon-1.0-beta1-personal+26.1.2.jar`（20:00:54）；实机复测待用户重启客户端后进行。

**教训（进检查表）**：新增「相对排版量 + 画布坐标」两套数值时，先写清每个量的基准，
再做比较或相减；本轮静态自查只查了「几何是否同源」，漏了「基准是否一致」。

## 九、第二轮：顿挫的真因（JFR 实测）与三处修复

**用户复现描述**（2026-09-21）：「模块中心下拉卡顿严重 有顿挫感觉 不流畅」「特别是展开多个分组的时候
挤满了画面…滑块就在抖动」。注意「滑块抖动」是**新线索**：滚动条滑块也在抖 → 不是某一处的绘制 bug，
而是**每帧位移量本身不均匀**。

**实测取证**（不改一行模组代码，`jcmd <pid> JFR.start settings=profile` 挂在正在跑的开发客户端上，
录音 `/ui-jfr2.jfr`，面板全程开着，含一次完整展开）：

| 观测 | 结果 | 排除的假设 |
| --- | --- | --- |
| `FramerateLimiter` 在 Render thread 上的 park 次数 | **2 次 / 3.5 分钟** | 帧率**不是**被 maxFps=260 的上限卡住（也排除了限速器 1ms 粒度睡眠导致抖动的猜想） |
| `thread-cpu-load`：Render thread | 0.13% 系统 + **1.30% 用户** | 面板的 CPU 开销（Skia 绘制 / 文本 / 排版）**不是**瓶颈 |
| `cpu-load` 整机 JVM | 平均 1.54% | 同上；热点表前 25 名全是世界渲染（CloudRenderer / Sodium chunk tree / C2ME / EMF） |
| `jdk.JavaMonitorEnter`（Render thread） | **0 次** | 不是等锁 |
| `gc` / `gc-pauses` | 每约 8 秒一次 Young GC，停顿 2~6ms；偶发 Old GC 9~16ms | 不是持续性卡顿源，但属于**周期性帧时尖峰** |

**结论**：这一帧多长由**世界渲染**决定（`enableVsync:false`、`maxFps:260`、`renderDistance:32`、
单人世界同时还跑着集成服务端与区块构建），帧长在 4ms~20ms 之间起伏；而模组动画推进用的是
**原始 dt**（`(now - lastRenderMs)/1000`，只做了 33ms 上限）→ 每帧走的像素数忽多忽少，
眼睛看到的就是「一步大一步小」。原版界面的动画是「每帧固定增量」（帧长再抖每帧位移都一样），
所以同一个客户端里原版界面看着顺、模组界面顿。

**修复（三处，互相独立）**

1. **动画步长走平滑时钟** — 新增 [FrameClock](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/anim/FrameClock.java)：
   把真实帧间隔做一阶低通（τ=120ms，单帧上限 33ms，>250ms 视为断档重新起算），
   `ClickGuiScreen` / `PanelScreen` / `ModuleScreen` 三处帧首统一改用它产出的 dt。
   低通只压抖动、不压平均，长期平均步长仍等于真实帧间隔 —— 动画时长不变、低帧率下也不会变慢。
2. **视口外剔除** — [CardPage.draw](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/page/CardPage.java#L207-L222)：
   卡片顶边落在内容视口之外（含 24px 余量，给投影糊开）就整张跳过。多个分组全展开时清单长过一屏，
   屏幕裁剪之外的行本来也看不见，再逐行布局 + 多层 Skia 绘制只是白烧帧时。命中不在绘制里判，剔除不影响可点性。
3. **玻璃世界帧复用** — [SkiaBlurRenderer.captureWorldFrame](file:///d:/mcaddon/yiyiaddon/src/main/java/com/yiyiaddon/ui/render/SkiaBlurRenderer.java#L102-L140)：
   登记区域与手里那张一致时最多连用 3 帧。原先每帧都 `glGenTextures + glTexImage2D` 一张面板大小的纹理
   （guiScale 3 下约 2508×2148 RGBA8 ≈ 20MB）+ `glBlitFramebuffer` + `glFlush`，画完再删 —— 逐帧分配/释放
   会让帧时抖。面板静止（展开 / 滚动正是这个状态）时区域不变 → 复用；面板在动时区域每帧都变 → 仍逐帧重采，
   不会露出错位背景。世界帧是 GUI 上屏前截的，复用也不会引入面板自反馈（旧实现专门避开的蓝雾）。

**验证**

- `.\gradlew compileJava --console=plain -q` → **EXIT=0**；重建客户端后实机确认：面板正常渲染、多个分组同时
  展开的行/状态/对齐都对、玻璃无蓝雾或无错位（视口剔除与世界帧复用均未造成可见回归）。
- **平滑时钟的数值验证**（按 `Spring.critical(0.28)` 的真实常数 ω=5.8/0.28、8ms 子步复刻，帧长按实测分布生成：
  主体 4~6ms，尖峰概率 8%），跑 150 次展开动画，量「折角」= 某帧位移相对前后邻帧均值的偏离（这个指标
  能隔离弹簧自身的加速曲线，只留帧长抖动造成的位移不均匀）：

  | 推进方式 | 最大折角（均值） | 折角 > 3px 的帧 | 到位帧数 |
  | --- | --- | --- | --- |
  | 原始 dt | **16.9 px**（≈ 半行） | 879 个（每次动画 5.86 个） | 99 |
  | 平滑时钟 | **1.6 px** | 18 个（每次动画 0.12 个） | 93 |

  例：一帧 16.8ms 混在 4~6ms 的帧里，原始 dt 下那一步走 **18.5px**（邻帧约 7px，即一次 2.6 倍的跳变），
  平滑后是 7.5px；到位帧数 99 → 93，动画总时长基本不变（低通只压抖动、不压平均）。
- 原始录音留档：`归档/ui-jfr-20260921-1.jfr`（多人服务器段，限速器活跃）、`归档/ui-jfr-20260921-2.jfr`
  （单人世界段，本节全部数据来源）。

**教训（进检查表）**：动画质量的怀疑顺序应该是「**时钟** → 布局 → 绘制」，而不是先改动画曲线；
用户说「抖动」时先问「谁在抖」—— 滑块也抖就说明是全局的每帧位移量化问题，不是局部绘制 bug。
性能结论一律以 `jcmd JFR` 实测为准（本轮四条实测否掉了三个猜想）。
