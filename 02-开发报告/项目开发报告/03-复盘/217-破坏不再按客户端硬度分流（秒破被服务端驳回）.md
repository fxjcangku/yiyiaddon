# 217 · 破坏不再按客户端硬度分流（「秒破」被服务端驳回）

- 日期：2026-09-22
- 触发（用户原话）：「死作物没汉化 … 然后现在导致不挖掉死作物 你看日志 没挖掉」
  「（那格）能挖掉 空手 不过有硬度 跟巨型菠萝一样 用效率挖的话就挖的很快 左键 用空手挖得慢
  所以要适配每一个服务器 之前的服务器挖一下就掉了 这个服不一样 要学习才行」
- 相关：[196](196-复盘-巨型变种砸一下又弹回来始终挖不掉.md)（同一根因的另一半：那次只修了「非零硬度」那条路）

## 一、日志证据

```
20:09:20  发现枯死作物 · 正在清理
20:09:21  START_DESTROY_BLOCK 4802,85,-5605（共 8 格，同 tick 连发 START+STOP，连发两遍）
20:09:27  发现枯死作物 · 正在清理      ← 又发现了，说明上一轮没清掉
20:11:19 / 20:11:21 同上
```

**关键判据：这一路没有任何 `破坏 开始挖掘` 日志。** 那条日志只在 `breakAt` 走「会话」分支时打；
没有它，说明这些格子走的是**同 tick 秒破**那条快捷。而秒破全被服务端驳回、方块一直在，
于是每轮重扫又把它当待办派发一遍 —— 死循环。

## 二、成因：一条以「客户端硬度」为前提的快捷

```java
if (requiredDigTicks(digProgress(mc, pos, state), SPECIAL_BREAK_THRESHOLD) == 0) {
    return owner.adapter.breakBlock(pos, Direction.UP);   // START+STOP 同 tick
}
```

`digProgress` 读的是客户端算出来的每刻进度，**它的前提是「客户端认定的硬度 == 服务端认定的硬度」**：

- 真零硬度方块（绊线 / 农作物）：`getDestroyProgress` 返回 `+∞` → 0 刻 → 一包即毁 ✓ 快捷成立；
- 这台服的死作物：绊线承载、模型被服务器资源包换掉 → **客户端算 0 硬度**，
  但服务端按自己的判定要按住若干刻 → 秒破一律被驳回 ✗ 快捷不成立。

用户手动验证正好印证：「空手能挖掉、有硬度、效率工具挖得快」—— 那格在服务端**是要按住的**。

上一轮（第 196 条）只修了反方向：客户端算「非零硬度」时不再走秒破、改走会话。
这次的场景是**客户端算零硬度、服务端却要按住**，于是从另一半漏了过来。

## 三、改动

1. **取消「按客户端硬度分流」**：`breakAt` 一律走完整会话（START → 按够 tick → STOP）。
   - 真零硬度方块：服务端收到 START 即销毁，客户端下一 tick 见到空气就判成功 —— 只多 1 tick；
   - 要按住的方块：按估算按住再 STOP，估算离谱时退回固定时长并逐轮翻倍。
   - 一句话：**模块不猜服务端要多久，只负责按到底并读结果**。
2. 「一包即毁」这个读数只保留一个用途：**不必先换手**（省掉绊线类格子的换手开销）。
   这一轮若被驳回，`tickBreakDig` 的翻倍重试里本来就会换手拿工具，所以「这服要工具」也能自己补上。
3. **首轮按住时长不再可能是 0**：客户端算零硬度时给最小档（20），之后 20 → 40 → 80 → 120 收敛。
   （给 0 会让「服务端其实要按住」的格子永远只按 0 tick —— `0 × 2` 还是 0，永远挖不掉。）
4. 批量破坏保持原样：它是 best-effort 快路径，服务端驳回时那几格下一轮作为主目标走会话流程，照样清得掉。

### 第二轮（改完仍被指出「没有用包里的效率」）

用户复测：**「可以挖了 但是没用用包里的效率」** —— 能挖掉，但慢，因为手里那件没换。

成因：我第一版把「客户端算一包即毁」当成「不必换手」的理由。可服务端是在 STOP（或 START 即判定）
那一刻按**手上那件**算进度的，客户端算出来的一包即毁**与它无关**：
- 空手（或拿着纸片）→ 服务端按 1.0 的速度算 → 要按住二十几刻；
- 换上效率工具 → 进度爆表 → 服务端收到 START 就销毁（正是玩家手动说的「点一下就掉」）。

一句话：**少换一次手，换来的是 20 倍的等待**，这笔账完全算反了。

处置：破坏**一律先走 `ensureDigTool`**（含零硬度那一类），`instantBreak` 只保留「定首轮按住几刻」这一个用途。
真零硬度的格子不受影响：服务端第一刻就把它拆了，紧接着手就换回来了。

## 四、为什么这次不再需要「按服务器学习」

用户的原话是「要适配每一个服务器 … 要学习才行」。但这次问题的本质不是**口径不同**，
而是**我们用了客户端估算去替服务端做决定** —— 同一套代码换台服务器就失效。

正确的适配方式是让流程本身与服务器无关：**只发「按住左键」这一套标准动作，按到方块消失为止**。
零硬度与要按住的方块在这套流程下都成立，所以不必为任何服务器写死参数，
真正需要"学"的只有那些**语义不同**的东西（例如特殊变种的收法是左键还是右键、要不要专用工具 —— 那是第 194/204 条）。

判断标准可以固化下来：
- **只是快慢/时长的差异** → 不要学，走服务端权威的通用流程；
- **动作或语义不同**（左键还是右键、要哪件道具） → 才需要按服务器学。

## 五、验证

- `GetDiagnostics`：`StardewFarmExecutor.java` 0 诊断。
- 待实机（jmy）：让模块去清那株枯死作物，期望日志出现
  ```
  破坏 开始挖掘 目标=4802,85,-5604 … 按下按住 20 tick
  破坏 目标已消失 目标=4802,85,-5604
  ```
  且不再反复「发现枯死作物 · 正在清理」。若第一轮 20 tick 不够，应看到「结束挖掘」后重来一轮
  （按住 40 / 80），最终消失。

## 六、教训

1. **凡是「用客户端算出来的量去替服务端下结论」的分支，都要标出来重点怀疑**：
   硬度、破坏速度、命中判定这类量客户端都有本地近似值，服务端一律有最终解释权。
   本次与第 196 条是同一个错的两半，分两次才补全 —— 补的时候应当一次问清「两个方向都覆盖了吗」。
2. **「快路径」必须带失败回退**：秒破本身没错（绝大多数服上它更快），错的是**没有回退**。
   现在它有回退（下一轮走会话），所以可以安全保留。
3. **按住时长这类"估算"绝不允许出现 0**：0 在翻倍重试里是不动点，会把重试机制整个废掉。
