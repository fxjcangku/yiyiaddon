## 二、点位的唯一性与校验口径（★ 我误改 + 用户两次澄清，最终裁定见 §2.3）

### 2.1 我误改了什么

我把「点位」改成了 `Map<类型, List<点位>>`，**每类型每维度各一条**（主世界一个矿物箱、下界一个矿物箱
互不覆盖），覆盖保护 / 删除 / 清空也全部按「本维度」判定。

用户当场指出：**旧项目就是每类型只能设一个**。这条是我的越界改动。

### 2.2 第一轮回滚（撤销维度隔离）

`repository/MiningPointStore.java` 恢复旧结构：

- `Map<MiningPointType, MiningPoint>` 每类型一条；`get` / `has` / `set` / `remove` / `size` / `clearAll`
  全部回到「全局单条」语义。
- 落盘回到「单个坐标对象」写法。读取仍兼容中途出现过的数组写法（取第一项），避免已写出的档案读不回来。
- 删除本轮新增的 `hasOtherDimension` / `otherDimension` / `getAll` / `countInCurrentDimension` /
  `clearCurrentDimension`，以及围绕它们的全部界面改动：

| 文件 | 撤销内容 |
| --- | --- |
| `AutoMinerModule` | 自检缺项后缀「（其它维度已绑 X）」撤销，`addMissingPoint` 回到「未绑才加原文案」 |

### 2.3 第二轮回滚（撤销旧项目的两道几何校验）— 用户最终裁定

用户澄清真实意图：**「不能设置两个相同的箱子」= 唯一性只按类型判**；而三个点位**可以各在不同维度**
（例如下界食物箱 + 主世界矿物箱 + 末地挂机修复点）。据此：

| 旧项目 {@code WKCommand.validateBinding}（{@code :378-446}） | 处置 |
| --- | --- |
| 任一点位维度与当前维度不一致即**拒绝**（`§c跨维度绑定被拒绝！…`） | **删除**。跨维度拒绝会让「三点各在一个维度」这套用法直接不可配 |
| 三点位两两距离不得超过 **32 格**（`%s 与 %s 距离超过 32 格…`） | **删除**。点位分处不同世界，距离没有意义 |
| 同一 key 已有绑定即拒绝重设（覆盖保护，旧 `:133-137` 等） | **保留**——这就是用户要的「不能有两个矿物箱」 |

落地：`MiningPointStore#validate` 与其 `MAX_DISTANCE` 常量、两条文案、`MiningBindingService` 的两处
调用与 `VALIDATE_HINT` 常量一并删除。点位上仍记录当时所在维度，供状态页 / `.wk` 回执 / ESP 显示。

**由此产生的行为差异（属有意差异，需补入 42 号 §三 清单）**：旧项目的这两条拒绝在界面上**不再出现**。

### 2.4 教训（写入本文档以便后续批次对照）

- 旧项目的设计选择（哪怕看起来像缺陷）**不得由我单方面判定为 bug**。要改必须先讲清「旧项目是什么样、
  改完会变成什么样」，由用户拍板。
- 用户说的「只能设置一个」指的是**类型唯一**，不是「全项目只有一个坐标，也不能跨维度用」。
  我第一轮按「维度隔离」理解、第二轮按「恢复旧校验」理解，**两次都理解错了**。
  以后遇到这类表述，先把「你指的是哪一种」列成选项确认，不要直接施工。
- 复核时列出的「缺口」里，凡属**行为/数据语义**的，一律走「提请用户裁定」，不得混在「修复」里直接施工。

### 3.1 静默容器（`SCREEN_OPEN` → `event.cancel()`）

`AutoMinerModule` 订阅 `SCREEN_OPEN`，逐条照旧 `:1172-1182`：

- 玩家未进世界直接返回；
- 模块没开不拦（旧 `isActive()`）；
- **背包放行**——旧判定 `!(screen instanceof InventoryScreen)`，玩家按 E 必须能开背包；
- 其余容器界面一律 `cancel()`，`EventDispatcher:94-101` 收到 cancel 后 `client.setScreen(null)`。

**实现口径**：事件载荷只带界面类名（`EventDispatcher:95`），所以旧代码的
`instanceof AbstractContainerScreen<?>` 换成类名判定 `Class.forName(名字)` +
`AbstractContainerScreen.isAssignableFrom`——与 `StardewFarmModule` 同一做法，挖矿这边写了一份私有副本。

**已核实不会破坏卸货**：`MiningContainer#isContainerOpen` 读的是 `mc.player.containerMenu`
（`:314-332`），不是 `mc.screen`，所以取消界面不影响箱子数据的同步与发包。

**一处旧行为须知**（照旧保留，未额外放宽）：旧判定只放行 `InventoryScreen`。创造模式按 E 打开的是
`CreativeModeInventoryScreen`（**不是** `InventoryScreen` 的子类），因此在挖矿运行中、创造模式下
背包会被一起取消。旧项目就是这个行为，本次按一比一保留；若要放行，说一声加一行即可。

### 3.2 退出世界自动关模块（`DISCONNECT` → 关模块）

`AutoMinerModule.onEvent` 的 `DISCONNECT` 分支在做完 `pointStore.invalidate()` 之后，
补上旧 `onGameLeft` 的那一步：`if (isEnabled()) ModuleManager.setEnabled(MODULE_ID, false);`
（旧写法 `isActive() → toggle()` = 「在开才关」）。

顺序说明：先作废点位视图与装载上下文，再关模块——`onDisable` 里不会再触发按错误服务器写盘。
`ClientEventBus.publish` 是先快照再回调（`:107-119`），因此在回调里退订自己不会并发修改。

### 3.3 `save()` 服务器守卫

- 内存快照记 `loadedServer`；`save()` 在 `loadedServer` 为空或与 `WorldIdentity.fileSafeServer()` 不一致时**拒绝写盘**。
- 写入前 `ensureLoaded()`：服务器键变化则先重载，避免拿着旧服务器的数据覆盖新服务器的档案。
- `invalidate()`：`AutoMinerModule` 订阅 `ClientEventType.DISCONNECT`，断线即作废内存快照。

### 3.4 关模块退场清理

`reset()` 直接把状态置回 `IDLE`、不经过 `onStateExit`（旧项目亦如此，属旧实现遗留）。
新增 `shutdown()`：先补做退出副作用（`stopRepairCombat` / `restoreHotbar` / 释放右键），
再按当前状态恢复 Baritone `allowBreak`，最后才 `reset()`。`AutoMinerModule.onDisable()` 改调它。
