# 155-复盘-洒水器品质核对为何仍失效与实测归属过滤

日期：2026-09-21
分支：master（业务唯一真源，按第 231 条；26.2 分支另行 cherry-pick）

---

## 一、事件

154 已经加了「绑定时核实物品质」的 `displayMismatch`，但用户重启客户端吃新包后仍报：

> 还是可以乱绑定你看日志

并附两条成功播报（`run-26.1.2/logs/latest.log`）：

```
[02:12:27] 已设置洒水器点位 · 坐标 X4797 Y85 Z-5603 · 类型=初级洒水器 · 覆盖范围=实测 7×7 · 湿盆 35 格（顶到扫描边界…）
[02:12:33] 已设置洒水器点位 · 坐标 X4803 Y85 Z-5597 · 类型=初级洒水器 · 覆盖范围=实测 7×7 · 湿盆 35 格（顶到扫描边界…）
```

同轮另有一条关键反证：

```
[02:11:59] 设置洒水器失败 ▸ 原因=认不出这一格是哪一种洒水器；请写明类型：.stardew 添加洒水器 初级洒水器
```

**写明类型就必然成功、不写就必然认不出** —— 说明 `matchSprinklerDisplay` 在这一格上恒返回 `null`，
`displayMismatch` 的「认不出 → 放行」分支被无条件命中，核对等于没做。

## 二、根因（两处，缺一不可）

### 1. 读实物的口径错了：只读 `ITEM_MODEL` 组件

旧 `matchSprinklerDisplay`：

```java
SlotAccess slot = entity.getSlot(0);
ItemStack stack = slot == null ? ItemStack.EMPTY : slot.get();
var model = stack.get(DataComponents.ITEM_MODEL);
if (model == null) continue;          // ← 这里就把实物整个跳过了
```

本服是 **ItemsAdder 旧布局**：整服自定义物品挂在 `minecraft:paper` 上，身份写在
`custom_model_data` 里，数据组件中**没有 `minecraft:item_model`**（同项目 137 复盘已取证）。
于是 `model == null` 恒定成立 → 每个展示实体都被 `continue` 掉 → `match` 恒为 `null`。

### 2. 就算读到了模型，比较口径也会漏

旧比较是逐字比：

```java
itemModel.equals(sprinkler.itemModel())
```

而同一台洒水器在资源包里有两个模型（`sprinklers/sprinkler_1` 环境模型、
`sprinklers/sprinkler_1_item` 背包图），世界里挂的与索引登记的可能是任一个。
逐字比较必然出现「明明是同一种却对不上」。

**合并后果**：识别链断在实物那一端，`displayMismatch` 拿到的 `actual` 永远是 `null`，
按既定口径（认不出 → 放行，为多服务器兜底）无条件放行。这不是 154 的判据错，
是**判据的输入一直是空**。

## 三、改动

### 1. `StardewPointActions`（主改）

- `matchSprinklerDisplay`：改遍历全部 `Display`（不再只收 `ItemDisplay`）；未命中 / 歧义各写一条
  `LOGGER.info("[星露谷] 洒水器实物识别未命中：格=… 展示物=…")` 取证日志——不能再用「猜」代替「看」。
- 新增 `sprinklerOfDisplay(Entity)`：三条证据依次比对
  ① 物品模型末段序号（`StardewInventoryService.resolvedModelOf` → `sprinklerByItemModel`）；
  ② 压平身份（`ItemModelDispatchIndex.flatIdentityOf` → `sprinklerByFlatIdentity`）；
  ③ 展示物名称（服务器下发的「初级洒水器」→ `sprinklerByName`）。
  `block_display` 另走方块语义，判据与方块世界路径同源。
- `sprinklerByItemModel`：两侧都先剥 `_item` 后缀再比序号名（`sprinklerSerialOf`）。
- 新增 `describeDisplay(Entity)`：诊断日志里一次给全「形态 + 物品 id + 模型键 + 名称」。

### 2. 覆盖范围实测的**归属过滤**（同轮另一处真机问题）

先前三台洒水器的实测结论几乎一模一样、且全部顶到扫描边界——一片田里湿盆连成一片，
不按归属过滤就是把隔壁那台浇的盆算到自己头上。改动：

- `SprinklerCoverage.capture(BlockPos, List<BlockPos>)`：按**水平距离**把每个盆归给最近的那台
  洒水器（等距时两边都算），只保留归属自己的格；`peers` 为空 / null 时不做过滤（退回旧行为，
  宁可多算也不算漏）。只比 XZ —— 盆层 = 洒水器层 − 1，垂直差不是归属依据。
- `StardewPointActions.sprinklerPeers(BlockPos)`：当前维度全部已绑定洒水器 + 本次这一格。
- `StardewFarmModule.measureSprinklerCoverage()`：先收集 `peers` 再逐台实测。
- 代价（已写进 javadoc）：`peers` 要尽量完整，漏一台它的湿盆就会算到旁边头上——
  这也是「先把洒水器都绑一遍，再 `.stardew 实测范围`」的原因。

## 四、验证

- `.\gradlew.bat compileJava --console=plain -q`：EXIT=0。
- `.\gradlew.bat build --console=plain -q`：EXIT=0。
- **是否实机：未实机**。用户重启客户端吃新包后的预期：
  1. 对准初级洒水器写明「高级洒水器」→ 应被拒，播报给出实物正确类型；
  2. 写明实物本身那种 → 正常绑定；
  3. 若仍认不出，日志会出现 `[星露谷] 洒水器实物识别未命中：格=… 展示物=…`，
     那一行直接给出实物的物品 id、模型键与名称，据此一条定位，不再靠猜。
- **历史错绑不自动纠正**：`4797,85,-5597` 现被标成「高级洒水器」，需重新绑定一次。
  实测覆盖范围是物理事实，与身份无关，重测即可刷新。

## 五、为何不改成「一律禁止人工写明类型」

这是多服务器适配的底线：非 ItemsAdder 布局的服务器上，实物外观未必能映射到资源索引里的
某个洒水器条目，此时人工写明是**唯一**的绑定路径。因此本次修复仍是
「**认得出就必须一致**」，不是「一律不许写」。识别不出时放行 + 留取证日志，
既保住别的服务器，也把本服的识别缺口暴露出来。
