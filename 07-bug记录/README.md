# 07-bug记录

放「**已修好、但还没随包发出**」的玩家可见改动 —— 也就是「发现 bug → 记录 → 下一次发布填进发布页」
这条链的中间那本账。

- **一份待发布版本一个文件**，文件名 = 它要随哪个版本发出去（如 `1.0-beta2.md`）。
  该版本发布完成后在文件开头标「已随 `<标签>` 发布」，然后另开下一版的文件；旧文件原样留档，不删。
- **发现即记**：用户实机反馈的、自己复现的、出包验收时发现的都记，**只记玩家能看见的效果**
  （什么操作会怎样 → 现在怎样）。内部实现（类名 / Mixin / 混淆 / 映射 / 加固）不进这里，
  那些写在 `02-开发报告/项目开发报告/03-复盘/`。
- **不重复记**：当前线上包已经有的改动不再写进新版本的表。判断依据是线上 Release 的附件与正文，
  不是记忆（可 `gh release view <标签> --repo fxjcangku/yiyiaddon --json body` 回读）。
- **发布时**：按《开发习惯》第四十章（第 238~241 条）把条目誊进发布页正文的 `1 更新日志`，
  按 修复 / 新增 / 变更 归类，一类一条、一条一句话。
- **没有台账文件不许发**（《开发习惯》第 245 条）：出包前先确认 `<本版版本号>.md` 在，不存在就先建一份，
  哪怕这一版只有一条；发布动作逐条过文件里的「发布清单」（版本号 / 正文 / 附件 / 埋点 / 回读）。

规则正本见 `开发习惯.md` 第四十一章。
