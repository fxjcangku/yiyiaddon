### 7. 修复 · 洒水器被挖掉后仍被当成维护对象（ESP 还在、还报「本轮 1 台」）（192，2026-09-22）

- 状态：**已实机验收通过**（用户 2026-09-22「刚刚的bug已经修好了，被挖就不启动了」；日志证据
  22:37:50 自检播报「启动自检未通过 ▸ 洒水器 4797, 85, -5603：洒水器已不存在（那一格的洒水器实体消失了，
  可能已被挖掉）」并禁止启动）

- 现象：已绑定的洒水器被挖掉之后，模块照常走去「维护」它、ESP 方框还留在原处，
  并汇报「洒水器维护完成 ▸ 本轮 1 台」——玩家看到的是一条假结论。
- 成因：贴图形态洒水器（`item_display`）的载体格本来就是空气，绑定校验只比 BlockState，
  被挖掉后空气还是空气 → 判定「绑定仍然有效」；维护链路又只按「本维度有哪些点位」取对象，
  从不做点位校验。
- 处置：绑定校验对贴图形态追加「那一格还挂着展示实体」；点位校验给出确定结论「洒水器已不存在」；
  维护链路与 ESP 都剔除这类点位（「区块还没加载」不算剔除），并第一次发现时提示一次、给出清理出路。
- 玩家视角写法（待誊入正文）：
  - `修复洒水器被挖掉后仍作为维护对象、ESP 标记留在原处的问题 —— 现在会识别该洒水器已不存在，跳过维护并提示清理点位。`

### 8. 修复 · 同一格换成别的洒水器型号仍被当成原来那款（193，2026-09-22）

- 状态：**已实机验收通过**（用户 2026-09-22「ok了 修复了」）

- 现象：把已绑定的「优质洒水器」换成「高级洒水器」，模块照样按优质洒水器维护——认不出这一格换了东西。
- 成因：贴图形态洒水器的型号信息只在展示实体的物品上（方块格永远是空气）；绑定校验只比了

  绑定时也当场核对型号，不符直接拒绝并说明；失效的点位从维护对象与 ESP 里剔除并提示一次。
- 玩家视角写法（待誊入正文）：
  - `修复同一格替换为其它洒水器型号后仍按原型号维护的问题 —— 现在核对该格实际挂载的型号，不一致时跳过维护并提示重新绑定。`

### 9. 变更 · 特殊变种（金色 / 巨型 / 变种）的收法按服务器学习（194 + 204，2026-09-22）

- 现象：本服（jmy.seasonmc.xyz）的巨型菠萝要「左键破坏」（工具不限、空手也能挖、拿工具更快），
  而老服的金色番茄是「手持金锄头右键」—— 口径写死在代码里，总有一边收不了；
  也有的服是「左键破坏但必须手持某件专用道具」，写死的工具同样对不上（用户 2026-09-22 三条口径）。
- 处置：特殊变种收法改为<b>按「服务器 + 资源包指纹 + 作物」学习并保存</b>，一条口径 = <b>动作 + 手持</b>
  （动作：左键破坏 / 右键；手持：不限 / 玩家当时手里那件工具；工具身份不看附魔 —— 附魔只决定挖得快不快）：
  **只从玩家自己的手动动作里学**（空手砸掉也算；那一格确实被收掉才落盘），
  不自动试探（试探会砸坏右键服上的巨型作物，不可逆）。
  同一个服学会一次就够：本服其它还没学过的变种先按同一条收（作物专属记录优先于它）；
  口径要求专用工具而背包里没有那件时，只提示一次并跳过这一格，不停机、不影响收其它作物。
  没学过的服照旧用老口径（金锄头右键），互不影响。本服（jmy）三种巨型
  （巨型卷心菜 / 巨型菠萝 / 巨型番茄）已预置为「左键破坏 + 工具不限」，无需示范。
- 玩家视角写法（待誊入正文）：
  - `特殊变种（金色 / 巨型 / 变异作物）的收割方式改为按服务器学习：手动收获一次即记录动作与手持工具，同一服务器内其它变种沿用同一口径，不同服务器各自独立、互不影响。`
  - `若某服务器要求专用工具，背包与副手里没有那件时只提示一次并跳过该格，不影响其它作物收获。`

### 10. 修复 · 背包塞满后还在收菜 / 产物箱满了没有提示（195，2026-09-22）

- 现象：① 背包 36 格全被别的东西占满，模块照样一格一格收菜（收下来的成品只能掉在地上），
  并没有先去卸货；② 产物箱满、卸不出去时，只有一条普通状态行「产物箱没有可用空间」，
  既不显眼也不停手，玩家以为还在正常干活。
- 成因：① 插队卸货的资格写的是「该作物自己的成品数达到卸货阈值」，背包被无关物品塞满时
  这个阈值永远到不了，于是插队永远不成立；② 箱子满只更新状态卡、退避 60 秒继续跑。
- 处置：① 背包**一个空格都不剩**时改为「只要还有一件超出保留量的成品就去卸」（不再看阈值）；
  ② 背包满了又卸不出去（没绑产物箱 / 不在当前维度 / 箱子没空间）时**停收停拣**并报一条
  `critical`，说清卡在哪一步与出路，背包腾出空间后自动恢复；③ 产物箱没空间改按 `critical` 播报。
- 处置（同日第二次实机复现后补，195 续）：
  ④ **「空格数」数错了边界**：`Inventory#getContainerSize()` 是 41 格（36 主背包 + 4 护甲 + 1 副手），
  把护甲 / 副手那 5 个空位算进来，36 格塞满时仍报「还有 5 格空」——于是「满了就停收 / 先去卸货」
  两条判据**永远不成立**（实机：背包看着塞满，模块照收不误、也不去卸货）。现在只数主背包 0~35
  （`StardewInventoryService.MAIN_SLOTS`，边界只写一处）。

### 11. 修复 · 巨型变种「砸一下又弹回来、始终挖不掉」（196，2026-09-22）

- 状态：**已推迟到 `1.0-beta3.md`**（用户 2026-09-22：巨型作物这块留到 beta3 一次性写进更新日志，
  本版不出现；代码已在树上、随 beta2 包发出，推迟的是更新日志条目，不是回滚）
- 现象：故意放在地上的巨型菠萝，模块尝试破坏时有破坏动作、方块闪一下又回来，始终没被挖掉；
  玩家也看不出它用的是哪只手 / 哪件东西。
- 成因：巨型作物的承载体是<b>非零硬度</b>方块（紫颂植株 0.4），而破坏走的是「零硬度载体」那条
  `START + STOP 同 tick 连发`的通道 —— 服务端按 `进度 × 已挖 tick ≥ 0.7` 校验，同 tick 的 STOP
  直接被驳回；那条通道还会<b>本地立刻置空气</b>，于是观感就是「闪一下又回来」，并且本地预测让
  验证层误判成功、下一轮方块又回来。
- 处置：破坏按服务端阈值分两条路 —— 零硬度载体（绊线 / 农作物）保留同 tick 秒破；非零硬度走
  `START → 等够所需 tick → STOP`，期间协调器把控制权留在这一格；STOP 后 20 tick 未消失就重来
  （最多 3 轮），仍不行则 `ABORT` + 退避 + 提示「服务端没放行这一格」。
  同理，批量破坏只对零硬度格子连发，非零硬度的格子留给下一轮走完整流程。
- 处置（同日第二次实机复现后补，196 续）：日志里只有「破坏 开始挖掘」、从来没有「结束挖掘」——
  ① 序列原先靠相位机反复调用才能推进，一旦中途重扫 / 换任务 / 相位跳转，那个 START 就永远悬着；
  现在改由协调器**每客户端 tick 独立推进**（`tickBreakDig`），START 之后一定会等到 STOP 或 ABORT；
  ② 重规划原先无条件 `ABORT`，而重规划随时可能发生（重扫、季节代次变化、玩家开背包…），
  于是「START → 被 ABORT → 再 START」无限循环、方块永远挖不掉；现在重规划不再中止序列
  （换目标才 ABORT，停机 / 换世界仍兜底）。
  ③ 另加「开挖前先换手再算进度」+「所需 tick 超过 200 就不开挖掘会话」两道闸：实机里手里拿着苹果时
  每刻进度 1.0E-4、需 <b>7002</b> tick，模块开了一个永远挖不完的会话（玩家看到的就是「站着瞄着不动手」）。
- 玩家视角写法（待誊入正文）：
  - `修复清枯苗 / 清错位 / 清杂物与巨型变种收割中「方块闪动后复位、始终不掉落」的问题 —— 现在按服务端挖掘进度挖到底，挖不动时明确提示。`

- 查证过程（共五轮，前四轮的推断都被实机否定，**教训写在最后**）
- 现象：故意放在地上的巨型菠萝（`customcrops:pineapple_gigantic_pineapple`，载体
  `minecraft:chorus_plant`）认出来了、口径也学对了（日志「特殊变种收法已学会 … 动作=BREAK 存盘=true」），

  （服务端 `too far` 阈值 5.5 格内）、`onGround=true`。也就是说**客户端算得出、够得着、手也对**，
  而按住 120 tick（阈值的 **14 倍**）仍被驳回 —— 可见服务端**根本没在处理这些 STOP**。
- 成因：服务端 `ServerPlayerGameMode` 全局只记**一个** `destroyPos`，STOP 分支的第一句就是
  `if (pos.equals(this.destroyPos))`，不等则整段跳过。而模块在挖那一格的同时，**批量清理**
  （`sendBatchOne` → `breakInstantIfSafe`）还在对**别的零硬度格子**发秒破的 START —— 每发一次
  START，服务端的 `destroyPos` 就被改到那一格，我们这一格的 STOP 随即全部落空。
  挖不动的观感与「服务端保护了这一格」一模一样，于是前两轮一直在换工具、加长按住时间、
  改换手时机上打转（那些改动本身没错，但都不是这一格挖不掉的原因）。
- 处置（第一轮）：破坏会话期间**独占**服务端那一个 `destroyPos` —— 会话进行中 `breakAt` 只服务
  这一格（不再「换目标先 ABORT 再重开」），`breakInstantIfSafe` 也直接跳过、不发任何 START。
  这两条本身没错（服务端确实只记一个 `destroyPos`，同批秒破真的会抢走它），但实机复测仍全拒。
- 处置（第二轮，定案）：**破坏整条链路改走原版 `MultiPlayerGameMode`** ——
  `startDestroyBlock` / `continueDestroyBlock` / `stopDestroyBlock`，由原版维护 START 时机、
  本地进度累计到 1.0 才发 STOP、以及换手包的同步，与玩家手动按住左键**逐字同源**。
  模块自拼 START / STOP 即使包类型、顺序、面都对，仍与服务端认的那一套存在细微差异，
  表现就是「怎么按都不认」。自算 tick / 自选 STOP 时机 / 自管裂纹这些副本一并删除
  （`BREAK_MIN_HOLD_TICKS`、`BREAK_MAX_HOLD_TICKS`、`BREAK_FALLBACK_HOLD_TICKS`、
  `BREAK_RESEND_AFTER_TICKS`、`BREAK_MAX_ATTEMPTS` 五个常量与 `holdTicksFor`）；
  超时改成「连续推进 200 刻（10 秒）仍不消失」封顶，仍不动就播报 + 60 秒退避。
- 处置（第三轮）：日志打出 `交互距离=5.50`、`原版接管=true`、离方块 3.49、`onGround=true`
  —— 距离与路径全部正常，而同一时刻另一格打出 `选中物品=2 minecraft:apple 每刻进度=1.0E-4`
  （苹果没有 TOOL 组件、速度本就是 1.0，不该算出 0）。两条并起来只剩一个解释：
  **客户端与服务端对「手上那件」认知分叉** —— 服务端手里是那个 TOOL 组件速度为 0 的自定义道具，
  `0 × 任意时长 = 0`，永远到不了 0.7（这也顺带解释了「零硬度格子能秒破、非零硬度一格都砸不掉」：
  秒破走的是「进度 ≥ 1.0 立即拆」，不需要速度）。
  分叉来源：`DefaultStardewAdapter` 的换手与视角发包（`ServerboundSetCarriedItemPacket`、
  `handleContainerInput`、`ServerboundMovePlayerPacket.Rot`）是模块里**唯一没走绕行通道**的几个 ——
  一旦被本模组自己的发包规则拦下（延迟 / 取消），客户端本地预测已经换了手、服务端却没换，
  分叉会一直留到下一次全量同步。
  处置：换手与视角同步统一改走 `ClientPacketSender`（新增 `selectHotbar` / `swapToHotbar` /
  `swapOffhandWith`，全部绕行发放），并新增 `sendRuleCount()`；破坏日志末尾带上 `发包规则=N`，
  复测一次即可判定「这些包有没有被本模组的规则处理过」。
- 处置（第四轮，定案）：
  - ① `发包规则=0` —— 包没被本模组任何规则拦过，**第三轮的「分叉」推断不成立**（换手包改走绕行
    本身是正确做法，保留）。
  - ② 第三轮「把破坏交给原版 `MultiPlayerGameMode`」这条**是错的、已回退**：原版那套状态是给
    「玩家真的按住左键」用的 —— `Minecraft` 每刻都会检查攻击键，没按下就调 `stopDestroyBlock()`。
    模块借它的推进时，会话状态每刻被清掉，`continueDestroyBlock` 于是每刻走「重开」分支、
    **每刻重发一次 START**；服务端的 `destroyProgressStart` 随之每刻重置，「已挖 tick 数」永远是 0，
    `0.7` 永远达不到。**这就是「原版流程挖满 201 刻仍纹丝不动」的真正原因。**
  - ③ 真正缺的是**挥手**：原版「按住左键」的完整动作是「挥手 + START + 每刻推进」，模块直接拼包
    漏掉了挥手（`ServerboundSwingPacket`），而服务端的破坏校验常要求破坏动作伴随挥手动画
    （反作弊的常见判据）。
  - 现在：自己管 START / STOP（一个 START 只配一个 STOP，确认窗口内绝不重发）+ 每轮开挖前
    挥一次手；会话式实现与五个常量（`BREAK_RESEND_AFTER_TICKS` / `BREAK_MIN_HOLD_TICKS` /
    `BREAK_MAX_HOLD_TICKS` / `BREAK_FALLBACK_HOLD_TICKS` / `BREAK_MAX_ATTEMPTS`）全部恢复，
    `holdTicksFor` 一并回来；`breakAt` 的会话闸与「会话期间不秒破」两条保留。
  - 诊断字段保留：破坏日志带 `选中槽` / `选中物品` / `离方块` / `onGround` / `交互距离` / `发包规则`。
- 处置（第五轮，有实测对照）：给 `SendInterceptor` 加「发包记录」开关（把方块动作 / 挥手 / 选中槽
  三类包的时序与绕行状态打进日志），请玩家**手动**砸同一格做对照 —— 拿到决定性差异：
  原版「按住左键」在挖掘期间是**每刻发一次挥手包**（`Minecraft#continueAttack`），
  实测一秒约二十次 `挥手 MAIN_HAND`；而模块此前只在开挖时挥一次、之后二十刻静默，
  服务端的破坏校验因此认为「没在挖」，把 STOP 驳回。
  处置：破坏会话期间（`tickBreakDig`）**每刻挥一次手**。
  这条是第一份来自「手动 vs 模块」直接对照的证据，不再依赖对服务端判据的推断 ——
  前四轮的教训就是：客户端能看到的量（距离、进度、手持物、包类型）全都正常时，
  该做的是把两边的包序列摆在一起实测，而不是继续猜服务端。
- **教训**（下次遇到「服务端一律不认」时先照这条走）：
  - ① 客户端的量（距离 / 进度 / 手持物 / 包类型 / 发包规则条数）**全部正常**而服务端不认时，
    唯一有效的下一步是**把「玩家手动做同一件事」与「模块做这件事」的包序列逐条对照**，
    不要再在客户端加参数、换 API（前四轮：换工具、加长按住、改换手时机、改走原版、假设分叉，
    全部无效，白耗四轮）。
  - ② 破坏（挖掘）在协议层是**三件套**：「START 一次 + **逐刻挥手** + STOP 一次」。
    只发 START / STOP 会被服务端的破坏校验当成「没在挖」而驳回。
  - ③ 原版 `MultiPlayerGameMode` **不能**借给模块用：它的状态由 `Minecraft` 每刻按攻击键维护，
    模块驱动时状态每刻被 `stopDestroyBlock()` 清掉，`continueDestroyBlock` 于是每刻重开、
    每刻重发 START，服务端的 `destroyProgressStart` 随之每刻重置，永远过不了阈值。

  处置：`breakAt` 里「悬空时本轮不开挖」—— 等落地再挖。
- 成因二（本轮推翻的误判）：曾按「空手也算出 `物品破坏速度=0.0`」推定

    ABORT 后几秒回到 1.0」—— 0 是「边挖变 0」的常态读数，与手持物、与具体哪一格都无关；

  也就是说：该属性只影响客户端估算，不影响服务端放行，**不能反过来当「挖不动」的判据**。

  - ① 删掉「开新会话前估算离谱就拒挖」的整块及其播报与去重字段；
  - ② 删掉「松手前读数跌到 0 就废掉这一轮」的整块（它把每一轮都主动作废，表现成 START / ABORT 抖动）；

  效率附魔给的是玩家的 `MINING_EFFICIENCY` 属性（等级²，只在正确工具上生效），**不在
  `ItemStack#getDestroySpeed` 里** —— 原来的挑工具只比物品本体速度，带效率与不带效率的是同一个读数。
  处置：新增 `effectiveDigSpeed`（本体速度 + 向引擎附魔数据要来的采掘效率加成）作为挑工具排序键；
  `ensureDigTool` 换手后本轮不再同 tick 复读（客户端属性由服务端同步，换手要一个来回）。

### 32. 修复 · 清枯苗 / 清杂物「挖了不掉、反复重试」+ 破坏一律先换工具（217，2026-09-22）

- 状态：**已实机验收通过**（用户 2026-09-22「可以挖了」）
- 现象（用户原话）：「死作物没汉化 … 然后现在导致不挖掉死作物 你看日志 没挖掉」
  「（那格）能挖掉 空手 不过有硬度 跟巨型菠萝一样 用效率挖的话就挖的很快 左键 用空手挖得慢
  所以要适配每一个服务器 之前的服务器挖一下就掉了 这个服不一样」
  第二轮：「可以挖了 但是没用用包里的效率」
- 日志证据（`run-26.1.2/logs/latest.log`）：每轮都判定成待办、每轮都失败，方块纹丝不动 ——
  ```
  20:09:20 发现枯死作物 · 正在清理
  20:09:21 方块动作 START_DESTROY_BLOCK 4802,85,-5605（×8 格，同 tick 连发 START+STOP）
  20:09:27 发现枯死作物 · 正在清理     ← 又发现了
  20:11:19 / 20:11:21 同上
  ```
  关键：这一路**没有任何 `破坏 开始挖掘` 日志**，说明走的是「零硬度秒破」那条快捷（同 tick 连发），
  而不是完整挖掘会话。
- 成因：破坏按**客户端算出的硬度**分两条路 —— 算出零硬度就走「START + STOP 同 tick 秒破」。
  那条通道的前提是「客户端认定的硬度 == 服务端认定的硬度」；这台服的死作物用绊线承载、
  模型被服务器资源包换掉，客户端算出来是 **0 硬度**，服务端却要按住若干刻才放行 ——
  秒破被一律驳回、方块一直在，于是每轮重扫又把它当待办派发一遍，循环往复。
- 处置：
  - `breakAt` **不再按客户端硬度分流**：一律走「START → 按够 tick → STOP」的完整会话。
    真零硬度方块服务端收到 START 就销毁、客户端下一 tick 见到空气即判成功（只多 1 tick）；
    要按住的方块等够 tick 再 STOP。**放不放行由服务端裁决，模块不猜** —— 换服务器因此不必重新适配。
  - 「一包即毁」这个读数只保留一个用途：定首轮按住多少刻（给它最小档，不必是 0）；
    **不再用它跳过换手** —— 服务端是在 STOP（或 START 即判定）那一刻按**手上那件**算进度的，
    不换手就是「拿着纸片干等」。第二轮实机因此反馈「可以挖了 但是没用用包里的效率」，
    现在破坏一律先走 `ensureDigTool`（含客户端算一包即毁的那类格子）：空手要按住二十几刻的那一格，
    换上效率工具后服务端收到 START 就销毁（与玩家手动「点一下就掉」一致）。
  - 首轮按住时长**不再可能是 0**：客户端算零硬度时给最小档，之后逐轮 20 → 40 → 80 → 120 收敛
    （给 0 会让「服务端其实要按住」的格子永远只按 0 tick，永远挖不掉）。
  - 批量破坏保持原样（best-effort 快路径）：服务端若驳回，那几格下一轮作为主目标走会话流程照样清得掉。
- 玩家视角写法（待誊入正文）：
  - `修复部分服务器上枯死作物 / 杂物「反复重试却始终不掉」的问题 —— 现在一律按服务端的挖掘进度挖到底，不再依赖客户端估算。`

- 诉求（用户原话）：「只有首页那个界面有关闭 ui 的按钮，你帮我设置一个按 g 可以关闭 ui 吧，
  按 g 可以开启，按 g 也可以关闭」—— 模块页与控制台只有返回键，想一步关掉整个界面只能退回主界面再点关闭。
- 处置：
  - 关闭落在界面基类 `SkiaScreen#keyPressed`（全部扩展界面都是它的子类、且各自的 `keyPressed`
    最后都转发到这里），比较的是**打开键的绑定值**（`ModuleKeybindManager#isClickGuiKey`）——
    玩家改建位后跟着变；
  - 语义是「关掉整个界面」而不是「退一级」：在模块页 / 控制台里按它直接回到游戏
    （从暂停界面打开的回到暂停界面），与 ESC 的逐级返回分工明确；直接切屏、不播关闭动画；
  - 输入优先：输入框打字、键位录制在子类里先拿到键盘，**键入 g / 绑定 g 都不会被它抢走**；
  - 关闭时 `suppressClickGuiKey()` 吞掉这一次按下边沿：否则同一个 tick 的快捷键轮询会把它当成
    「在游戏里按了 G」，界面刚关又被打开。
- 玩家视角写法（待誊入正文）：
  - `变更按 G 键可关闭整个界面（原来只能打开）—— 开与关是同一个键，在任何界面下都可用；键位可在设置页更改。`

### 38. 修复 · 删掉区域后「目标选择器」里那种作物仍留在已选（2026-09-22）

- 状态：**代码已改、待实机复测**
- 现象（用户原话 + 截图）：删掉番茄那块地之后，「选择作物」里的已选一栏仍然列着番茄
  （「我刚刚不是已经删除了番茄的区域了吗 但是目标选择器里面还是有番茄 能不能同步删除选择器里面的？」）
- 成因：目标作物勾选（`StardewSettings#selectedCropKeys`）与种植区域是两处数据，
  只有「换品种」那条路会同步退勾选（`changeRegionCrop` 用 `cropKeyInUse` 判断），
  **删区域这条路没做这件事** —— 于是番茄还挂在已选里，作物计划照旧把它算成目标、
  还会跟着报「背包无番茄种子」，可全服已经没有一块地能种它了。
- 处置：
  - 新增 `StardewFarmModule#dropUnusedCrops()`：全服（跨维度）再没有任何区域绑着它时，
    从目标作物里退勾选；`removeRegion` 与 `clearRegions` 删除完区域后都调它，
    回执加一行 `目标作物 ▸ 番茄 已无区域在用，已同步取消勾选`（没有可退的就不加这一行）；
  - 判据复用换品种那条同一把尺（`cropKeyInUse` + `Selection#deselect`，后者的注释写着
    「只有能证明这个键确实已经没有任何地方在用的调用方才能调」）；
  - **有混种区时一律不动**：混种区可以种任何已勾选作物，勾选仍然有效；
  - 只退「勾选」这一处，作物计划里的数量配额原样保留，重新勾上即恢复；
  - 运行中的模块下一 tick 自动生效（`configureCoordinator` 每 tick 重读选择）。
- 玩家视角写法（待誊入正文）：已并入上面「更新日志正文（定稿）」里的对应一条。
